# URL 단축 서비스 모의 면접 회고 (2회차)

- 일시: 2026-11-27
- 형식: 확장 면접(기본 설계가 끝난 서비스에 기능 추가), 약 30분 기준. 면접관 역할은 Claude가 맡았다.
- 전제: 사용자 10억 명, 읽기 피크 약 35,000/s, L1·L2 캐시가 있는 상태 ([interview-guide.md](interview-guide.md) Part 2·3)
- 질문: 클릭 통계 → 고유 방문자 → 만료와 삭제 → 커스텀 별칭
- 진행: 네 질문 모두 직접 답하지 않고 모범 답안을 보는 **학습 모드**로 진행했다. 그래서 평가 대신 답안과 패턴을 정리한다.
- 1회차: [mock-interview-01.md](mock-interview-01.md)

## 1. 한눈에 보기

| 주제 | 핵심 패턴 | 기존 설계와 만나는 지점 |
|---|---|---|
| 클릭 통계 | 핵심 경로는 비동기로 두고, 부가 기능의 실패가 핵심 경로로 번지지 않게 한다 | 302 `max-age=300` 이 5분 안의 재클릭 집계를 가린다 |
| 고유 방문자 | 정확도와 메모리를 맞바꾸고, 병합 가능성으로 기간을 합산한다 | 원시 이벤트 30일 보관이 정확한 재계산의 근거가 된다 |
| 만료와 삭제 | 결정적인 것(만료)과 사건(삭제)을 분리한다. 캐시 TTL 이 곧 삭제 반영의 상한이다 | "키 → URL 은 불변" 전제가 깨진다. L2 전용 부정 캐시 방식을 재사용한다 |
| 커스텀 별칭 | 정확성은 이미 보장됨을 먼저 짚고, 사용자 경험과 남용에 집중한다 | UNIQUE·조건부 쓰기, range 의 건너뛰기, `ascii_bin`, 조회 키 정규식 |

- 공통 교훈: 확장 면접의 최고점은 **새 기능이 기존 결정의 어디와 부딪히는지 스스로 짚는 것**이다. 면접 전에 "이미 내린 결정 목록"(302 + max-age, 2단 캐시와 TTL, 부정 캐시 위치, 키 형식과 collation, 조회 키 검증)을 한 장으로 정리해 둔다.

## 2. 클릭 통계

**질문**: "링크마다 클릭 수를 보여 주세요. 가능하면 국가별, 시간대별로도요."

**먼저 물을 것**
- 정확도: 대시보드인가, 과금인가? → 대시보드라 1% 안팎 오차 허용으로 가정한다.
- 실시간성: 몇 분 늦어도 되는가? → 비동기 집계가 가능하다.
- 고유 방문자와 봇 제외가 필요한가? → 원시 이벤트를 남길지, 근사 자료구조가 필요한지가 정해진다.

**규모**: 클릭 수 = 읽기 수다. 평균 약 11,600/s, 하루 약 10억 건이다. 이벤트 약 100 B 면 원시 데이터가 하루 약 100 GB, 1년 약 36 TB 다. 그래서 미리 집계하고 원시 데이터는 짧게 보관한다.

| 선택지 | 판단 |
|---|---|
| 리다이렉트마다 DB `count + 1` | 응답이 DB 쓰기를 기다리고, 바이럴 링크에서 행 락 경합이 생긴다 |
| Redis `INCR` (키 × 국가 × 시간) | 총합만이면 간단하지만, 조합으로 키가 폭증하고 장애 시 유실된다 |
| **비동기 이벤트 로그 → 스트림 집계 (채택)** | 리다이렉트는 버퍼에 넣고 바로 302 를 준다. 집계는 별도 시스템이 한다 |

```
리다이렉트 서버 ──(비동기 버퍼)──▶ Kafka (파티션 키 = short_key)
  → 스트림 집계 (GeoIP, 봇 필터, 1분 윈도 합계, 고유 방문자는 HLL)
  → OLAP (ClickHouse / Druid): 시간별 집계는 영구, 원시 이벤트는 30일
```

**파고드는 질문**
- 이벤트 전송이 실패하면? 리다이렉트는 실패시키지 않는다. 버퍼가 차면 버리고, 버린 수를 지표로 남긴다. "Redis 가 죽어도 리다이렉트는 동작한다"와 같은 원칙이다.
- 바이럴 링크로 파티션이 쏠리면? 앱 서버에서 1초 단위로 먼저 합산해서 보내거나, 키에 접미사를 붙여 파티션을 분산한다.
- 중복 집계는? at-least-once 라 재시도 때 중복이 생긴다. 대시보드면 감수하고, 과금이면 이벤트 ID 로 멱등 처리한다.
- **기존 설계와의 충돌**: 302 에 `max-age=300` 이 붙어 있어 5분 안의 재클릭은 서버에 오지 않는다. 정확한 수가 필요하면 `no-store` 로 바꾸고 늘어난 요청은 L1 이 흡수한다. 아니면 "5분 안의 재클릭은 한 번"으로 정의를 바꾼다.

**30초 답변**
> 리다이렉트 경로에서는 클릭 이벤트를 비동기 버퍼에 넣기만 하고 바로 302 를 돌려주겠습니다. 클릭이 하루 10억 건이라 동기로 DB 를 갱신하면 바이럴 링크에서 행 락 경합이 생깁니다. 이벤트는 short_key 를 파티션 키로 Kafka 에 보내고, 스트림 처리에서 국가·시간별 1분 집계를 만들어 OLAP 저장소에 쌓습니다. 원시 이벤트는 하루 100 GB 라 30일만 보관합니다. 대시보드용이라 약간의 중복은 허용하고, 이벤트 전송이 실패해도 리다이렉트는 실패시키지 않습니다. 지금 302 에 max-age 5분이 붙어 있어 5분 안의 재클릭은 집계되지 않으므로, 정확한 수가 필요하면 no-store 로 바꾸겠습니다.

## 3. 고유 방문자

**질문**: "같은 사람이 하루에 100번 누르면 100이다. 링크 1억 개의 하루 고유 방문자를 세려면 메모리가 얼마나 들고, 어떻게 줄이나?"

**방문자 정의**: 로그인이 없으므로 IP + User-Agent 를 솔트로 해시한 값을 쓴다. 원본 IP 는 저장하지 않는다. NAT 뒤 여러 사람은 한 명으로, IP 가 바뀐 한 사람은 여러 명으로 세어지므로 근사치라고 먼저 밝힌다.

| | 정확한 집합 | **HyperLogLog (채택)** |
|---|---|---|
| 크기 | 하루 고유 쌍 약 5억 × 8 B ≈ 4 GB, 자료구조 오버헤드로 수십 GB | 카운터당 최대 약 12 KB. 방문자가 적으면 희소 표현으로 수백 B 이하 |
| 오차 | 0% | 약 0.81% (레지스터 2^14개). 2^12개면 약 3 KB, 약 1.6% |
| 기간 합산 | 일별 숫자는 더할 수 없어 집합을 기간만큼 보관해야 함 | **병합 가능**: 시간별 → 일별 → 주별을 중복 없이 합친다 |

- 링크 1억 개가 모두 12 KB 면 1.2 TB 지만, 클릭은 롱테일이라 대부분 희소 표현에 머문다. 하루 전체는 수 GB 수준이다.
- 정확한 값이 필요하면 30일 보관한 원시 이벤트로 `COUNT(DISTINCT)` 를 요청 시에만 계산한다.

**30초 답변**
> 로그인이 없으니 방문자는 IP 와 User-Agent 를 솔트 해시한 값으로 근사하겠습니다. 정확히 세면 하루 수십 GB 가 들고, 주간 고유 방문자를 구하려면 집합을 여러 날 보관해야 합니다. 그래서 HyperLogLog 를 쓰겠습니다. 카운터 하나가 최대 12 KB, 오차 약 0.8% 이고, 대부분의 링크는 희소 표현으로 수백 바이트 이하입니다. 가장 중요한 성질은 병합 가능성이라 시간별 HLL 을 합치면 일별·주별 고유 방문자가 중복 없이 나옵니다. 정확한 값이 필요하면 30일치 원시 이벤트로 다시 계산합니다.

## 4. 만료와 삭제

**질문**: "링크에 만료 시각을 지정하고, 만료 전에도 직접 삭제하고 싶다. '키 → URL 불변' 전제로 만든 캐시의 어디가 깨지고 어떻게 고치나?"

**깨지는 곳**: 캐시 계층마다 TTL 이 곧 "삭제된 링크가 계속 동작할 수 있는 최대 시간"이 된다.

| 계층 | 지금 TTL | 삭제 후 동작 가능 시간 |
|---|---|---|
| 브라우저 `max-age=300` | 5분 | 최대 5분, 서버가 지울 방법이 없음 |
| L1 | 5분 | 최대 5분 |
| L2 | 1일 | **최대 1일** |

| | 만료 (시각을 미리 앎) | 삭제 (사건) |
|---|---|---|
| 해결 | 캐시 값에 `expiresAt` 을 함께 넣고 읽을 때 비교. 캐시 TTL = min(기본 TTL, 남은 시간) | 무효화가 필요 |
| 무효화 | 필요 없음 | 필요 |

**삭제 처리**
1. 저장소는 소프트 삭제(`status`, `deleted_at`)다. **키는 절대 재사용하지 않는다.** 재사용하면 이미 공유된 옛 링크가 새 URL 로 간다. md5 체인도 지켜진다.
2. L2 는 삭제 API 가 "삭제됨" 표식으로 즉시 덮어쓴다. 부정 캐시와 같은 방식이다.
3. L1 은 TTL 을 30~60초로 줄이고 감수하거나, Redis Pub/Sub 로 무효화하고 TTL 을 안전망으로 둔다.
4. 브라우저는 `max-age` 를 같은 기준으로 줄인다.

**SLA 로 정한다**: "삭제가 몇 초 안에 반영되어야 하는가"에 맞춰 모든 계층의 TTL 을 그 이하로 둔다. 피싱·법적 요청 같은 긴급 삭제는 L1 브로드캐스트와 CDN purge 까지 한다.

**놓치기 쉬운 것**
- 중복 제거 인덱스가 삭제된 키를 돌려줄 수 있다. 상태를 확인하고, 삭제된 키면 새 키를 발급해 인덱스를 갱신한다.
- 응답은 만료·삭제면 `410 Gone`, 없는 키면 `404`. 존재 여부 노출이 싫으면 404 로 통일한다.
- 삭제하려면 소유자를 알아야 하므로, 생성 시 소유자 ID 나 관리 토큰을 저장한다.

**30초 답변**
> 만료와 삭제는 캐시의 불변 전제를 깨서, 캐시 계층의 TTL 만큼 지워진 링크가 동작하게 됩니다. 지금이면 L2 때문에 최대 하루입니다. 만료는 시각을 미리 아니 캐시 값에 만료 시각을 넣고 읽을 때 비교하면 무효화가 필요 없습니다. 삭제는 소프트 삭제로 하고 키는 재사용하지 않습니다. 삭제 시 L2 를 "삭제됨" 표식으로 덮어쓰고, L1 은 TTL 을 1분 이하로 줄이거나 Pub/Sub 로 무효화합니다. 브라우저 max-age 도 같은 기준으로 줄입니다. 결국 "삭제가 몇 초 안에 반영되어야 하는가"를 SLA 로 정하고 모든 계층의 TTL 을 그 이하로 맞추는 문제입니다.

## 5. 커스텀 별칭

**질문**: "`/spring-sale` 처럼 원하는 이름으로 링크를 만들고 싶다. 자동 발급 키와 충돌하지 않게 하려면?"

**정확성은 이미 지켜진다**: UNIQUE(KV 면 조건부 쓰기)가 최후 방어선이다. 별칭이 먼저 차지한 번호는 자동 발급이 건너뛴다(range 전략에 구현하고 테스트함). 자동 키가 먼저면 별칭 요청이 `409 Conflict` 를 받는다. 그래서 진짜 질문은 사용자 경험과 남용이다.

| 이름 공간 분리 | 장점 | 단점 |
|---|---|---|
| **길이·문자 집합 (권장)**: 자동 키는 정확히 7자 Base62, 별칭은 8~32자에 `-`·`_` 허용 | 깔끔하고 구조적으로 겹치지 않음 | 짧은 별칭은 예외 정책이 필요 |
| 경로 접두사 `/c/spring-sale` | 완전 분리, 단순 | URL 이 길어짐 |
| 같은 공간 공유 | 구현이 쉬움 | 별칭이 미래의 자동 키를 차지할 수 있음 |

**별칭에서만 생기는 문제**
1. **소문자로 정규화**: 키 컬럼은 `ascii_bin` 이라 `/Spring-Sale` 과 `/spring-sale` 이 다른 링크가 되어 피싱에 쓰일 수 있다. v2 collation 함정을 반대 방향에서 만난 것이다.
2. **예약어·금칙어**: `api`, `admin`, `login`, `health`, 브랜드 사칭(`google`), 욕설. 선점은 빈도 제한이나 유료 플랜으로 막는다.
3. **검증과 스키마를 함께 넓힌다**: 조회 키 정규식 `^[0-9a-zA-Z]{1,16}$` 와 `VARCHAR(16)` 을 모두 바꾼다. 한쪽만 바꾸면 404 나 저장 오류가 난다.
4. **동시 요청**: 조건부 쓰기 하나만 성공하고 나머지는 409. 자동 키와 달리 다른 이름으로 대신 만들지 않는다.
5. **삭제된 별칭의 재사용**: 유예 기간(예: 90일) 뒤에만 풀고, 그 전에는 원래 소유자만 쓰게 한다.
6. **중복 제거는 자동 키에만** 적용한다. 별칭은 사용자가 명시적으로 원한 것이다.

**30초 답변**
> 같은 키가 두 URL 을 가리키는 일은 이미 UNIQUE 와 조건부 쓰기가 막고, 별칭이 차지한 번호는 자동 발급이 건너뛰도록 range 전략에서 구현해 두었습니다. 그래도 이름 공간은 나누겠습니다. 자동 키는 정확히 7자 Base62, 별칭은 8자 이상에 하이픈을 허용하면 구조적으로 겹치지 않습니다. 별칭은 소문자로 정규화합니다. 키 컬럼이 대소문자를 구분해서 대소문자만 다른 피싱 링크가 생길 수 있기 때문입니다. 예약어와 사칭 이름은 막고, 조회 키 검증과 컬럼 길이를 함께 넓힙니다. 같은 별칭 동시 요청은 한 쪽만 성공하고 나머지는 409 입니다.
