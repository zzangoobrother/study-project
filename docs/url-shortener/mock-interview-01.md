# URL 단축 서비스 모의 면접 회고 (1회차)

- 일시: 2026-11-23
- 형식: 시스템 설계 면접, 약 45분. 면접관 역할은 Claude가 맡았다.
- 문제: "URL 단축 서비스를 설계해 주세요."
- 범위: 생성과 리다이렉트. 사용자 지정 별칭, 만료, 클릭 통계는 범위에서 뺐다.
- 참고 문서: [interview-guide.md](interview-guide.md)

## 1. 종합 평가

| 단계 | 평가 | 한 줄 요약 |
|---|---|---|
| 1. 요구사항과 추정 | 보통 | 숫자는 정확했지만 저장 용량을 추정하지 않았고, 남는 공간 질문에 답하지 않았다 |
| 2. 상위 설계와 읽기 경로 | 좋음 | 첫 답은 짧았다. 그래도 negative cache를 L2에만 두고 Feistel로 예측을 막는 답이 좋았다 |
| 3. 키 생성 심화 | 매우 좋음 | 해시 방식을 빠뜨렸지만, 범위 낭비와 리전 공간 계산은 정확했다 |

실제 면접이었다면 통과권이다. 후반부로 갈수록 숫자를 근거로 판단하는 답이 늘었다.

## 2. 질문과 답변 흐름

### 2.1 요구사항과 추정

| 질문 | 내 답 | 보완할 내용 |
|---|---|---|
| 기능 범위 | "생성과 리다이렉트만 하면 되나요?" | 예/아니오로 묻지 말고 범위를 직접 제안한다. 예: "핵심은 둘로 잡고 별칭, 만료, 통계는 범위 밖으로 두겠습니다" |
| 규모 | 사용자 10억 명, 하루 생성 1억 건을 확인 | 보관 기간과 읽기:쓰기 비율도 같이 묻거나 직접 가정한다 |
| QPS | 쓰기 평균 1,000, 피크 2,000. 읽기 피크 2만 (비율 10:1) | 숫자가 설계에 주는 의미를 덧붙인다. 예: "읽기 2만은 DB 한 대로 어려우니 캐시가 필요합니다" |
| 키 길이 | 10년 동안 3,650억 개. 62^6 ≈ 568억은 부족하니 7글자 | 62^7 ≈ 3.5조가 필요량의 약 10배라는 비교까지 말한다 |
| 저장 용량 | **추정하지 않음** | 3,650억 × 500B ≈ 180TB이므로 DB 한 대로는 안 되고 분산 저장이 필요하다 |
| 남는 공간이 괜찮은가 | **답하지 않음** | 10년 뒤에도 공간 사용률이 약 10%다. 무작위 키라면 시도당 충돌 확률이 약 0.1이고 5회 연속 실패 확률은 약 10⁻⁵다. 남는 공간은 낭비가 아니라 여유다 |
| 대소문자 구분 | collation이 대소문자를 무시하면 `aB`와 `Ab`가 충돌한다. 생성하면 UNIQUE 위반으로 500이 나고, 조회하면 다른 URL로 리다이렉트된다 | 처음부터 증상 → 원인 → 해결 순서로 말한다. `ascii_bin`으로 고쳤더니 비 ASCII 키 문제가 새로 생겨 형식 검증으로 404 처리한 것까지 이어 말한다 |

### 2.2 상위 설계와 읽기 경로

| 질문 | 내 답 | 보완할 내용 |
|---|---|---|
| API | `POST /api/v1/urls`, `GET /{key}` | 요청과 응답의 모양, 실패 코드(400, 503)를 함께 말한다 |
| 301과 302 | 301은 캐시로 부하가 줄지만 통계와 변경이 어려우니 302 | 302에 짧은 `Cache-Control: max-age`를 붙이는 중간 지점까지 제시한다 |
| 읽기 경로 | L1 로컬 캐시 → L2 Redis → DB, 없으면 404 | 로드밸런서, 캐시에 없을 때 채우는 방법, 키가 없을 때 처리까지 한 번에 설명한다 |
| 캐시 우회와 채우기 | 없는 키는 negative cache로 막고, 생성할 때 write-through로 채운다 | 키워드만 말하지 말고 동작을 설명한다. 예: "없는 키도 짧은 TTL로 '없음'을 캐시해서 DB까지 내려가지 않게 막습니다" |
| negative cache에 남은 값 | 다른 서버의 L1에 "없음"이 남아 TTL 동안 404가 난다. 생성할 때 무효화 메시지를 브로드캐스트한다 | 원인 분석이 정확했다 |
| 브로드캐스트 없이 해결 | **negative cache는 L2에만 두고, Feistel로 다음 키를 예측하지 못하게 한다** | 이번 면접에서 가장 좋은 답이다. 비용이 큰 해결책 대신 구조로 문제를 피했다 |

### 2.3 키 생성 심화

| 질문 | 내 답 | 보완할 내용 |
|---|---|---|
| 키 생성 방식 | auto increment, random, 분산 카운터 | **해시(MD5) 방식을 빠뜨렸다.** 나열에서 멈추지 말고 비교하고 선택해야 한다 (3절 모범 답안 참고) |
| 서버가 범위를 쓰다가 죽으면 | 남은 범위는 버리고, 재시작하면 새 범위를 받는다 | 근거를 같이 말한다 |
| 버리는 근거 | **같은 키를 두 번 발급하는 쪽이 더 나쁜 장애다. 낭비는 약 255억 개로 공간의 1% 미만이다** | 오늘 가장 완성도 높은 답이다. 판단 기준과 정량 근거가 한 문장에 다 있다 |
| 할당 서버가 죽거나 멀티 리전이면 | 다음 범위를 미리 받아 두고, 리전 비트로 범위를 나눈다 | 언제 받는지를 말한다. 예: "현재 범위를 80% 쓰면 다음 범위를 비동기로 받습니다" |
| 리전 공간 | 리전 4개면 2비트, 리전당 약 8,750억 개. 60%가 한 리전에 몰려도 2,190억 개라 충분하다 | 정확했다. 리전 비트는 64비트가 아니라 62^7(약 41.7비트) 공간의 상위 비트에서 뗀다 |
| `url_index` 쓰기 순서 | `short_url`을 먼저 쓴다. 고아 행은 해가 없다 | 동시 요청과 멀티 리전 상황까지 말하면 만점이다 (3절 참고) |

## 3. 모범 답안 정리

### 3.1 키 생성 방식 비교

| 방식 | 여러 서버 | 충돌 | 중복 제거 | 키 예측 |
|---|---|---|---|---|
| auto increment | 안 됨. DB 한 대가 병목이자 단일 장애점이고, 샤딩하면 번호가 겹친다 | 없음 | 없음 | 쉬움 |
| random | 됨. 조정이 필요 없다 | 있음. 존재 확인 뒤 재시도하고, 10년 뒤 충돌 확률은 시도당 약 0.1 | 없음 | 어려움 |
| 해시(MD5) | 됨. 조정이 필요 없다 | 있음. 7글자로 자르니 충돌하고, salt 체인으로 푼다 | 자동 | 어려움 |
| 분산 카운터 (범위 할당) | 됨. 서버가 받은 범위 안에서 메모리로 발급한다 | 없음 | 없음. 별도 인덱스가 필요하다 | 쉬움. Feistel로 섞는다 |

**30초 답변 예시**

> 범위 할당 카운터를 고르겠습니다. 3,650억 건 규모에서 random과 해시는 충돌하면 존재를 확인하고 다시 써야 하므로 생성 한 건이 여러 번 왕복할 수 있습니다. 범위 할당은 각 서버가 1만 개 단위로 범위를 받아 메모리에서 발급하니 충돌이 원천적으로 없고 쓰기 한 번이면 끝납니다. 초당 2,000건이어도 할당 서버로 가는 요청은 초당 0.2번입니다.
> 단점은 키를 예측할 수 있고 중복 제거가 안 된다는 것입니다. 예측은 Feistel 순열로 막고, 중복 제거는 URL 해시 → 키 인덱스를 따로 두어 해결합니다. 해시 방식은 중복 제거가 자동이지만 충돌 체인 비용과 설정을 바꿀 수 없다는 제약 때문에 고르지 않았습니다.

### 3.2 `url_index` 쓰기 순서

- `url_index`를 먼저 쓰고 서버가 죽으면, 인덱스는 존재하지 않는 키를 가리킨다. 같은 URL로 다시 요청한 사용자는 그 키를 받고, 접속하면 404가 난다. 사용자에게 보이는 장애다.
- `short_url`을 먼저 쓰고 서버가 죽으면, 아무도 가리키지 않는 고아 행만 남는다. 해가 없다.
- 같은 URL로 동시에 두 요청이 오면, `url_index`를 조건부 쓰기(없을 때만)로 넣는다. 진 쪽은 이긴 쪽의 키를 돌려주고, 진 쪽이 쓴 `short_url`은 고아 행이 된다.
- 멀티 리전에서는 리전 간 복제가 마지막 쓰기 우선(LWW)이라 중복 제거를 완벽하게 보장할 수 없다. 최선을 다하는 수준이라고 미리 밝힌다.

## 4. 개선점

1. **첫 답을 두세 문장으로 한다.** 꼬리 질문의 절반 이상이 "근거는요?"였다. 결론 → 근거(숫자나 대안과의 비교) → 대가나 한계 순서로 말한다.
   - 예: "302를 쓰겠습니다. 301은 브라우저 캐시로 부하가 줄지만, 통계와 대상 변경이 어려워집니다. 부하는 서버 쪽 캐시로 감당하겠습니다."
2. **질문이 두 개면 둘 다 답한다.** 이번에 세 번 절반만 답했다. 남는 공간, 요청 흐름, 선택 이유다. 답하기 전에 "두 가지 여쭤보셨는데, 먼저 ~"처럼 순서를 말한다.
3. **직접 겪은 것을 무기로 쓴다.** 해시 방식은 v3에서 직접 만들었는데도 빠뜨렸다. 면접 전에 아래 경험 목록을 다시 읽는다.
   - collation 버그: 대소문자 충돌로 500이 났고, `ascii_bin`으로 고친 뒤 비 ASCII 키 문제가 새로 생겼다
   - REQUIRES_NEW와 self-invocation 프록시 함정
   - MD5 salt 체인과, 배포 후 설정을 바꾸면 안 되는 이유
   - REPEATABLE READ 스냅샷 때문에 재조회가 오래된 값을 읽은 문제

## 5. 배운 것

- 면접관의 꼬리 질문은 대부분 **"그 선택의 대가는?"**의 변형이다. 302는 부하, 범위를 버리면 공간 낭비, 두 곳에 쓰면 순서 문제가 대가다. 대가를 먼저 말하면 면접관보다 한 발 앞선다.
- 같은 결론이라도 **정량화**가 답의 신뢰도를 가른다. "충분합니다"보다 "0.7%입니다"가 강하다.
- 해결책을 내면 그 해결책의 비용을 묻는다. 무효화 브로드캐스트보다 구조로 문제를 피하는 해결책이 더 좋은 평가를 받는다.
