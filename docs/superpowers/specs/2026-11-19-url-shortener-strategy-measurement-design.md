# URL 단축 서비스: 세 키 전략 실측 비교 설계

> **상태 (2026-11-20): 실측은 하지 않기로 했다.**
> - url-shortener 는 시스템 설계 면접 대비용이라, 측정 인프라(계측 코드, k6 도구, 약 1시간의 부하와 장비 발열)에 비해 얻는 것이 적다고 판단했다. 계측 코드와 측정 스크립트는 저장소에 남기지 않는다.
> - 이 문서는 **구조 분석과 가설(H1~H4), 이론값 공식, 무엇을 재면 검증되는지**를 정리한 분석 문서로 남긴다.
> - 중단 전 S1a(포화 탐색) 일부에서 얻은 사실이 하나 있다. 같은 Mac 에서 k6·앱·MySQL 을 함께 돌렸을 때 세 전략 모두 **초당 2,000건까지 포화되지 않았다**(실패율 1%, p95 500ms 기준). 사용자 100명 규모에서는 키 전략이 처리량 병목이 아니라는 근거다. 부하 생성기와 앱이 같은 장비에 있었으므로 이 값은 "적어도 이만큼"이라는 하한으로만 읽는다.
> - 아래 "계측", "측정 환경과 절차", "시나리오" 절은 실제로 측정할 때의 설계로 남겨 둔다.

## 의도
- counter / random / md5 세 전략의 **특성을 숫자로 남긴다.** 결과로 하나를 고르거나 나머지를 지우지 않는다. 세 전략과 전환 스위치는 그대로 둔다.
- 지금까지 비교는 구조 분석에 머물렀다("counter 는 INSERT+UPDATE", "random 은 키 공간이 찰수록 재시도" 등). 이번에는 이 서술을 측정값으로 바꾼다.
- 선례: Loopers 락 전략 측정. k6 부하를 걸고, 같은 jar 를 설정만 바꿔 띄우고, 가설 → 측정 → 결과 순서로 기록한다.
- 관련 설계: v1 `2026-11-14-…-v1-design.md`, v2 `2026-11-16-…-v2-design.md`, v3 `2026-11-18-…-v3-design.md`

## 목표 / 비목표
- 목표
  - 시나리오 S1~S4 를 전략별로 3회씩 측정하고, 결과와 해석을 이 문서의 "결과" 절에 남긴다.
  - 겉지표(k6: 처리량, 응답 시간, 상태 코드)와 내부 지표(시도 횟수, 충돌 종류, 소진, 중복 제거, 요청당 SQL 수)를 함께 남긴다.
  - 측정 도구(카운터, 스크립트)는 남겨 두어 다시 측정할 수 있게 한다.
- 비목표: 성능 튜닝, 캐시 도입, 다른 장비 간 비교, 전략 채택이나 삭제, 운영 수준의 벤치마크 엄밀성(전용 장비, 통계적 유의성 검정).
- 반대 목표
  - 계측이 동작을 바꾸면 안 된다. 기존 테스트는 계측을 추가하기 전과 같이 모두 통과해야 한다.
  - 숫자만 남기고 조건(키 길이, 점유율, 요청률, 환경)을 남기지 않는 결과는 재현할 수 없으므로 실패로 본다.

## 접근 방식 검토
- **A. k6 HTTP 부하 + 서버 내부 지표 (채택)**: 실제 HTTP, 커넥션 풀, MySQL 을 거치므로 재시도와 충돌이 실제 경합 속에서 드러난다. 대가로 프로덕션 코드에 카운터가 들어간다.
- B. Testcontainers 측정 하네스: 프로덕션 코드를 건드리지 않고 재현성이 높다. 하지만 HTTP 와 커넥션 경합이 빠져 실제 응답 시간과 다르다.
- C. JMH: 순수 연산만 잴 수 있다. 차이의 대부분이 DB 왕복에서 나오므로 제외한다.

## 가설 (측정 전에 기록)
- **H1 (S1)**: 키 7자리, 충돌이 없는 기준선에서는 세 전략 모두 **요청당 SQL 이 2회**이고 응답 시간 차이는 작다(p50 기준 ±20% 이내).
  - counter: INSERT + UPDATE
  - random: exists + INSERT
  - md5: select + INSERT
  - 근거: 구조상 왕복 횟수가 같다.
- **H2 (S2)**: 키 공간 점유율이 p 일 때 random 과 md5 의 평균 시도 횟수는 이론값 `(1 - p^5) / (1 - p)` 를 따르고, 소진(503) 비율은 `p^5` 를 따른다.
  - 측정 구간 동안 점유율이 변하는 만큼은 오차로 허용한다.
  - counter 는 키 길이가 id 에 따라 늘어나므로 해당하지 않는다(그 사실 자체를 결과로 적는다).
- **H3 (S3)**: 같은 URL 재요청 비율이 r 이면, md5 는 새 행이 약 `(1 - r)` 배로 줄고 중복 요청은 SQL 1회(select)로 끝난다. counter 와 random 은 r 과 관계없이 요청마다 행이 생긴다.
- **H4 (S4)**: GET 은 세 전략 모두 같은 조회 경로(형식 검증 + `findByShortKey`)이므로 차이가 없다.

## 계측 (프로덕션 코드 변경)
- 의존성: `spring-boot-starter-actuator`, `org.hibernate.orm:hibernate-micrometer`(버전은 Boot BOM 을 따른다).
- Micrometer 지표. 태그 `strategy` = counter|random|md5.
  - `shortener.create.attempts` (DistributionSummary): 요청 1건에 시도한 키 개수. counter 는 항상 1.
  - `shortener.create.collisions` (Counter, 태그 `type` = precheck|unique): random 과 md5 의 충돌. md5 의 precheck 는 "다른 URL 이 차지한 키"를, unique 는 "UNIQUE 위반 후 다른 URL"을 센다.
  - `shortener.create.recovered` (Counter): md5 가 UNIQUE 위반 후 재조회로 같은 URL 을 찾아 회복한 횟수.
  - `shortener.create.dedup` (Counter): md5 가 이미 있는 같은 URL 의 키를 돌려준 횟수.
  - `shortener.create.exhausted` (Counter): 소진되어 503 이 난 횟수.
- SQL 수: Hibernate statistics (`hibernate.generate_statistics=true`) + hibernate-micrometer 가 노출하는 `hibernate.statements`(prepared statement 수).
- **`loadtest` 프로파일에서만 켠다**: statistics 활성화와 actuator `metrics` 엔드포인트 노출. 기본 프로파일의 동작과 노출 범위는 그대로 둔다. 카운터 자체는 항상 기록한다(오버헤드가 무시할 수준).
- 카운터는 각 Creator 안에서 기록한다(`MeterRegistry` 주입). 이미 있는 `log.warn`/`log.debug` 와 같은 지점이다.

## 측정 환경과 절차
- 같은 jar: `./gradlew :url-shortener:bootJar` 로 한 번만 빌드하고, `java -jar … --spring.profiles.active=loadtest --shortener.key-strategy=<s> [--shortener.random.key-length=… --shortener.md5.key-length=…]` 로 실행한다.
- DB: `url-shortener/docker-compose.yml`(MySQL 8.4, 3307). **실행마다 테이블을 비우고** 시나리오에 필요한 시드를 넣는다. Hikari 등 나머지 설정은 기본값이다.
- 1회 실행 순서:
  1. 테이블 초기화(`TRUNCATE`)와 시드
  2. (앱이 떠 있지 않거나 전략/키 길이가 바뀌었으면) 앱 기동, health 대기, 워밍업 10초(결과에서 제외)
  3. 지표 스냅샷(before)
  4. k6 측정 구간
  5. 지표 스냅샷(after)
  - 내부 지표는 after − before 차이로 계산한다. 그래서 앱을 띄워 둔 채 회차를 이어 가도 된다.
  - 앱 재기동은 전략이나 키 길이가 바뀔 때만 한다. 매번 재기동하면 회차마다 차가운 JVM 에서 시작해 초반 숫자가 흔들리고, 시간도 더 든다 *(2026-11-19 사용자와 합의: 총 측정 시간 약 2시간 → 약 1시간)*.
- 반복: 조건마다 3회 측정하고 중앙값을 보고한다. 3회의 범위(최소~최대)도 함께 적는다. 단 S1a 는 S1b 의 요청률을 정하는 용도이므로 전략마다 1회만 한다.
- 측정 구간 길이: S1b·S3·S4 는 30초, S2 는 20초다. 초당 수백 건이면 수천 건이 쌓여 p95/p99 를 내기에 충분하다.
- 환경 기록: 장비(CPU, 메모리), OS, JDK, MySQL 버전, Docker 자원 할당, Hikari 풀 크기, 측정 시각. 결과 절 맨 위에 적는다.
- 산출물: `url-shortener/loadtest/` 아래에 스크립트, 시드 SQL, `results/<날짜>-<시나리오>-<전략>-<회차>.json`(k6 요약 + 지표 차이).

## 시나리오
### S1 기준선: 처리량과 응답 시간
- 조건: 키 7자리(random, md5 기본값). 요청마다 고유 URL 이다. 빈 테이블에서 시작한다.
- S1a 포화 탐색: 요청률을 단계적으로 올려(ramping-arrival-rate) 전략별로 실패율 1% 또는 p95 500ms 를 넘기 직전의 처리량을 기록한다.
- S1b 고정 부하: 세 전략이 모두 감당하는 요청률(S1a 결과의 최소값의 약 60%)로 30초 측정한다. p50, p95, p99, 요청당 SQL 수를 기록한다.

### S2 키 공간 점유율
- 조건: random 과 md5 의 키를 **3자리**(62³ = 238,328)로 한다. 측정 전에 점유율 p ∈ {0%, 50%, 80%, 90%, 95%} 가 되도록 **시드로 미리 채운다.**
  - 시드 키는 서로 다르고 균등하게 무작위인 3자리 Base62 이다. 시드 URL 은 측정 URL 과 겹치지 않는다.
  - md5 에게 시드 행은 "다른 URL 이 차지한 키"이므로 random 과 같은 조건이 된다.
- 측정: 고정 요청률(S1b 와 같은 값)로 20초 동안 고유 URL 을 POST 한다. 워밍업이 점유율을 바꾸지 않도록 S2 의 워밍업은 시드 전에 한다.
- 기록: 평균 시도 횟수, 충돌(precheck/unique), 소진(503) 비율, p95. 그리고 **이론값 `(1 - p^5)/(1 - p)`, `p^5` 와 나란히 놓은 표.** 측정 중 늘어난 행 수와 그로 인한 점유율 변화도 적는다.
- counter: 해당 없음(키 길이가 id 에 따라 늘어나 점유율 개념이 없음)으로 표에 적는다.

### S3 같은 URL 재요청 비율
- 조건: 키 7자리. 재요청 비율 r ∈ {0%, 50%, 90%}. 매 요청은 확률 r 로 "이미 보낸 URL 풀"에서 하나를 고르고, 그 밖에는 새 URL 을 만든다.
- 측정: 고정 요청률로 30초.
- 기록: 새로 생긴 행 수(DB count 의 차이), `dedup` 횟수, 요청당 SQL 수, p50/p95.

### S4 GET 리다이렉트
- 조건: 전략별로 1만 건을 먼저 만들어 두고, 그 키들로 고정 요청률 30초 동안 GET 을 보낸다. 리다이렉트는 따라가지 않는다.
- 기록: p50/p95, 요청당 SQL 수. 세 전략이 같은지 확인하는 기준점이다.

## 결과 기록 형식
- 이 문서 끝에 "결과" 절을 추가한다.
  - 환경
  - 시나리오별 표(중앙값과 범위)
  - 가설별 판정(채택/기각/부분)과 근거
  - 예상 밖의 관찰
- 숫자만 쓰지 않고, 각 표 아래에 "이 숫자가 말하는 전략의 특성"을 한두 줄 덧붙인다.
- 그래프: 요약 스크립트가 원시 JSON 에서 Mermaid `xychart-beta` 그래프를 자동으로 만들어 표 아래에 둔다 *(2026-11-19 사용자 요청)*. 대상은 S2 시도 횟수·503 비율 곡선(이론값 포함), S3 행 증가, S1·S4 응답 시간, S1a 포화 처리량이다. 표가 원본이고 그래프는 보조다.

## 빌더 재량
- k6 스크립트 구조(시나리오별 파일 또는 환경변수 분기), 시드 생성 방법(SQL 또는 스크립트), 실행 자동화 스크립트의 형태
- S1a 의 단계 폭과 S1b 의 정확한 요청률, S3 의 URL 풀 크기
- 지표 스냅샷 수집 방식(actuator JSON 을 curl 로 받아 jq 로 처리하는 등)
