# URL 단축 서비스 범위 할당 카운터 설계 (range)

## 의도
- 면접 정리 문서(`docs/url-shortener/interview-guide.md`)의 10억 규모 설계에서 키 생성 방식으로 **범위 할당 카운터 + Feistel + Base62**를 확정했다. 이 결정을 기존 모듈에 네 번째 키 전략 `range` 로 구현한다.
- 목적은 동작 확인이 아니라 **설계에서 말로 주장한 내용을 테스트로 증명**해 면접에서 경험담으로 쓰는 것이다. 증명할 주장은 세 가지다.
  1. **중복 발급이 없다**: 여러 서버(발급기)가 동시에 범위를 받아도 범위가 겹치지 않고, 같은 번호를 두 번 발급하지 않는다.
  2. **서버가 재시작하면 남은 범위는 버린다**: 이어 쓰지 않는다. 버린 번호는 다시 발급되지 않는다.
  3. **키는 예측할 수 없고 항상 7글자다**: Feistel 순열로 순서를 섞고, cycle walking 으로 62^7 범위를 넘지 않는다.
- 이전 설계: v1 `2026-11-14-url-shortener-v1-design.md`, v2 `2026-11-16-…`, v3 `2026-11-18-…`
- 로드맵의 "v4(샤딩된 여러 DB)"와는 다른 작업이다. 이번 작업은 DB 한 대에서 동작하는 범위 할당이고, 샤딩은 여전히 보류다.

## 목표 / 비목표 / 반대 목표
- 목표
  - `shortener.key-strategy=range` 로 고를 수 있는 `RangeShortUrlCreator` 를 추가한다. 기본 전략은 random 그대로 둔다.
  - 위의 세 가지 주장을 각각 테스트로 증명한다.
- 비목표
  - 다음 범위 미리 받기(prefetch). 다음 단계(B안)로 따로 한다.
  - 리전 비트 파티션, `url_index` 중복 제거, KV 저장소, 실제 다중 인스턴스 배포, 성능 측정.
  - 다른 전략이 만든 행과의 중복 제거.
- 반대 목표 (동작하더라도 실패로 본다)
  - 범위 할당이 URL 생성 트랜잭션에 묶여 함께 롤백되는 구현. 롤백되면 다른 서버가 같은 범위를 다시 받아 중복 발급이 생긴다.
  - 7글자를 넘는 키가 나오는 구현. 62^7 은 2의 거듭제곱이 아니어서 비트 단위 Feistel 만 쓰면 생긴다.
  - 남은 범위를 이어 쓰려고 발급 위치를 매번 저장하는 구현. 목적과 정반대다.

## 접근 방식 검토
- 할당 저장소
  - **MySQL 의 `key_range` 테이블 (채택)**: 이미 쓰고 있고 트랜잭션으로 원자성이 보장된다. 할당은 1만 건에 한 번이라 빈도가 문제 되지 않는다.
  - Redis `INCRBY`: 장애 후 AOF 유실로 카운터가 뒤로 돌아가면 같은 범위를 다시 나눠 준다. 할당 저장소의 핵심 성질("값이 절대 뒤로 가지 않는다")을 깨므로 제외한다.
  - etcd, ZooKeeper: 실무의 정석이지만 학습 목적에 비해 인프라가 무겁다.
- 원자적 증가 방식
  - **① 비관적 락 (채택)**: `SELECT … FOR UPDATE` 로 읽고 `UPDATE` 한다. 별도 빈에서 `@Transactional(propagation = REQUIRES_NEW)` 로 실행한다. 재시도 루프가 없어 읽기 쉽고, 기존 `ShortUrlInserter` 패턴과 같다. 할당 빈도가 낮아 락 경합도 거의 없다.
  - ② 조건부 UPDATE(CAS): `WHERE next_start = 읽은값` 으로 바꾸고 0행이면 재시도한다. KV 저장소의 조건부 쓰기와 같은 모양이라 면접에서는 "KV 로 옮기면 이 방식으로 바꾼다"고 말로 연결한다.
- 범위 (사용자 결정: A안)
  - **A (채택)**: 범위 할당, 동시 할당, 재시작 시 버림, Feistel + cycle walking.
  - B: A + prefetch. 다음 단계로 미룬다.
  - C: B + 리전 파티션. 숫자로 설명하는 것으로 충분하므로 하지 않는다.

## 구성 요소

### 1. `key_range` 테이블
```sql
CREATE TABLE IF NOT EXISTS key_range (
    name       VARCHAR(32) NOT NULL PRIMARY KEY,
    next_start BIGINT      NOT NULL
);
INSERT IGNORE INTO key_range (name, next_start) VALUES ('short_url', 0);
```
- `schema.sql` 은 기동할 때마다 실행되므로(`sql.init.mode: always`) `INSERT IGNORE` 로 최초 1회만 시드한다.
- `next_start` 는 다음에 나눠 줄 범위의 시작 번호다. 오직 증가만 한다.

### 2. `KeyRangeAllocator` (별도 빈)
- `allocate()` 는 `[start, end)` 범위 하나를 돌려준다.
  - `@Transactional(propagation = REQUIRES_NEW)` 이다. 호출자에 트랜잭션이 있어도 할당은 즉시 독립적으로 커밋된다.
  - `key_range` 행을 비관적 락(PESSIMISTIC_WRITE)으로 읽는다.
  - `start = next_start`, `end = min(start + blockSize, 62^7)` 로 정하고 `next_start = end` 로 갱신한다.
  - `start ≥ 62^7` 이면 번호 공간을 모두 쓴 것이므로 `ShortKeyGenerationException`(503)을 던진다.
- 별도 빈이어야 하는 이유는 `ShortUrlInserter` 와 같다. 자기 호출이면 프록시를 거치지 않아 REQUIRES_NEW 가 조용히 무시된다. 클래스 주석에 남긴다.
- `blockSize` 는 `shortener.range.block-size` 이고 기본값은 10000 이다. 1 이상인지 기동할 때 검증한다. 배포 후 바꿔도 앞으로 받을 범위의 크기만 달라지므로 안전하다.

### 3. `RangeNumberIssuer` (번호 발급기)
- 현재 범위 `[cursor, end)` 를 메모리에 들고, `next()` 를 호출할 때마다 번호 하나를 돌려준다.
  - 범위를 다 쓰면 `KeyRangeAllocator.allocate()` 로 새 범위를 받는다. 처음 호출할 때도 새 범위를 받는다.
  - `next()` 는 `synchronized` 다. 범위를 받는 동안 다른 스레드가 기다리는 것은 1만 건에 한 번이라 감수한다.
- **재시작 시 버림은 별도 코드 없이 성립한다.** 범위는 메모리에만 있으므로 프로세스가 죽으면 남은 번호가 사라지고, 새 발급기는 새 범위를 받는다. 이 점을 클래스 주석에 남긴다.
- 테스트에서 "서버 여러 대"와 "재시작"을 흉내 낼 수 있게, 발급기는 Spring 밖에서도 `new RangeNumberIssuer(allocator)` 로 여러 개 만들 수 있어야 한다. 애플리케이션에서는 빈 하나만 쓴다.

### 4. `FeistelPermutation` (번호 섞기)
- 번호 공간 `[0, N)`, `N = 62^7 = 3,521,614,606,208` 위의 일대일 대응(전단사)이다. 같은 입력은 늘 같은 출력이고, 서로 다른 입력은 서로 다른 출력이다.
- 구조
  - N 을 덮는 가장 작은 짝수 비트 수는 42비트다(2^42 ≈ 4.4조). 21비트씩 둘로 나누는 균형 Feistel 을 4라운드 돌린다.
  - 라운드 함수는 `(오른쪽 절반, 라운드 키)` 를 섞어 하위 21비트를 내는 비암호 해시면 충분하다. 목적이 보안이 아니라 순서를 예측하지 못하게 하는 것이기 때문이다.
  - **cycle walking**: 결과가 N 이상이면 그 결과에 다시 순열을 적용하고, N 미만이 될 때까지 반복한다. 2^42 위의 순열이므로 반드시 끝나고, 평균 반복 횟수는 2^42 / N ≈ 1.25 회다.
- 역변환 `inverse()` 를 함께 제공한다. 운영 코드에서는 쓰지 않지만 테스트로 전단사를 증명하는 데 쓴다.
- 테스트에서 작은 공간을 전수 검사할 수 있도록, 공간 크기 N 과 비트 수를 생성자로 받는다. 예를 들어 N = 62^2 = 3,844, 12비트로 만들면 모든 입력을 다 돌려 볼 수 있다.
- 라운드 키는 `shortener.range.feistel-secret`(long)에서 만든다.
  - **배포 후 바꾸면 안 된다.** 순열이 바뀌면 새로 발급하는 키가 이미 발급된 키와 겹친다. md5 설정처럼 `application.yml` 에 경고 주석을 단다.

### 5. `RangeShortUrlCreator` (전략)
- `@ConditionalOnProperty(name = "shortener.key-strategy", havingValue = "range")`
- `create(url)`
  1. `n = issuer.next()`
  2. `key = Base62(feistel.permute(n))` 를 왼쪽 `'0'` 채움으로 7자리에 맞춘다.
  3. `ShortUrlInserter.insert(ShortUrl.create(url, key))` 로 저장하고 키를 돌려준다.
  4. UNIQUE 위반(`DataIntegrityViolationException`)이면 다음 번호로 넘어가 1부터 다시 한다. 최대 `shortener.range.max-attempts`(기본 5, 1 이상, 기동 시 검증)번 시도하고, 모두 실패하면 `ShortKeyGenerationException`(503)을 던진다.
- 범위 할당 카운터끼리는 충돌하지 않는다. UNIQUE 위반은 **같은 DB 에 다른 전략(random, md5 등)이 만든 키가 남아 있을 때만** 생긴다. 이 점을 주석과 설계에 남긴다. 실패한 번호는 버린다.
- `create` 에 `@Transactional` 을 붙이지 않는 이유는 `RandomShortUrlCreator` 와 같다.

### 6. 설정 (`application.yml`)
```yaml
shortener:
  range:
    block-size: 10000
    max-attempts: 5
    # feistel-secret 은 배포 후 바꾸지 않는다. 순열이 바뀌면 새 키가 이미 발급된 키와 겹친다.
    feistel-secret: <임의의 long 값>
```

## 테스트 (증명할 주장별)
공유 싱글톤 MySQL 컨테이너를 쓰므로 `key_range.next_start` 는 테스트끼리 누적된다. 그래서 범위의 정확한 값을 단정하지 말고, 테스트 시작 시점의 값을 읽어 상대적으로 단정한다. 짧은 키를 넣는 테스트는 자기가 넣은 행을 정리한다(v3 규칙).

1. **중복 발급 없음**
   - 여러 스레드가 동시에 `allocate()` 를 호출하면, 받은 범위들이 서로 겹치지 않고 빈틈 없이 이어진다.
   - 발급기 여러 개(서버 여러 대 흉내)가 동시에 각각 많은 번호를 발급해도, 전체 번호에 중복이 없다. 블록 크기를 작게(예: 10) 잡아 할당이 여러 번 일어나게 한다.
   - 할당은 독립 커밋된다: 바깥 트랜잭션 안에서 `allocate()` 를 호출하고 바깥을 롤백해도 `next_start` 는 증가한 채로 남는다. (반대 목표 검증)
2. **재시작 시 버림**
   - 발급기 A 가 범위를 받아 일부만 쓴 뒤 버려지고(재시작 흉내), 새 발급기 B 가 만들어진다. B 의 첫 번호는 A 가 받은 범위의 끝 이상이고, A 범위의 남은 번호는 이후 어떤 발급기도 발급하지 않는다.
3. **예측 불가와 7글자**
   - 작은 공간(N = 62^2)을 전수 검사해 `permute` 가 전단사이고 결과가 모두 N 미만임을 확인한다.
   - 실제 공간(N = 62^7)에서는 표본(경계값 0, N−1 포함)에 대해 `inverse(permute(x)) == x` 이고 결과가 N 미만임을 확인한다. 연속된 입력 수십만 개의 결과에 중복이 없음도 확인한다.
   - 연속된 번호에서 나온 키들이 연속되지 않는다. 예: 연속 입력 1,000개의 결과를 정렬했을 때 인접한 차이가 1인 경우가 대부분이 아니다.
   - 발급된 키는 모두 정확히 7글자이고 `^[0-9a-zA-Z]{7}$` 에 맞는다.
4. **전략 동작**
   - `key-strategy=range` 일 때 POST 로 201 과 7글자 키를 받고, GET 으로 302 리다이렉트된다.
   - 다른 전략이 만든 키가 다음 발급 키와 같은 상황을 만들면, 그 번호를 건너뛰고 다음 키로 저장된다.
     - 다음 번호는 미리 알 수 없으므로, 먼저 키 하나를 만들고 `inverse` 로 번호 n 을 구한 뒤 n+1 의 키를 미리 넣어 두고 다시 생성한다. n+1 이 현재 범위 끝을 넘지 않도록 블록 크기를 충분히 크게 둔 별도 테스트 클래스에서 한다. (구현자 판단으로 추가)
   - 번호 공간 소진: `next_start` 를 62^7 로 맞춘 뒤 생성하면 503 이다. 테스트가 끝나면 `next_start` 를 원래 값으로 되돌린다.
     - 싱글톤 발급기가 이미 범위를 메모리에 들고 있으면 503 이 나지 않는다. 이 테스트만 쓰는 최상위 테스트 클래스에 `block-size=1` 을 주어, 생성할 때마다 할당이 일어나게 한다. (구현자 판단으로 추가)
   - 설정 검증: `block-size`, `max-attempts` 가 1 미만이면 기동에 실패한다.

## 면접 경험담으로 연결
| 면접 질문 | 테스트로 남는 증거 |
|---|---|
| 서버가 범위를 쓰다 죽으면? | 재시작 테스트: 남은 번호는 버리고 다시 발급되지 않는다 |
| 동시에 범위를 받으면 겹치지 않나? | 동시 할당 테스트 + 비관적 락 |
| 할당이 롤백되면? | REQUIRES_NEW 독립 커밋 테스트 |
| 순차 키는 예측되지 않나? | Feistel 전단사 전수 검사 + 연속성 테스트 |
| 62^7 은 2의 거듭제곱이 아닌데 Feistel 이 되나? | cycle walking 과 7글자 보장 테스트 |
| 할당 저장소로 Redis 는? | 값이 뒤로 가면 중복 발급이 생기므로 제외 (설계 근거) |

## 범위 밖으로 둔 것
- 면접 정리 문서(`interview-guide.md`)는 이번 작업에서 고치지 않는다. 그 문서에는 이 전략이 아직 "분산 카운터 (v4, 보류)"로 적혀 있고, 범위 크기 예시도 이 설계의 10000과 다르다. 구현이 끝난 뒤 테스트 결과를 경험담으로 반영하는 별도 작업으로 한다.

## 구현자에게 맡기는 것
- 라운드 함수의 구체적인 식(비암호 해시면 된다), 라운드 키를 secret 에서 만드는 방법.
- `KeyRange` 를 JPA 엔티티와 `@Lock` 으로 다룰지, 네이티브 쿼리로 다룰지. 단, 비관적 락과 REQUIRES_NEW 는 지켜야 한다.
- 테스트 클래스 구성. 단, `@Nested` 와 `@TestPropertySource`/`@MockitoBean` 조합은 이전에 동작하지 않았으므로 최상위 클래스로 나눈다.
- Gradle 은 `JAVA_HOME=/Library/Java/JavaVirtualMachines/temurin-21.jdk/Contents/Home` 으로 실행한다.
