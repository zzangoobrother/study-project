## 1. 개요

2026-09-06 문서는 락 보유 시간을 줄여 핫스팟 상한을 708 → 887 TPS 로 올렸고, 12.6 장에서
**"락 구간에서 코드로 걷어낼 수 있는 것은 이번에 다 걷어냈다"** 고 결론냈다.

그 결론에는 검증되지 않은 전제가 하나 있다. 근거가 된 부하 테스트가 **항상 항목 1 개짜리 주문만
보냈다**는 것이다.

```javascript
// loadtest/ab.js
items: [{ productId: productId, quantity: 1 }],
```

항목이 여러 개면 재고 차감이 상품 수만큼 반복되고, **그 반복이 전부 락 구간 안에서 일어난다.**
1 개짜리 주문에서는 반복이 없으니 이 비용이 0 이고, 그래서 측정에 잡히지 않았다.

이 문서는 그 반복을 **한 문장으로 접는다.** 조건부 `UPDATE` 전략은 그대로 유지한다 —
바뀌는 것은 그 판정을 몇 번에 나눠 보내는가 하나다.

## 3. 문제 — 락 구간이 항목 수에 비례한다

### 3.1 락은 첫 `UPDATE` 에서 잡히고 `COMMIT` 에서 풀린다

```kotlin
// OrderFacade.place — 현재
sorted.forEach { item ->
    if (!productService.decreaseStock(productId = item.productId, quantity = item.quantity.value)) {
        throw CoreException(ErrorType.CONFLICT, "...")
    }
}
```

`decreaseStock` 은 상품당 한 번씩 왕복한다. InnoDB 배타 행 락은 **트랜잭션이 끝나야** 풀리므로,
첫 번째 `UPDATE` 가 잡은 락은 나머지 왕복과 `COMMIT` 을 전부 기다린다.

```
항목 1 개                     항목 3 개
─────────────                 ─────────────────────────────
UPDATE p1  ← 락 획득          UPDATE p1  ← 락 획득
COMMIT     ← 해제             UPDATE p2     ) 이 왕복 2 개가
                              UPDATE p3     ) p1 의 락 구간 안에 있다
                              COMMIT     ← 해제
```

**p1 의 락 보유 시간이 항목 수에 따라 늘어난다.** 같은 상품을 사려는 다른 주문은 그만큼 더 기다린다.

### 3.2 정렬의 역설

2026-08-24 문서는 데드락을 막기 위해 `productId` 오름차순으로 차감하도록 정했다. 그 판단은 옳고
유지한다. 다만 부수 효과가 하나 있다 — **가장 낮은 ID 의 상품이 가장 먼저 잠기고 가장 오래 잠긴다.**

부하 테스트의 핫 상품이 `productId = 1` 이다. 정렬 순서상 언제나 첫 번째다. 즉 다중 항목 주문에서
핫스팟 상품은 **가장 불리한 자리**를 배정받는다.

정렬 방향을 뒤집는 것은 해결이 아니라 문제를 옮기는 것이다. 그때는 가장 높은 ID 가 같은 처지가 된다.
**락 획득 시점의 차이를 없애는 것**이 해법이고, 그것이 4 장이다.

### 3.3 얼마나 손해인가 (추정)

2026-09-06 문서의 개선 후 상한 887 TPS 를 역산하면 락 창구가 약 1.13ms 다.
여기에 왕복이 하나씩 더해진다고 보면 이렇게 된다.

| 항목 수 | 락 창구 (추정) | 핫스팟 상한 (추정) |
|---|---|---|
| 1 | 1.13ms | 887 TPS (실측) |
| 3 | 약 1.33ms | 약 750 TPS |
| 5 | 약 1.53ms | 약 650 TPS |

**왕복 하나를 0.1ms 로 가정한 값이며, 그 가정 자체가 측정되지 않았다.** 표의 목적은 배수를
주장하는 것이 아니라 **비용이 항목 수에 선형으로 붙는다**는 구조를 보이는 것이다.

여기에 2026-09-06 문서 9 장의 성질이 겹친다 — 대기 시간은 이용률에 선형이 아니다. 포화 근처에서는
락 창구가 조금만 늘어도 응답 시간이 비선형으로 무너진다. **선형으로 늘어난 락 구간이 비선형으로
증폭된다**는 뜻이다.

### 3.4 왜 지금까지 안 보였는가

`ab.js` 가 항목 1 개만 보냈기 때문이다. 그 시나리오에서는 이 비용이 정확히 0 이므로,
2026-09-06 문서의 상한 887 TPS 는 **가능한 가장 유리한 조건에서 잰 값**이다.

> 부하 스크립트가 만들지 않는 형태의 요청은 그 시스템에 존재하지 않는 것과 같다.
> **측정하지 않은 축은 최선의 값으로 보고된다.**

## 4. 설계 — 한 문장으로 N 행을 차감한다

### 4.1 쿼리

판정을 SQL 안에 두는 성질은 그대로 두고, 행 수만 늘린다.

```sql
UPDATE products
   SET stock = stock - CASE id WHEN :id0 THEN :q0 WHEN :id1 THEN :q1 ... END
 WHERE id IN (:id0, :id1, ...)
   AND deleted_at IS NULL
   AND stock >= CASE id WHEN :id0 THEN :q0 WHEN :id1 THEN :q1 ... END
```

`WHERE` 절의 `CASE` 가 핵심이다. **행마다 다른 수량으로 판정**하므로, 어떤 상품 하나라도 부족하면
그 행만 갱신되지 않는다. 조건이 `stock >= :quantity` 인 성질은 상품별로 그대로 보존된다.

`updated_at` 을 건드리지 않는 것도 유지한다 (2026-08-24 문서 6.3 장) — 재고가 빠진 것은
상품을 편집한 것이 아니다.

### 4.2 판정 — 영향 행 수가 항목 수와 같은가

```kotlin
val affected = productService.decreaseStocks(sorted)   // 반환: 갱신된 행 수
if (affected != sorted.size) {
    throw CoreException(ErrorType.CONFLICT, "...")      // 트랜잭션 전체 롤백
}
```

지금의 판정(`영향 행 수 0 이면 실패`)을 그대로 확장한 것이다. **부분 성공은 롤백으로 처리된다** —
일부 행이 갱신됐더라도 `CoreException` 이 트랜잭션을 되돌리므로 재고가 어긋난 채 남지 않는다.
2026-09-06 문서 6.2 장이 정한 성질을 그대로 쓴다.

### 4.3 이 방식이 성립하는 전제는 이미 갖춰져 있다

새로 만들 것이 없다. 세 가지 전제가 모두 기존 코드에 있다.

| 전제 | 어디에 있는가 |
|---|---|
| 한 주문에 같은 `productId` 가 두 번 나오지 않는다 | `OrderCommand.Place.init` 이 400 으로 차단 (2026-08-24 문서 6.7 장) |
| 어느 상품이 부족한지 구분하지 않는다 | `OrderFacade.place` 의 기존 주석 — "0 행은 재고 부족과 상품 소멸을 함께 뜻한다" |
| 소프트 삭제 상품은 차감 대상이 아니다 | `deleted_at IS NULL` 조건 유지 |

첫 번째가 특히 중요하다. **중복이 허용됐다면 한 행이 `CASE` 에 두 번 나올 수 없어 이 설계가 성립하지
않는다.** 다른 이유(응답의 항목 수가 요청과 달라지는 문제)로 세운 규칙이 여기서 전제가 되어 준다.

### 4.4 정렬이 불필요해진다

데드락 방지를 위한 `sortedBy { it.productId }` 는 **여러 문장이 순차로 락을 잡기 때문에** 필요했다.
한 문장이 되면 MySQL 이 인덱스(PK) 순서로 락을 잡으므로 **정렬 순서가 엔진 차원에서 통일된다.**

그래도 **정렬은 남긴다.** 이유는 두 가지다.

- 저장되는 항목의 순서와 무관한 순수 방어이고 비용이 없다.
- 이 설계가 되돌려지거나 다른 경로가 상품을 여러 번 갱신하게 될 때 다시 필요해진다.

즉 **정렬은 이제 필수가 아니라 이중 안전장치다.** 이 성격 변화를 코드 주석에 남긴다.

### 4.5 구현 위치

`infrastructure` 다. 항목 수가 요청마다 다르므로 `@Query` 애노테이션으로는 표현할 수 없고,
쿼리 문자열을 동적으로 조립해야 한다. **SQL 의 형태가 계층 밖으로 새지 않게** 하는 것은
`infrastructure` 의 기존 책임이다 (CLAUDE.md — 소프트 삭제 필터, `Pageable` 번역 등을 흡수한다).

도메인이 보는 계약은 이렇다.

```kotlin
// domain/product/ProductRepository
fun decreaseStocks(items: List<StockDecrease>): Int
```

`Long` 과 `Int` 를 나열한 파라미터가 아니라 값 객체 리스트를 받는다. `Quantity` 가 이미 1 이상을
보장하므로, **이 객체가 만들어졌다는 사실이 검증 통과를 의미한다**는 규약이 유지된다.

### 4.6 실패 메시지는 정밀도를 잃는다

지금은 실패한 상품 하나를 특정해 메시지에 담는다.

```
[productId = 3] 재고가 부족하거나 주문할 수 없는 상품입니다.
```

한 문장이 되면 **어느 행이 조건에 걸렸는지 영향 행 수만으로는 알 수 없다.** 요청한 상품 전체를
담는 형태가 된다.

```
[productIds = [1, 3, 7]] 재고가 부족하거나 주문할 수 없는 상품이 포함되어 있습니다.
```

**버린 선택지 — 실패 후 재조회로 특정하기.** 실패 경로는 핫패스가 아니므로 쿼리를 하나 더 써도
처리량에 영향이 없다. 그럼에도 하지 않는다. 롤백될 트랜잭션 안에서 조회하면 부분 성공한 자기
변경이 보여 값이 헷갈리고, 그 조회 역시 같은 행의 락을 기다릴 수 있다. **무엇보다 "부족한 상품을
특정해 알려준다" 는 계약을 이 코드베이스가 세운 적이 없다** — 기존 정책도 재고 부족과 상품 소멸을
구분하지 않는다.

## 5. 무엇이 바뀌지 않는가

이 변경이 건드리지 않는 것을 적어 둔다. 리뷰에서 가장 먼저 의심할 자리들이다.

| 성질 | 근거 |
|---|---|
| 초과 판매 방지 | `stock >= :quantity` 조건이 행마다 그대로 평가된다 |
| 재시도 없음 | 조건부 `UPDATE` 유지 — 낙관적 락을 도입하지 않는다 |
| 롤백 방어선 | `CoreException` → `@Transactional` 롤백 (2026-09-06 문서 6.4 장) |
| 애그리거트 경계 | `OrderModel` ↔ `OrderItemModel` 관계 무변경 |
| 값 객체의 역할 | `Stock` 은 여전히 읽기 측 계약이고 `decrease()` 를 갖지 않는다 |
| 주문 저장이 차감보다 앞 | 2026-09-06 문서 6 장의 순서 그대로 |
| `OrderInfo` 변환 시점 | `clearAutomatically` 함정 그대로 — 차감 전에 끝낸다 (그 문서 6.3 장) |

동시성 테스트 10 건은 **하나도 약화시키지 않는다.** 오히려 다중 항목 동시 주문 테스트를 추가해야
이 설계의 계약이 고정된다 (8.2 장).

## 6. 락 전략 3 안의 처리량 비교

조건부 `UPDATE` 를 유지하는 결정은 2026-08-30 시점에 이미 내려졌고 2026-09-06 문서 11.2 장에
근거가 있다. 여기서는 그 결정을 **처리량의 관점에서** 다시 본다. 왜 이 방식이 빠른지 알아야
4 장의 개선이 왜 같은 방향인지가 설명되기 때문이다.

### 6.1 세 방식의 락 구간

```
A. 조건부 UPDATE (현재)
   BEGIN
     ... 조회 · 조립                         (락 없음)
     UPDATE ... WHERE id=? AND stock>=?      ← X 락 획득
     COMMIT                                  ← 해제
   락 구간 = UPDATE 실행 + COMMIT

B. 비관적 락 (SELECT ... FOR UPDATE)
   BEGIN
     SELECT ... FOR UPDATE                   ← X 락 획득  (왕복 1)
     (앱에서 재고 검사)                       ← 락을 쥔 채 앱으로 나갔다 온다
     UPDATE ...                              ← 왕복 2
     COMMIT                                  ← 해제
   락 구간 = 왕복 1 개 + UPDATE + COMMIT

C. 낙관적 락 (@Version)
   BEGIN
     SELECT ...                              (락 없음)
     (앱에서 재고 검사)
     UPDATE ... WHERE id=? AND version=?     ← X 락 획득
     COMMIT                                  ← 해제
     영향 행 0 이면 예외 → 롤백 → 재시도
   락 구간 = UPDATE 실행 + COMMIT   ← A 와 사실상 같다
```

**낙관적 락의 락 보유 시간은 조건부 `UPDATE` 와 거의 같다.** 차이는 락 구간의 길이가 아니라
**락을 기다린 뒤 무엇이 일어나는가**에 있다.

### 6.2 핵심 — 락을 기다린 뒤 성공하는가, 실패하는가

같은 상품을 두 요청이 동시에 살 때를 따라가 본다. 재고는 100 이고 각각 1 개씩 산다.

| | 조건부 `UPDATE` | 낙관적 락 |
|---|---|---|
| T1 | 락 획득 → `stock >= 1` 참 → 99 로 갱신 → 커밋 | 락 획득 → `version = 5` 참 → 갱신 → 커밋 |
| T2 | 락 대기 … T1 커밋 후 획득 | 락 대기 … T1 커밋 후 획득 |
| T2 의 판정 | `stock >= 1` → **99 >= 1 참** | `version = 5` → **6 이므로 거짓** |
| T2 결과 | **성공** | **0 행 → 예외 → 롤백 → 재시도** |

**두 방식이 똑같은 시간을 기다렸는데 한쪽만 성공한다.**

조건부 `UPDATE` 의 `WHERE` 절은 "재고가 남았는가" 를 묻는다. 다른 트랜잭션이 앞서 갔더라도
재고만 남아 있으면 참이다. 낙관적 락의 `WHERE` 절은 "내가 읽은 뒤 아무도 손대지 않았는가" 를 묻는다.
**앞서 간 트랜잭션이 있다는 사실 자체가 거짓 사유**다.

핫스팟은 정의상 "앞서 간 트랜잭션이 항상 있는" 상황이다. 그래서 낙관적 락은
**대기 비용을 다 치르고 나서 버려진다.**

### 6.3 핫스팟에서의 처리량

동시에 K 개 요청이 같은 행에 몰렸다고 하자.

- **조건부 `UPDATE`**: 락 창구 하나에 한 건씩 통과한다. K 건을 처리하는 데 락 창구 K 개.
- **비관적 락**: 역시 한 건씩 통과한다. 다만 창구 하나가 왕복 하나만큼 넓다.
- **낙관적 락**: 한 창구에 한 건만 성공하고 나머지 K−1 건은 실패해 처음부터 다시 한다.
  재시도가 다시 경합을 만들어 **부하가 스스로를 증폭시킨다.**

낙관적 락의 기대 시도 횟수는 충돌 확률 p 에 대해 1/(1−p) 다. 핫스팟에서 p 는 1 에 가까워지고,
그러면 시도 횟수가 발산한다. 실무에서 이것은 **라이브락에 가까운 상태**로 나타난다 —
에러율은 0 인데(재시도가 흡수하므로) 응답 시간만 끝없이 늘어난다. 2026-09-06 문서 12.3 장이
경고한 "서버 지표만 보면 정상인데 클라이언트는 타임아웃" 이 그대로 재현될 것이다.

비관적 락과 조건부 `UPDATE` 의 차이는 **왕복 하나**다. 락 창구가 1.13ms 인데 왕복이 0.1ms 면
창구가 약 9% 넓어지고, 상한은 그만큼 내려간다. 포화 근처의 비선형성(2026-09-06 문서 9 장)을
감안하면 응답 시간 격차는 그보다 크게 벌어진다.

### 6.4 분산에서의 처리량

분산 시나리오는 그림이 다르다. 서로 다른 행을 건드리므로 **충돌이 거의 없다.**

- **낙관적 락**: 충돌이 없으니 재시도도 없다. 조건부 `UPDATE` 와 거의 같은 성능이 나온다.
- **비관적 락**: 충돌이 없어도 왕복 하나를 더 쓴다. 분산의 병목은 커넥션 풀이고
  (2026-09-06 문서 4.2 장), 커넥션 점유 시간이 늘면 리틀의 법칙에 따라 상한이 내려간다.
  **경합이 없는 곳에서도 손해를 본다.**

> 낙관적 락이 나쁜 방식이라는 뜻이 아니다. **충돌이 드문 곳에서는 잘 맞는다.**
> 재고 차감은 그 반대 조건 — 충돌이 잦고, 충돌해도 대개 성공할 수 있는 — 이라 맞지 않을 뿐이다.

### 6.5 다중 항목이 격차를 벌린다

항목이 N 개면 각 방식의 비용이 이렇게 붙는다.

| 방식 | 락 구간 안 왕복 (항목 N 개) | 실패 확률 |
|---|---|---|
| 조건부 `UPDATE` — 현재 | **N** | — |
| 조건부 `UPDATE` — 4 장 적용 후 | **1** | — |
| 비관적 락 | 2 이상 (`FOR UPDATE` + 갱신) | — |
| 낙관적 락 | 1 | **1 − (1−p)^N** — 항목이 늘수록 급격히 오른다 |

낙관적 락은 **항목 하나라도 충돌하면 주문 전체를 다시 시도**해야 한다. 항목 3 개에 각 p = 0.5 면
성공률이 0.125 다. 다중 항목 주문에서 낙관적 락이 특히 불리한 이유다.

### 6.6 결론

| 시나리오 | 처리량 순서 |
|---|---|
| 핫스팟 (단일 행 집중) | 조건부 `UPDATE` > 비관적 락 ≫ 낙관적 락 |
| 분산 (행이 흩어짐) | 조건부 `UPDATE` ≳ 낙관적 락 > 비관적 락 |
| 다중 항목 | 격차가 모든 시나리오에서 벌어진다 |

**조건부 `UPDATE` 는 세 번째 선택지가 아니라 비관적 락을 한 문장으로 압축한 형태다.** InnoDB 배타
행 락을 쓰는 것은 비관적 락과 같고, 다른 점은 판정을 앱으로 가져오지 않아 왕복이 없다는 것뿐이다.
"명시적 락이 없다" 가 아니라 **"락은 같고 왕복이 없다"** 가 정확한 서술이다.

4 장의 개선은 이 방향을 한 단계 더 민 것이다 — **N 개 행의 락 획득까지 한 문장 안으로 접는다.**

> 이 절의 비교는 **구조 분석이지 실측이 아니다.** 세 방식을 같은 하네스로 재 본 적이 없다.
> 순서에 대한 확신과 배수에 대한 확신은 다르며, 이 문서는 앞의 것만 주장한다.

## 7. 위험과 한계

### 7.1 항목 수 상한이 없다

`OrderCommand.Place` 는 항목 수를 제한하지 않는다. 항목이 많아지면 `CASE` 절이 그만큼 길어지고
바인딩 파라미터가 항목당 2 개씩 늘어난다. 현실적인 주문에서는 문제가 되지 않지만,
**한 문장의 크기가 요청에 비례하는 구조**라는 점은 기록해 둔다. 상한을 둘지는 별도 판단이 필요하다.

### 7.2 실패 원인의 해상도가 낮아진다

4.6 장. 단일 항목 주문에서는 지금과 메시지가 같고, 다중 항목에서만 목록이 된다.

### 7.3 정렬이 필수에서 이중 안전장치로 바뀐다

4.4 장. 코드에 남기되 **성격이 바뀌었다는 사실을 주석에 적지 않으면** 다음 사람이 "쓸모없는 정렬" 로
보고 지울 수 있다. 지우는 것 자체는 이 설계에서 안전하지만, 다른 경로가 생기면 다시 위험해진다.

### 7.4 `order_items` INSERT 는 이 방향으로 줄일 수 없다

같은 발상(왕복을 접는다)을 INSERT 에 적용할 수는 없다. 두 겹으로 막혀 있다.

- `hibernate.jdbc.batch_size` 가 프로젝트 어디에도 설정되어 있지 않다 —
  `rewriteBatchedStatements: true` 가 켜져 있지만 Hibernate 가 배치를 만들지 않으므로 아무 일도 하지 않는다.
- 설정하더라도 소용없다. `BaseEntity` 가 `GenerationType.IDENTITY` 이고,
  **Hibernate 는 IDENTITY 에서 배치 INSERT 를 비활성화한다.** 생성된 키를 즉시 읽어야 하기 때문이다.

뚫으려면 ID 전략을 바꿔야 하는데 `BaseEntity` 는 `modules/jpa` 에 있어 세 앱이 공유한다.
**이 문서는 그 길을 닫힌 것으로 본다.**

### 7.5 개선 폭을 아직 말할 수 없다

3.3 장의 표는 추정이다. 실측하려면 8 장이 먼저다.

## 8. 측정 계획

### 8.1 하네스를 먼저 고쳐야 한다

`ab.js` 에 **항목 수를 환경변수로 받는 시나리오**를 추가한다. 항목 1 개 결과는 2026-09-06 문서와
비교 가능해야 하므로 기존 동작이 기본값이어야 한다.

주의할 점이 하나 있다. 다중 항목 주문은 상품을 여러 개 고르므로 **핫스팟과 분산의 경계가 흐려진다.**
"핫 상품 1 개 + 무작위 N−1 개" 형태로 고정해야 핫 행의 락 보유 시간을 재는 실험이 된다.

측정 조건은 2026-09-06 문서 3.5 장의 가드를 그대로 따른다 — 포화 이전 구간에서는
`dropped_iterations = 0`, 포화 이후에는 VU 여유를 확인한다.

### 8.2 테스트

- **동시성 통합 테스트** — 같은 상품을 포함한 다중 항목 주문을 동시에 넣고 초과 판매가 없는지.
  기존 10 건은 그대로 통과해야 한다.
- **부분 실패 롤백** — 항목 3 개 중 하나만 재고가 부족할 때 나머지 두 상품의 재고가
  원래대로인지, 주문 행이 남지 않았는지.
- **단위 테스트** — 차감이 **한 번만** 호출되는지 (`verify(times(1))`).
  이 단언이 없으면 누군가 루프로 되돌려도 아무도 모른다.

### 8.3 무엇을 근거로 삼을 것인가

2026-09-06 문서 8.4 장의 규칙을 따른다. **같은 환경 안에서 조건을 통일해 얻은 A/B 만 근거로 쓴다.**
항목 1 개 결과와 항목 N 개 결과를 같은 표에 놓고 비교하지 않는다 — 그것은 서로 다른 실험이다.
