## 1. 개요

### 1.1 지금 상품 목록은 정렬을 전량 filesort 로 처리한다

`products` 에 걸린 인덱스는 하나뿐이다.

```kotlin
// ProductModel.kt
@Table(
    name = "products",
    indexes = [Index(name = "idx_products_brand_id", columnList = "brand_id")],
)
```

이 인덱스는 **브랜드 필터만 처리한다.** `ORDER BY like_count DESC, id DESC` 는 인덱스가 없으므로
필터를 통과한 행 전부를 읽어 정렬한 뒤 `LIMIT` 만큼 잘라낸다. 인기 브랜드에 상품이 25,000 건 있으면
20 건을 보여주려고 25,000 건을 정렬한다.

**시드가 137 건이라 지금은 아무 문제도 드러나지 않는다.** 137 건은 정렬해도 순식간이다.
문제는 데이터가 늘어난 뒤에 드러나며, 그때는 이미 운영 중이다.

### 1.2 왜 지금인가

세 가지가 맞물렸다.

1. **측정 하네스가 있다.** `loadtest/` 의 Docker compose·자원 배분·k6 설정을 그대로 쓸 수 있다.
2. **측정 규약이 있다.** 2026-09-09 문서 4.4 장이 워밍업 편향을 찾아내 "버리는 실행 2 회" 를 규약에 넣었다.
   그 규약 없이 읽기 경로를 재면 같은 함정을 다시 밟는다.
3. **문서 구조가 있다.** 2026-09-09 문서의 **가설(3.1~3.6) → 실측(3.7) → 판정(3.8)** 이 그대로 맞는 문제다.
   인덱스 설계는 논증으로 끝낼 수 있는 것처럼 보이지만, 실제로는 데이터 분포에 달려 있어 재 봐야 한다.

### 1.3 이 문서는 인덱스만 다룬다

10 만 건을 심으면 인덱스로 풀리지 않는 병목이 함께 드러난다 — `OFFSET` 깊은 페이지와 `count` 쿼리다.
**둘 다 해결은 후속 문서로 넘긴다** (4.4 · 4.5 장). 다만 count 는 **어떻게 세는지가 A 안과 B 안에서
크게 갈리므로 판정 격자 안에서 잰다** — 세는 행 수를 줄이는 일만 밖으로 미룬다 (3.3 장).

2026-09-11 문서를 2026-09-09 에서 분리한 것과 같은 판단이다. 한 문서가 여러 주제를 다루면
어느 것도 끝까지 가지 못한다.

## 2. 범위

### 포함

- **`sort=likes_desc` 두 경로의 인덱스 설계** — 브랜드 필터 유무
- **10 만 건 시드** — 결정적 생성, 롱테일 분포 (5.2 장)
- **`EXPLAIN` / `EXPLAIN ANALYZE` 전후 비교** — 개선 전 · A 안 · B 안 × content · count 12 칸 (5.4 장)
  그리고 격자 밖의 **오름차순 인덱스 1 회** — `DESC` 키워드가 필요한지를 가른다 (3.4 장)
- **k6 end-to-end 확인** — 채택안 1 개 도착률 (5.5 장)

### 제외

| 제외 대상 | 이유 |
|---|---|
| `OFFSET` 깊은 페이지 | 인덱스로 풀리지 않는다. 커서 페이징이 필요하고 API 계약이 바뀐다. 관측만 한다 (4.4 장). |
| `count` 쿼리 **최적화** | 전량 집계를 없애려면 캐시나 근사 집계가 필요하고 `totalElements` 의 의미가 바뀐다. 다만 count 의 **실행 계획은 A/B 판정에 들어간다** — 거기서 두 안의 차이가 가장 크게 벌어진다 (3.3 · 4.5 장). |
| `latest` / `price_asc` 정렬 | 같은 기법이 적용되지만 이 문서는 판정하지 않는다. 좋아요순에서 정한 방식을 나중에 옮긴다. |
| 커버링 인덱스 | 쿼리가 `SELECT *` 라 현실적으로 불가능하다 (3.1 장). |
| 캐시 도입 | 인덱스로 무엇이 해결되고 무엇이 남는지 먼저 알아야 한다. 순서의 문제다. |
| `LocalDataSeeder` 수정 | 시드 137 건은 `order-v1.http` 의 품절 409 확인 목적이다. `loadtest/prepare.sql` 주석이 세운 원칙을 따른다. |

## 3. 인덱스 설계와 가설

> **3.1~3.5 는 측정 전에 쓴 가설이다.** 실측은 3.6 장에, 판정은 3.7 장에 들어간다.
> 측정이 끝나면 각 절 끝에 판정을 붙이고 이 인용 블록을 지운다.

### 3.1 커버링 인덱스는 선택지가 아니다

`ProductQueryDslRepository.execute` 가 `selectFrom(productModel)` 이므로 `SELECT *` 다.
`products` 의 컬럼은 아홉 개다.

```
id · brand_id · name · price · like_count · stock · created_at · updated_at · deleted_at
```

`name` 을 인덱스에 넣으면 인덱스가 테이블만 해진다. **커버링은 포기한다.**

그래서 이 설계의 목표는 커버링이 아니라 하나다.

> **정렬을 인덱스가 대신하게 해서, 읽는 행 수를 25,000 에서 20 으로 줄인다.**

행 접근은 PK 룩업 20 회로 남는다. 개선의 주 지표는 `EXPLAIN` 의 `rows` 이고,
부 지표는 `Extra` 에서 `Using filesort` 가 사라지는 것이다.

### 3.2 대상 경로 둘

```sql
-- 경로 ① 브랜드 필터 있음
WHERE brand_id = ? AND deleted_at IS NULL
ORDER BY like_count DESC, id DESC
LIMIT 20 OFFSET ?

-- 경로 ② 브랜드 필터 없음
WHERE deleted_at IS NULL
ORDER BY like_count DESC, id DESC
LIMIT 20 OFFSET ?
```

`id DESC` 가 마지막 정렬 키인 것은 2026-08-13 문서 5.5 장의 규약이다 — 정렬 키가 같은 행들의
순서가 쿼리마다 달라지면 페이지 경계에서 중복과 누락이 생긴다. **인덱스도 이 키까지 포함해야
정렬이 완전히 해결된다.** `(brand_id, like_count)` 까지만 걸면 동점 구간에서 다시 정렬이 필요하다.

**두 경로에 인덱스가 각각 필요하다.** 선두 컬럼이 `brand_id` 인 인덱스는 경로 ② 에 쓸 수 없다.
인덱스는 선두 컬럼부터 연속으로만 사용할 수 있고, 경로 ② 에는 `brand_id` 조건이 없기 때문이다.

### 3.3 쟁점 — `deleted_at` 을 인덱스에 넣을 것인가

두 경로 모두 `deleted_at IS NULL` 이 붙는다. 이것을 인덱스에 포함하느냐가 갈림길이다.

**A 안 — 필터·정렬 컬럼만**

```sql
CREATE INDEX idx_products_brand_like ON products (brand_id, like_count DESC, id DESC);
CREATE INDEX idx_products_like       ON products (like_count DESC, id DESC);
```

정렬은 인덱스가 해결한다. `deleted_at IS NULL` 은 인덱스에 없으므로 행을 읽은 뒤 걸러낸다.
삭제된 행을 만나면 버리고 다음을 읽으므로, `LIMIT 20` 을 채우는 데 20 건보다 더 읽는다.
`Extra` 에 `Using where` 가 남는다.

**B 안 — `deleted_at` 을 선두에**

```sql
CREATE INDEX idx_products_del_brand_like ON products (deleted_at, brand_id, like_count DESC, id DESC);
CREATE INDEX idx_products_del_like       ON products (deleted_at, like_count DESC, id DESC);
```

`IS NULL` 은 MySQL 에서 인덱스를 탈 수 있다. 등치 조건처럼 선두를 고정하고, 그 뒤가 정렬 순서
그대로다. `LIMIT 20` 이 정확히 20 건만 읽고 멈춘다. 대신 인덱스가 커지고,
**카디널리티가 낮은 컬럼을 선두에 두는 통상적 안티패턴을 정면으로 위반한다.**

#### 그 안티패턴이 여기서는 왜 성립하지 않는가

"카디널리티 높은 컬럼을 앞에" 라는 규칙은 **행을 좁히는 것이 목적일 때**의 이야기다.
`deleted_at` 은 거의 전부 `NULL` 이라 좁히는 데 기여하지 않는다.

여기서 `deleted_at` 을 앞에 두는 목적은 좁히기가 아니라 **뒤따르는 컬럼의 정렬 순서를 보존하는
것**이다. 등치(또는 `IS NULL`)로 고정된 선두 뒤에서만 인덱스 순서가 곧 `ORDER BY` 가 된다.
선두가 범위 조건이면 그 뒤는 정렬 순서를 잃는다.

**같은 컬럼이 목적에 따라 다른 자리를 갖는다.** 규칙을 기억하는 것과 규칙의 근거를 아는 것의
차이가 여기서 갈린다.

#### 갈림길은 목록 쿼리가 아니라 count 쿼리일 수 있다

위 두 문단은 `LIMIT 20` 을 채우는 목록 쿼리만 놓고 A 와 B 를 비교한다. 그 비교에서는 차이가
크지 않다 — 삭제 5.3% 면 A 가 20 건 대신 평균 21 건쯤 읽을 뿐이다.

그런데 `ProductQueryDslRepository.execute()` 는 **목록 1 회에 쿼리를 두 번 낸다.** content 와 count 다.
count 쪽에서는 같은 차이가 전혀 다른 크기로 나타난다.

```
경로 ① count :  SELECT COUNT(*) FROM products WHERE brand_id = 1 AND deleted_at IS NULL

A 안  (brand_id, like_count, id)
      brand_id = 1 로 25,000 엔트리를 훑지만 deleted_at 이 인덱스에 없다.
      NULL 여부를 알려면 행을 봐야 하므로 25,000 회 행 접근이 따라붙는다.

B 안  (deleted_at, brand_id, like_count, id)
      deleted_at IS NULL 과 brand_id = 1 이 둘 다 선두 연속이다.
      23,685 엔트리를 인덱스만으로 세고 끝난다. 행 접근 0.
```

**`LIMIT` 이 없기 때문이다.** 목록 쿼리는 20 건을 채우면 멈추므로 A 의 불리함이 1 건으로 끝나지만,
count 는 조건에 맞는 행을 전부 세야 하므로 그 불리함이 25,000 배로 확대된다.
같은 인덱스 차이가 한쪽에서는 무시할 만하고 다른 쪽에서는 지배적이다.

그래서 **A/B 판정을 목록 쿼리만으로 내리면 안 된다.** 두 쿼리가 한 요청에 함께 나가므로,
목록에서 오차 범위인 차이와 count 에서 지배적인 차이를 합산한 것이 사용자가 실제로 겪는 비용이다.
4.5 장은 원래 count 를 "관측만" 하는 것으로 두었으나, 이 이유로 **판정 격자 안으로 옮겼다.**

### 3.4 `DESC` 키워드는 필요한가

`ORDER BY like_count DESC, id DESC` 는 **전부 내림차순**이다. 이런 경우 MySQL 은 오름차순
인덱스를 거꾸로 읽어 같은 결과를 낸다(`Extra: Backward index scan`). 즉 `DESC` 없이도 계획이
같을 수 있다.

그래도 명시한다. 두 가지 이유다.

1. 의도가 드러난다 — 이 인덱스가 어떤 `ORDER BY` 를 위한 것인지 정의에서 읽힌다.
2. 나중에 `like_count DESC, id ASC` 같은 **혼합 정렬**이 생기면 그때는 진짜로 필요해진다.
   혼합 정렬은 역방향 스캔으로 처리할 수 없다.

**확인 지점 — 여기에 함정이 하나 있다.** `Backward index scan` 은 "오름차순 인덱스를 거꾸로
읽었다" 는 표시다. 그런데 A 안·B 안은 `DESC` 를 명시해 만들므로 MySQL 8.0 에서 진짜 내림차순
인덱스가 되고(`SHOW INDEX` 의 `Collation` 이 `D`), 그 인덱스에서 `ORDER BY ... DESC` 는
**정방향 스캔**이다. **즉 A/B 격자에서는 이 문자열이 나타나지 않는 것이 정상이고, 그 부재는
`DESC` 가 필요했다는 근거가 되지 못한다.**

그래서 이 질문은 격자가 아니라 **별도 측정 한 번**으로 답한다. A·B 를 모두 지우고 경로 ②
인덱스를 `DESC` 없이 하나만 만든 뒤 같은 쿼리를 `EXPLAIN` 한다.

```sql
CREATE INDEX idx_products_like_asc ON products (like_count, id);
EXPLAIN SELECT * FROM products WHERE deleted_at IS NULL
 ORDER BY like_count DESC, id DESC LIMIT 20;
```

`Extra` 에 `Backward index scan` 이 있고 `Using filesort` 가 없으면 `DESC` 없이도 같은 계획이
나온 것이니, `DESC` 는 문서화 목적이었다고 정직하게 적는다. 다른 인덱스가 남아 있으면 옵티마이저가
그쪽을 고르므로 확인이 성립하지 않는다 — 반드시 이 인덱스 하나만 두고 잰다.

### 3.5 가설

| # | 예측 | 판정 지표 | 실측 |
|---|---|---|---|
| 3.5.1 | 개선 전 두 경로 모두 `Using filesort`, 경로 ① 의 `rows` ≈ 25,000 | `EXPLAIN` 의 `Extra` · `rows` | *(측정 후)* |
| 3.5.2 | A · B 모두 `filesort` 가 사라지고 `rows` 가 세 자릿수 이하로 떨어진다 | 〃 | *(측정 후)* |
| 3.5.3 | **A 는 삭제 5% 때문에 `LIMIT 20` 을 채우는 데 20 건보다 더 읽는다** | `EXPLAIN ANALYZE` 의 `actual rows` | *(측정 후)* |
| 3.5.4 | 그 초과분이 미미해 A 와 B 의 실측 차이는 오차 범위다 | `EXPLAIN ANALYZE` 의 `actual time` | *(측정 후)* |
| 3.5.5 | **오름차순 인덱스**로 만들어도 `Backward index scan` 으로 같은 계획이 나온다 — 즉 `DESC` 없이도 된다 | 오름차순 인덱스 1 회 측정의 `Extra` (**A/B 격자가 아니다** — 3.4 장) | *(측정 후)* |
| 3.5.6 | **count 쿼리에서는 B 가 A 를 크게 이긴다** — A 는 행 접근이 따라붙고 B 는 인덱스 온리로 끝난다 (3.3 장) | count 쿼리의 `Extra` 에 `Using index` 유무 · `actual time` | *(측정 후)* |

3.5.1~3.5.5 는 목록(content) 쿼리에 대한 것이고, **3.5.6 만 count 쿼리에 대한 것이다.**
다만 **3.5.5 는 격자 밖에서 따로 잰다** — 같은 content 쿼리를 보지만 A/B 격자로는 판정되지 않는다 (3.4 장).
두 쿼리가 한 요청에 함께 나가므로 판정은 둘을 합쳐서 내린다.

#### 무엇이 이 가설을 반증하는가

- **3.5.4 가 깨지면** — B 가 유의미하게 빠르면 B 를 채택한다. 인덱스 1 컬럼의 비용보다
  삭제 행을 건너뛰는 비용이 크다는 뜻이다.
- **3.5.6 이 깨지면** — count 에서도 A 와 B 가 비슷하면, MySQL 이 A 안에서도 행 접근 없이
  판정할 길을 찾았다는 뜻이다(예: 다른 인덱스와의 index merge). 그 경로를 `EXPLAIN` 에서
  추적해 기록한다. 이 경우 A 가 그대로 이긴다.
- **3.5.3 이 나타나지 않으면** — A 의 `actual rows` 가 정확히 20 이면 MySQL 이 `deleted_at` 을
  예상과 다른 방식으로 처리한 것이다. 그 경로를 추적해 기록한다.
- **3.5.5 가 깨지면** — 오름차순 인덱스에서 `filesort` 가 남거나 역방향 스캔이 나오지 않으면
  `DESC` 가 실제로 필요하다는 뜻이다. 그러면 Hibernate `@Index` 가 `desc` 를 통과시키지 못할 때
  대안이 "빼면 된다" 가 아니라 "SQL 로 만들어야 한다" 가 된다 (4.3 장).
- **3.5.2 가 깨지면** — 인덱스를 걸었는데도 `filesort` 가 남으면 인덱스 정의나 쿼리 형태에
  문제가 있다. 그 경우 이 설계 전체를 다시 본다.

#### 기본값은 A 다 — 단, count 도 비겼을 때만

3.5.4 를 "A 가 이긴다" 가 아니라 **"차이가 오차 범위"** 로 쓴 것은 의도적이다.

삭제 5.3% 면 `LIMIT 20` 을 채우는 데 평균 21 건쯤 읽는다. 1 건 더 읽는 비용이 인덱스 1 컬럼
증가 비용보다 크다고 볼 근거가 없다. **차이가 없으면 더 작은 인덱스를 고른다.** 이것이 기본값이고,
B 는 그것을 뒤집을 증거가 있을 때만 채택한다.

**그 기본값은 3.5.4 와 3.5.6 이 둘 다 오차 범위일 때만 성립한다.** 3.5.4 하나만 보고 A 를 고르면
"차이가 없다" 가 아니라 "차이가 나는 쪽을 안 봤다" 가 된다. 3.5.6 이 예측대로 나오면 —
count 에서 B 가 크게 이기면 — **더 작은 인덱스라는 논거는 지고 B 를 채택한다.**

목록 쿼리 하나만 재고 판정했다면 3.5.4 는 거의 반드시 성립했을 것이다. 20 건과 21 건의 차이는
버퍼 풀 상주 상태에서 타이밍 노이즈보다 작기 때문이다. **반증될 수 없는 가설은 가설이 아니다.**
3.5.6 을 넣은 것은 격자를 넓히려는 것이 아니라 이 판정에 반증 가능성을 돌려놓기 위해서다.

인덱스는 공짜가 아니다. 쓰기마다 갱신되고 버퍼 풀을 차지한다. 이 시스템에서 `products` 는
주문마다 `UPDATE` 되고 좋아요마다 `UPDATE` 된다 — **쓰기가 잦은 테이블이다.**

#### "더 작은 인덱스" 의 차이가 생각보다 크다 — 기존 인덱스의 운명이 갈린다

`products` 에는 이미 `idx_products_brand_id (brand_id)` 가 있다. A 와 B 는 이 인덱스를 **남길지
말지**까지 가른다.

```
A 채택  idx_products_brand_like = (brand_id, like_count, id)
        선두가 brand_id 라 기존 인덱스를 완전히 흡수한다.
        idx_products_brand_id 는 완전 중복 → 지울 수 있다.          최종 인덱스 2 개

B 채택  idx_products_del_brand_like = (deleted_at, brand_id, ...)
        선두가 deleted_at 이라, 그 조건이 없는 쿼리는 이 인덱스를 못 쓴다.
        ProductQueryDslRepository.searchIncludingDeleted() 가 정확히 그 경우다
        (어드민 목록 — 조건이 brand_id 하나뿐이고 소프트 삭제도 보여줘야 한다).
        idx_products_brand_id 를 지울 수 없다.                      최종 인덱스 3 개
```

**인덱스는 선두 컬럼부터 연속으로만 쓸 수 있다** 는 성질이 여기서는 "쓸 수 있는가" 가 아니라
**"기존 인덱스를 대체할 수 있는가"** 쪽으로 작동한다. `(a, b, c)` 는 `(a)` 를 흡수하지만
`(x, a, b)` 는 흡수하지 못한다.

그래서 A 와 B 의 쓰기 비용 차이는 "인덱스 1 컬럼" 이 아니라 **인덱스 2 개 대 3 개**다.
쓰기가 잦은 테이블에서 이 차이는 3.5.4 의 오차 범위보다 크다. **3.5.6 이 B 의 손을 들어주지
않는 한, 이 항목이 A 쪽 논거를 한 번 더 굳힌다.**

다만 **이 문서는 `idx_products_brand_id` 를 지우지 않는다.** 그것은 이 문서가 재지 않은 다른
쿼리들(브랜드 필터 + `latest` · `price_asc`)에 영향을 주므로 별도 확인이 필요하다. 7 장의
열린 질문으로 남긴다 — 여기서 하는 일은 **그 선택지가 A 에만 열려 있다는 사실을 판정 근거에
넣는 것**까지다.

## 4. 위험과 한계

### 4.1 ⚠️ 버퍼 풀에 전부 올라간다 — 이 측정의 가장 큰 제약

10 만 건 × 9 컬럼이면 테이블이 수십 MB 다. 측정 환경의 `innodb_buffer_pool_size` 가 1G 이므로
**테이블과 인덱스가 전부 메모리에 상주한다.**

```
측정되는 것      정렬 비용 (CPU)
측정되지 않는 것  디스크 I/O 감소분
```

실제 서비스에서 인덱스의 더 큰 가치는 **디스크를 덜 읽는 것**인데, 이 환경에서는 드러나지 않는다.
**개선폭이 과소평가된다.**

이 한계를 안고 측정한다. 버퍼 풀을 줄여 재측정하는 것은 후속으로 남긴다 — 버퍼 풀을 줄이면
이번에는 그것이 지배 변수가 되어 인덱스 효과와 섞인다. 한 번에 하나씩 본다.

### 4.2 ⚠️ 인덱스가 운영 스키마에 반영될 경로가 없다

```
ddl-auto: none (dev 이상)  +  Flyway · Liquibase 부재  +  schema.sql 부재
```

`@Index` 로 선언하면 `local` · `test` 프로파일에서는 Hibernate 가 DDL 을 생성하므로 인덱스가
만들어진다. **`dev` 이상에는 심을 방법이 저장소에 없다.**

성능 개선을 문서로 증명해 놓고 운영에는 반영되지 않는 상태다. 이 문서의 범위에서 해결하지는
않지만, **마이그레이션 도구 도입을 후속 과제로 명시한다.**

같은 문제가 `uk_user_coupons_user_coupon` 유니크 제약에도 있다 — 쿠폰의 "최대 한 번 사용"
보장이 그 제약에 의존하는데, 그것 역시 `dev` 이상에 심을 경로가 없다.
**인덱스보다 제약 쪽이 위험이 크다.**

### 4.3 Hibernate `@Index` 의 `DESC` 지원

`columnList = "brand_id, like_count desc, id desc"` 가 Hibernate 6 에서 그대로 통과하는지
**채택안을 코드에 반영할 때 확인한다** — `ddl-auto: create` 로 도는 테스트 스위트가 스키마 생성에
실패하면 거기서 드러난다. 통과하지 않으면 인덱스는 SQL 로 직접 만들고 `@Index` 에는 주석으로
의도만 남긴다.

3.5.5 가 성립하면 `DESC` 없이도 같은 계획이 나오므로 이 위험은 해소된다. **가설 하나가 위험 하나를
덮는 구조다.** 다만 그 가설은 **오름차순 인덱스를 따로 만들어 봐야만** 판정된다 (3.4 장). A/B 격자에서
`Backward index scan` 이 안 보이는 것을 근거로 삼으면 안 된다 — `DESC` 인덱스에서는 원래 안 보인다.

**측정 순서가 중요하다.** 이 확인은 A/B 측정 직후, Task 4 에서 `@Index` 를 손대기 **전에** 끝나야 한다.
코드를 고친 뒤에 재면, `desc` 를 뺄지 말지 이미 정해 버린 뒤에 그 근거를 찾는 것이 된다.

### 4.4 `OFFSET` 깊은 페이지 — 관측만 한다

```
page=0      OFFSET 0       →  20 행 읽고 종료
page=4500   OFFSET 90000   →  90,020 행 읽고 90,000 행을 버린다
```

**인덱스로는 풀리지 않는다.** 인덱스가 정렬을 해결해도 `OFFSET` 은 건너뛸 행을 하나씩 세어야 한다.
해결책은 커서 페이징이고, 그것은 `PageQuery` · `PageResult` 규약과 `totalElements` 의 의미를
바꾸므로 별도 문서가 필요하다.

두 지점의 `EXPLAIN ANALYZE` 수치만 기록한다. **숫자를 남겨 두면 후속 문서가 근거를 다시
만들지 않아도 된다.**

### 4.5 `count` 쿼리 — 전량 집계는 남는다 (판정에는 들어간다)

`execute()` 는 목록 1 회에 쿼리를 두 번 낸다.

```sql
SELECT COUNT(*) FROM products WHERE brand_id = 1 AND deleted_at IS NULL;
```

인기 브랜드면 23,685 행을 센다(25,000 건에서 삭제 1,315 건을 뺀 값). **어느 안을 골라도 이 숫자는
줄지 않는다** — 전량 집계라는 성질 자체는 인덱스로 풀리지 않는다. 그것이 이 절이 "한계" 장에
남아 있는 이유다.

**한계인 것은 세는 행 수이고, 인덱스가 바꾸는 것은 그 23,685 를 어떻게 세느냐다.**

```
A 안  25,000 엔트리 + 25,000 회 행 접근  (deleted_at 이 인덱스에 없다)
B 안  23,685 엔트리, 행 접근 0            (Extra: Using index)
```

이 차이는 3.3 장이 설명하듯 `LIMIT` 이 없어서 생긴다. 목록 쿼리에서는 20 건을 채우고 멈추므로
같은 차이가 1 건으로 끝나지만, count 에는 멈출 지점이 없다.

> **이 절은 원래 "관측만 한다" 였다.** 목록 쿼리로만 A/B 를 판정하고 count 는 수치만 남기려 했는데,
> 그러면 **두 안의 차이가 가장 크게 벌어지는 자리를 판정에서 빼는 것**이 된다. 게다가 5.5 장의 k6 는
> count 를 포함한 실제 요청을 재므로, 목록 쿼리로 A 를 뽑아 놓고 k6 에서 B 가 빠른 모순이 생길 수 있다.
> 그래서 count 를 3.5.6 가설로 세우고 5.4 장 격자에 넣었다. **관측과 판정의 경계를 "이 문서가 고칠 수
> 있는가" 가 아니라 "채택 결정을 바꾸는가" 로 다시 그은 것이다.**

count 를 **더 빠르게 만드는 일**(캐시·근사 집계·`totalElements` 규약 변경)은 여전히 이 문서 밖이다.

### 4.6 측정값이 로컬 머신에 종속된다

Docker Desktop VM 의 자원 배분(5 CPU / 6144 MiB)에 따라 절대값이 달라진다.
**절대값이 아니라 같은 환경에서의 상대 비교만 근거로 삼는다** — 2026-09-06 문서와 같은 판단이다.

## 5. 측정 계획

### 5.1 환경 — 기존 규약을 그대로 재사용

| 항목 | 값 | 출처 |
|---|---|---|
| `commerce-api` | 3.0 CPU / 2g, JVM `-Xms1g -Xmx1g` | 2026-09-06 `loadtest/README.md` |
| `mysql` | 2.0 CPU / 2g, `innodb_buffer_pool_size=1G` | 〃 |
| 측정 전 | 컨테이너 `down -v` → 새로 기동 | 〃 |
| 측정 전 | **버리는 실행 2 회** | 2026-09-09 문서 4.4 장 |

마지막 줄이 핵심이다. 2026-09-09 문서 4.4 장은 같은 조건을 1 회차와 6 회차에 재서
**p95 가 552ms 와 4.1ms — 134 배** 차이나는 것을 찾아냈다. 그 규약 없이 재면 같은 함정을 다시 밟는다.

> **하네스를 읽기 경로에 재사용할 때 딸려오는 제약이 하나 있다.** `loadtest-compose.yml` 은 앱을
> `local` 프로필로 띄우고, 그 프로필의 `ddl-auto` 는 `create` 다. 주문 측정에서는 `prepare.sql` 로
> 재고만 덮어쓰면 됐으므로 드러나지 않았지만, **10 만 행을 쌓는 이 측정에서는 앱 컨테이너를 한 번
> 재기동하는 것만으로 시드가 전부 사라진다.** 인덱스 전환을 SQL 로만 하는 이유가 워밍업 보존
> 하나만이 아니게 된 셈이다 (5.3 장).

> **`EXPLAIN` 에도 워밍업이 필요한가.** 실행 계획 자체는 워밍업과 무관하다. 그러나
> `EXPLAIN ANALYZE` 는 쿼리를 실제로 실행하므로 `actual time` 은 영향을 받는다.
> `rows` · `key` · `Extra` 는 첫 실행에서 읽어도 되고, `actual time` 은 규약을 지켜서 읽는다.

### 5.2 시드 설계 — 결정적으로 심는다

**난수를 쓰지 않는다.** 재측정할 때 같은 데이터여야 하는데, `RAND()` 는 시드를 고정해도 MySQL
버전·플랫폼에 따라 달라질 수 있다. 2026-09-09 문서 4.4 장에서 이미 "편향이 두 번 다 걸리면
일관성이 정확성으로 오독된다" 를 겪었으니, 데이터만큼은 변수에서 뺀다.

**규모:** 브랜드 200 개 · 상품 100,000 건

#### `brand_id` — 롱테일, `id` 구간으로 결정

| `id` 구간 | `brand_id` | 건수 |
|---|---|---:|
| 1 ~ 25,000 | 1 | 25,000 |
| 25,001 ~ 40,000 | 2 | 15,000 |
| 40,001 ~ 50,000 | 3 | 10,000 |
| 50,001 ~ 75,500 | `4 + (id - 50001) / 1500` | 1,500 × 17 |
| 75,501 ~ 100,000 | `21 + (id - 75501) % 180` | 약 136 × 180 |

**최악 경로는 `brandId=1` 이다** — 25,000 건을 정렬해 20 건을 낸다.
균등 분포로 심으면 이 경로가 생기지 않아 개선폭이 밋밋해진다.

#### `like_count` — 지수 분포, `id` 로 결정

```
id % 1000 == 0   →  10000 + (id % 40000)    최상위      100 건  (0.1%)
id %  100 == 0   →   1000 + (id %  9000)    상위권      900 건  (0.9%)
id %   10 == 0   →    100 + (id %   900)    중위권    9,000 건  (9%)
그 외            →          (id %   100)    꼬리     90,000 건  (90%)
```

과반수가 한 자릿수~두 자릿수에 몰리고 소수가 크게 튀는 형태다. 실제 커머스의 좋아요 분포를 닮았다.

#### `deleted_at` — `id % 19 == 0`, 약 5.3%

**19 를 쓰는 이유가 이 시드의 핵심이다.**

`id % 20 == 0` 으로 심으면 그 행은 전부 `id % 10 == 0` 이므로 **삭제 상품이 좋아요 중위권
이상에만 몰린다.** 정렬 상위는 `LIMIT 20` 이 실제로 읽는 구간이므로, A 안이 건너뛰는 행이
실제보다 훨씬 많아 보인다. **분포의 우연이 A/B 판정을 뒤집는다.**

19 는 10 · 100 · 1000 과 서로소라 모든 `like_count` 버킷에 고르게 흩어진다.
비율은 5.26% 로 의도한 5% 에 충분히 가깝다.

> 이것이 2026-09-09 문서 4.4 장이 말한 편향의 전형이다. 재측정해도 같은 편향이 재현되므로
> 숫자는 안정적으로 나오고, **그 안정성이 정확성으로 오독된다.**
> 데이터를 설계할 때 잡지 않으면 나중에 잡을 수 없다.

#### 나머지 컬럼

| 컬럼 | 식 | 비고 |
|---|---|---|
| `name` | `'상품 ' || id` | 정렬·필터 대상 아님 |
| `price` | `1000 + (id % 500) * 100` | 1,000 ~ 50,900 원 |
| `stock` | `id % 200` | 0 이 섞여 품절 상태도 존재 |
| `created_at` | 기준일 − `(id % 365)` 일 | `latest` 정렬의 후속 측정용 |

`price` · `stock` · `created_at` 은 이 문서의 측정 대상이 아니다. 과제 요구("각 컬럼의 값은
다양하게 분포")를 만족시키고, `latest` · `price_asc` 를 나중에 잴 때 데이터를 다시 만들지
않아도 되도록 흩뜨려 둔다.

#### 파일

`loadtest/seed-products.sql` (신규). `LocalDataSeeder` 는 건드리지 않는다 —
`PRODUCT_COUNT = 137` 은 `order-v1.http` 의 품절 409 확인 목적이고,
`loadtest/prepare.sql` 주석이 이미 그 원칙을 세워 뒀다.

### 5.3 A/B 전환 — 같은 jar, SQL 한 줄

`@Index` 선언은 **측정이 끝날 때까지 건드리지 않는다.** 인덱스를 바꿀 때마다 jar 를 다시 빌드하면
JVM 워밍업 상태와 인덱스 효과가 섞인다 — 2026-09-09 문서가 "같은 jar, 환경변수 하나" 로 전환한
것과 같은 이유다. 여기서는 환경변수 대신 SQL 한 줄이다.

전환 SQL 의 **정본은 `loadtest/indexes-ab.sql`** 이며 A·B 각각의 생성·제거 네 블록을 담는다.
아래는 A → B 전환이 어떤 모양인지 보이는 **발췌**다. 실제 실행은 그 파일의 블록을 복사해서 한다 —
파일째 실행하면 A 와 B 가 동시에 생겨 무엇을 재는지 알 수 없게 된다.

```sql
-- loadtest/indexes-ab.sql 의 일부 (발췌)
DROP INDEX idx_products_brand_like ON products;
CREATE INDEX idx_products_del_brand_like
    ON products (deleted_at, brand_id, like_count DESC, id DESC);
```

### 5.4 `EXPLAIN` 격자 — 12 칸

**한 요청이 쿼리 두 개다.** 목록(content)만 재면 요청 비용의 절반만 재는 것이고, 하필 그 절반이
A 와 B 의 차이가 거의 없는 쪽이다 (3.3 장). 그래서 네 쿼리를 세 상태에서 잰다.

| | 개선 전 (현재) | A 안 | B 안 |
|---|---|---|---|
| 경로 ① content `brandId=1` | ○ | ○ | ○ |
| 경로 ② content 필터 없음 | ○ | ○ | ○ |
| 경로 ① count `brandId=1` | ○ | ○ | ○ |
| 경로 ② count 필터 없음 | ○ | ○ | ○ |

각 칸에서 기록하는 것:

```
EXPLAIN          type · key · key_len · rows · filtered · Extra
EXPLAIN ANALYZE  actual rows · actual time · loops
```

`EXPLAIN ANALYZE` 가 있어야 3.5.3(`LIMIT 20` 에 20 건보다 더 읽는가)을 판정할 수 있다.
추정 `rows` 로는 안 된다.

count 칸에서 특히 볼 것은 **`Extra` 의 `Using index`** 다. 이 문자열이 있으면 인덱스만으로 세고
끝난 것이고, 없으면 행을 읽으러 갔다는 뜻이다. 3.5.6 의 판정이 여기에 달려 있다.

**격자 밖에 측정이 하나 더 있다 — 오름차순 인덱스 1 회.** 3.5.5 는 이 12 칸으로 판정할 수 없어서
따로 잰다 (3.4 장). 격자에 13 번째 칸으로 넣지 않는 이유는 성격이 다르기 때문이다 — 이 12 칸은
**A 와 B 중 무엇을 채택할지**를 가르지만, 오름차순 측정은 채택안이 무엇이든 **그 인덱스를 `@Index`
로 선언할 수 있는지**를 가른다. 판정 대상이 다른 값을 같은 표에 넣으면 무엇을 비교하는 표인지 흐려진다.

> **count 의 `key` 가 `NULL` 로 나와도 그 자체가 오류는 아니다.** 경로 ② count 는 조건이
> `deleted_at IS NULL` 하나뿐인데 A 안 인덱스에는 그 컬럼이 없다. 옵티마이저가 쓸 만한 인덱스가
> 없다고 판단해 전체 스캔을 고르는 것이 자연스럽다. **그것이 곧 3.5.6 의 근거가 된다** —
> "A 안은 count 에서 인덱스의 도움을 받지 못한다" 를 보여주는 값이기 때문이다.

> **MySQL 8.0.18 이상이 필요하다.** 확인 결과 `mysql:8.0` 태그는 **8.0.46** 이었다
> (2026-09-17 Task 1). `EXPLAIN ANALYZE` 를 그대로 쓸 수 있고, 대체 계획
> (`EXPLAIN FORMAT=JSON` + `SHOW SESSION STATUS LIKE 'Handler_%'`)은 쓰지 않는다.

### 5.5 k6 — 채택안만, 1 개 도착률

```
loadtest/products.js  (신규)
  GET /api/v1/products?sort=likes_desc&brandId=1&page=0&size=20
  before vs 채택안
  기록: p95 · 에러율 · dropped_iterations
```

`loadtest/ab.js` 는 건드리지 않는다. 주문 측정의 재현성이 그 파일에 묶여 있어,
읽기 시나리오를 얹으면 기존 결과와 비교할 수 없게 된다.

**도착률을 하나만 쓰는 이유.** 이 측정의 목적은 상한 탐색이 아니라 "인덱스 효과가 API 계층까지
살아남는가" 의 확인이다. 상한 탐색은 2026-09-06 문서가 이미 겪었듯 포화 구간의 흔들림 때문에
훨씬 큰 노력이 든다.

### 5.6 무엇을 근거로 삼을 것인가

| 우선순위 | 지표 | 이유 |
|---|---|---|
| 1 | `EXPLAIN` 의 `rows` · `Extra` | 인덱스가 실제로 쓰였는지의 직접 증거 |
| 2 | count 쿼리 `Extra` 의 `Using index` | A/B 판정에서 가장 크게 벌어지는 자리 (3.5.6) |
| 3 | `EXPLAIN ANALYZE` 의 `actual rows` | 목록 쿼리 쪽 A/B 판정의 근거 (3.5.3) |
| 4 | `EXPLAIN ANALYZE` 의 `actual time` | 3.5.4 판정. 버퍼 풀 한계(4.1)를 감안해 읽는다 |
| 5 | k6 `p95` | end-to-end 확인. 인덱스 효과가 희석되어 나타난다 |

**k6 p95 의 크기가 `EXPLAIN` 을 뒤집지 않는다.** p95 에는 JVM · 직렬화 · 네트워크가 섞여 있어
인덱스 효과가 희석된다. 개선이 미미하게 보여도 그것이 인덱스가 무의미하다는 뜻은 아니다.

**다만 k6 가 판정의 *방향*을 뒤집으면 그때는 격자를 의심한다.** 크기가 희석되는 것과 순서가
뒤집히는 것은 다른 사건이다. A 를 채택했는데 k6 에서 B 가 더 빠르면, 희석으로는 설명되지 않는다 —
**격자가 재지 않은 쿼리가 요청 안에 있다는 뜻**이다. 실제로 이 문서는 count 를 격자 밖에 두었다가
같은 이유로 판정 기준을 다시 그었다 (4.5 장). 같은 일이 또 생기면 무엇이 빠졌는지부터 찾는다.

### 6.3 측정이 끝나면 진 쪽을 지운다

A/B 중 채택되지 않은 인덱스는 코드에 남기지 않는다. 2026-09-09 문서가 측정용 낙관적·비관적 락
구현을 재고 나서 걷어낸 것과 같다.

진 쪽은 **3.7 장의 판정 표에 근거로 남는다.** 다음에 누가
"`deleted_at` 을 인덱스에 넣으면 어떨까" 라고 물으면 그 표를 가리키면 된다.

남길 답은 규칙이 아니라 근거다. A 가 이겼다면 "넣으면 안 된다" 가 아니라
**"이 분포에서는 차이가 없었다"** 이고, B 가 이겼다면 "카디널리티가 낮으니 앞에 두면 안 된다" 가
아니라 **"count 에는 `LIMIT` 이 없어서 넣어야 했다"** 다 (3.3 장).

**어느 쿼리가 판정을 갈랐는지까지 적는다** — content 였는지 count 였는지. 이 문서는 한 번
그 구분을 놓쳐 판정 기준을 다시 그었고(4.5 장), 그 경위가 판정 자체보다 재사용 가치가 크다.

**최종 인덱스 개수도 함께 적는다.** A 가 이겼다면 `idx_products_brand_id` 를 흡수할 수 있으므로
2 개까지 줄일 여지가 생기고, B 가 이겼다면 그 인덱스가 남아 3 개가 된다 (3.5 장). 채택안의 정의만
적고 이 숫자를 빠뜨리면, 다음 사람이 "인덱스 하나 차이" 로 읽는다.

### 6.4 테스트

인덱스 추가는 쿼리 결과를 바꾸지 않으므로 **기존 테스트가 회귀 방어를 그대로 한다.**
`ProductQueryDslRepository` 를 거치는 통합 테스트와 `ProductV1ApiE2ETest` 가 정렬 순서와
페이징 경계를 이미 단언하고 있다.

**예외가 하나 있다 — 인덱스 선언의 존재 자체는 단언한다.** `ProductModelPersistenceTest` 에
`@Nested` 그룹을 더해 `SHOW INDEX FROM products` 로 두 인덱스가 스키마에 만들어지는지,
필터 없는 경로용 인덱스의 선두 컬럼이 `like_count` 인지를 본다.

성능을 단위 테스트로 지키자는 말이 아니다. **지키려는 것은 선언이 조용히 사라지는 회귀다.**
`@Index` 를 지워도 기존 748 건이 전부 통과하고, 느려진 것을 아무도 모른 채 배포된다.
4.2 장이 이미 "인덱스가 운영 스키마에 반영될 경로가 없다" 를 위험으로 올린 마당에,
`local` · `test` 에서라도 선언이 살아 있는지 보는 장치가 하나도 없는 것은 방어가 너무 얇다.

주의 — 이 테스트가 통과한다고 `dev` 이상에 인덱스가 있는 것은 아니다 (4.2 장).

다만 `@Index` 수정 후 전체 스위트를 한 번 돌려 `ddl-auto: create` 환경에서 스키마 생성이
깨지지 않는지 확인한다 — `DESC` 키워드가 Hibernate 를 통과하지 못하면 여기서 드러난다 (4.3 장).
