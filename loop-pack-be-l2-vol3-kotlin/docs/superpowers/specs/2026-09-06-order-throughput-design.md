## 1. 개요

주문 API 의 처리량을 부하 테스트로 측정하고, 병목을 특정해 **트랜잭션 구조를 바꿔 처리량을 올린다.**

이 문서는 새 기능을 만들지 않는다. 2026-08-24 문서가 세운 동시성 설계 — 조건부 `UPDATE` 와
`productId` 오름차순 정렬 — 는 그대로 유지된다. 바뀌는 것은 **그 락을 얼마나 오래 쥐고 있는가** 하나다.

앞선 문서들은 "초과 판매가 일어나지 않는가" 라는 정합성 질문에 답했다. 이 문서는 그 다음 질문에 답한다 —
**정합성을 지키면서 초당 몇 건까지 처리할 수 있는가.**

결과부터 적는다.

2 차 측정(Docker) 기준이다.

| 항목 | 개선 전 | 개선 후 | 변화 |
|---|---|---|---|
| 핫스팟 상한 (상품 1개 집중) | 708 TPS | **887 TPS** | **+25.3%** |
| 핫스팟 700 TPS 의 p50 | 8,331ms | **2.4ms** | **-99.97%** |
| 분산 1,200 TPS 의 p50 | 2,777ms | **11.9ms** | **-99.6%** |
| 주문 1건당 쿼리 수 | 7개 | **6개** | -1 |

락 구간에서 걷어낸 시간은 전체의 **13%** 인데 상한은 25% 오르고 응답 시간은 3,471 배 좋아졌다.
**그 간극이 이 문서의 핵심이다** (9 장).

분산 시나리오는 **상한을 단정하지 않는다.** 포화 구간의 달성 TPS 가 반복 측정마다 흔들려
(개선 전 1,030~1,284, 개선 후 1,008~1,176) 상한이라고 부를 수 없기 때문이다. 대신 무릎점으로 적었다.

## 2. 범위

### 포함

- 주문 API 의 처리량 한계 측정과 병목 특정
- `OrderFacade.place` 의 트랜잭션 내 실행 순서 재배치 (6 장)
- `order_items` 의 FK 소유권을 자식 엔티티로 이전 (7 장)
- 개선 전후 A/B 측정과 새 상한 재탐색

### 제외

- **인프라 설정 변경.** `innodb_flush_log_at_trx_commit`, `sync_binlog`, 커넥션 풀 크기를
  건드리지 않는다. 근거는 11.1 장에 있다.
- **낙관적 락 · 비관적 락 도입.** 조건부 `UPDATE` 를 유지한다 (11.2 장).
- **캐시.** 조회 경로는 이번 측정 대상이 아니다.
- **주문 취소 · 재고 복원.** 2026-08-24 문서의 제외 항목이 그대로 유효하다.

## 3. 측정 환경과 방법

### 3.1 환경 (2 차 측정 — 주 근거)

앱과 MySQL 을 각각 컨테이너에 넣고 **CPU · 메모리를 명시적으로 고정**했다.
자원 배분을 적어 두지 않으면 다음 사람이 같은 조건을 다시 만들 수 없다.

**호스트**

| 항목 | 값 |
|---|---|
| 기기 | Apple M2 Pro 10코어 / 16GB |
| OS | macOS 26.6.2 (25G83) |

**Docker Desktop VM**

| 항목 | 값 |
|---|---|
| 할당 CPU / 메모리 | **5 CPU / 6,144 MiB** |
| swap | 1,024 MiB |
| 가상화 | Apple Virtualization Framework + VirtioFS |
| Docker Engine / Compose | 24.0.5 / v2.20.2-desktop.1 |

**컨테이너**

| 컨테이너 | CPU | 메모리 | 이미지 · 설정 |
|---|---|---|---|
| `commerce-api` | **3.0** | **2 GB** | `eclipse-temurin:21-jre` (OpenJDK 21.0.12+8), JVM `-Xms1g -Xmx1g` |
| `mysql` | **2.0** | **2 GB** | `mysql:8.0` (실제 8.0.46, aarch64), `innodb_buffer_pool_size=1G` |
| `redis-master` / `redis-readonly` | 제한 없음 | 제한 없음 | `redis:7.0` (7.0.15) — 주문 경로 미사용, 부팅용 |
| **합계 (앱+DB)** | **5.0** | **4 GB** | VM 할당 안에 들어간다 |

부하 도구 k6(v2.1.0)는 **호스트에서** 돌린다. 컨테이너에 넣으면 측정 대상과 VM 자원을 다툰다.

`docker/loadtest-compose.yml` 이 이 배분을 소유하고, `loadtest/README.md` 에 절차가 있다.

#### 자원 한도는 반드시 눈으로 확인한다

Compose 에서 `deploy.resources.limits` 는 **Swarm 전용이라 `docker compose up` 에서 조용히 무시된다.**
에러도 경고도 나지 않으므로 "3코어로 제한했다" 고 믿은 채 5코어를 다 쓸 수 있다.
최상위 서비스 키(`cpus`, `mem_limit`)로 줘야 실제로 걸리며, 기동 후 확인해야 한다.

```bash
$ docker inspect loopers-loadtest-commerce-api-1 \
    --format '{{.HostConfig.NanoCpus}} {{.HostConfig.Memory}}'
3000000000 2147483648      # 3.0 CPU / 2 GiB — 실제로 걸렸다
```

JVM 쪽에서도 교차 확인된다 — `java -XshowSettings:system` 이 `Effective CPU Count: 3`,
`CPU Quota: 300000us / CPU Period: 100000us` 를 보고한다(cgroup v2 인식).

부수적으로 하나 더 드러났다. `mem_limit: 2g` 만 주면 Docker 가 **swap 을 메모리의 2배로 자동 설정**한다
(`MemorySwap=4294967296`). "2GB 제한" 이 실제로는 "RAM 2GB + swap 2GB" 였다. 힙을 1g 로 고정해
이번 측정에는 영향이 없었지만, 메모리 압박을 재는 실험이었다면 이 기본값이 결과를 조용히 바꿨을 것이다.

**절대 수치는 이 환경의 것이지 프로덕션 용량이 아니다.**
이 문서가 신뢰하는 것은 절대값이 아니라 **같은 조건에서 잰 개선 전후의 상대 변화**다.

### 3.2 도착률을 고정하는 이유

VU 고정 방식(`constant-vus`)을 쓰지 않는다. 서버가 느려지면 부하도 함께 줄어들어
"요청이 얼마나 들어왔을 때 무너지는가" 를 볼 수 없기 때문이다. **도착률을 고정해야 한계가 드러난다.**

### 3.3 시드 재고로는 부하 테스트가 성립하지 않는다

`LocalDataSeeder` 의 재고 총합은 **6,850개**다. 상품 137개 중 12개가 재고 0 이고,
나머지는 `((index % 10) + 1) * 10` 으로 10~100 이다.

500 TPS 로 1개씩 주문하면 **13.7초 만에 전 재고가 소진**되고, 그 뒤로는 전부 409 다.
그 상태에서 재는 것은 "409 를 얼마나 빨리 뱉는가" 이지 주문 처리량이 아니다.

측정 직전에 `UPDATE products SET stock = 100000000` 으로 재고를 주입해 해결했다.
**시더를 고치지 않은 것은 의도다** — 시더의 재고 분포는 `.http` 로 품절 409 를 확인하기 위한 것이라
(2026-08-24 문서 9 장) 부하 테스트 사정으로 바꾸면 그 목적이 깨진다.

### 3.4 두 시나리오를 나누는 이유

**상품 카디널리티가 결과를 지배한다.** 같은 API 인데 상한이 갈린다 —
1 차 환경에서는 5.5배(377 vs 2,075), 2 차 환경에서는 1.8배(708 vs 약 1,200)였다.
배수가 줄어든 것은 앱 CPU 를 3코어로 묶으면서 분산 시나리오의 제약이 커넥션 풀 위로 올라왔기 때문으로 보인다(12.7 장).

| 시나리오 | 상품 선택 | 무엇이 병목인가 |
|---|---|---|
| **핫스팟** | 항상 `productId = 1` | 단일 행의 배타 락 직렬화 |
| **분산** | 137개 중 랜덤 | 커넥션 풀 고갈 |

한쪽만 재면 절반의 그림만 본다. 핫딜 상품에 트래픽이 몰리는 상황이 핫스팟이고,
평상시 트래픽이 분산이다. **둘 다 실재하는 부하 형태다.**

### 3.5 A/B 비교의 조건 통일

개선 전후를 같은 조건에서 재기 위해 매 측정마다 다음을 맞췄다.

- 앱 재기동 (`ddl-auto: create` 라 스키마와 데이터가 새로 만들어진다 — 누적 행 수 0 에서 출발)
- 재고 주입
- `performance_schema.events_statements_summary_by_digest` 초기화
  — ⚠️ **k6 실행 직전에 했다. 그래서 워밍업이 digest 창 안으로 들어왔다**(5.1 장). 워밍업 직후로 옮겨야 한다.
- **동일한 k6 스크립트** (`ab.js`) — 2 차부터 저장소에 보존한다

#### 조건 통일을 "확인" 으로 강제한다

1 차에서는 위 항목을 절차로만 지켰다. 2 차에서 실제로 지켜지는지 검사해 봤더니 **세 번이나 깨져 있었다.**
그래서 러너가 매 측정 전에 다음을 확인하고, 하나라도 어긋나면 그 측정을 버린다.

| 확인 | 왜 필요한가 |
|---|---|
| `SELECT COUNT(*) FROM products` = 137 **AND** `COUNT(*) FROM orders` = 0 | 아래 두 함정 참고 |
| `SELECT MIN(stock) FROM products` = 100000000 | 재고 주입이 실제로 됐는가 |
| 측정 후 409 = 0 | 재고가 중간에 소진되지 않았는가 |
| 측정 후 `dropped_iterations` = 0 — **포화 이전 구간에 한해서** | 아래 "이 가드는 틀렸다" 참고 |

**함정 1 — actuator health 는 시딩 완료를 뜻하지 않는다.** 웹 서버가 `ApplicationRunner`(`LocalDataSeeder`)
보다 먼저 뜨므로, health UP 을 보고 재고를 주입하면 시더가 뒤이어 넣는 상품(11개마다 재고 0)이
주입을 피해 간다. 실제로 그 상품들만 409 를 뱉었다.

**함정 2 — "상품 137개" 만으로는 새 스키마임을 특정하지 못한다.** 이전 측정이 남긴 옛 스키마에도
상품은 137개 있어서, 앱이 테이블을 drop 하기 전에 조건이 참이 되어 옛 테이블에 주입해 버린다.
`orders = 0` 을 함께 봐야 한다.

> **"준비됐는가" 를 판정하는 조건이 이전 상태에서도 참일 수 있다면, 그건 판정이 아니다.**

#### 이 가드는 틀렸다 — `dropped_iterations = 0` 은 포화 구간에 요구할 수 없다

위 표의 마지막 줄은 측정을 시작하며 세운 것인데, 저장된 결과에 실제로 적용해 보면
**이 문서의 대표 수치 두 개가 모두 걸린다.**

| 측정 | 목표 | 달성 | `dropped_iterations` |
|---|---|---|---|
| `hotspot-after-800` | 800 | 800.0 | 0 |
| **`hotspot-before-800` — 개선 전 상한 708** | 800 | 708.0 | **4,840** |
| **`hotspot-after-1000` — 개선 후 상한 887** | 1,000 | 887.0 | **5,773** |
| `spread-after-1400` | 1,400 | 1,008.2 | **17,703** |

가드가 아니라 가드의 전제가 틀렸다. `dropped_iterations` 는 하네스 결함 신호가 아니라
**도착률 부족분 그 자체**다. 기대 요청 수(목표 TPS × 55 초 — 워밍업 10 초 + 측정 45 초)에서
실제 요청 수를 빼면
대부분 오차 ±2 로 `dropped_iterations` 와 같다.

```
hotspot-before-800   기대 44,000 − 실제 39,161 = 4,839      dropped 4,840
spread-before-1400   기대 77,000 − 실제 68,103 = 8,897      dropped 8,899
```

서버가 포화하면 응답이 늦어져 VU 가 제때 회수되지 않고, k6 는 다음 반복을 건너뛴다.
즉 **"달성 TPS < 목표 TPS" 와 "dropped > 0" 은 같은 사건을 두 번 말한 것**이다.
저장된 25 개 측정에서 달성 = 목표인 것과 `dropped = 0` 인 것이 예외 없이 일치했다.
그런데 상한을 재려면 반드시 포화시켜야 한다. **포화시킨 뒤 드롭이 없기를 요구하는 것은
모순이며, 그대로 지켰다면 상한을 하나도 재지 못했을 것이다.**

그래서 가드를 두 갈래로 나눈다.

| 구간 | 판정 |
|---|---|
| **포화 이전** (달성 = 목표) | `dropped = 0` 이어야 한다. 목표를 채웠는데 드롭이 있다면 계측이 어긋난 것이다 |
| **포화 이후** (달성 < 목표) | 드롭은 정상이다. 대신 **VU 여유**를 본다 — 필요 동시성(달성 TPS × 평균 응답 시간)이 `maxVUs` 아래인가. 넘으면 서버가 아니라 하네스를 잰 것이다 |

바뀐 기준으로 대표 수치를 다시 판정하면 둘 다 유효하다.

| 측정 | 달성 × 평균 = 필요 VU | `maxVUs` | 판정 |
|---|---|---|---|
| `hotspot-before-800` | 708.0 × 5,815ms ≈ **4,117** | 8,000 | 여유 있음 — 서버 한계 |
| `hotspot-after-1000` | 887.0 × 5,896ms ≈ **5,230** | 10,000 | 여유 있음 — 서버 한계 |

> **"이상적인 상태" 를 가드로 만들면 정작 재야 하는 상태가 전부 걸린다.**
> 가드는 무엇이 정상인지가 아니라 **무엇이 오염인지**를 물어야 한다.

#### `show-sql` 을 켠 채로 재면 로깅 처리량을 잰다

`local` 프로필은 `spring.jpa.show-sql=true` 다. 주문 1건이 쿼리 6~7개이므로 1,000 TPS 면
초당 7,000 줄이 Docker 의 json-file 로그 드라이버를 거쳐 디스크까지 간다.

| 핫스팟 600 TPS | 달성 TPS | p50 |
|---|---|---|
| `show-sql: true` | 593.5 | **624.7ms** |
| `show-sql: false` | 600.0 | **16.5ms** |

그래서 `loadtest-compose.yml` 이 `--spring.jpa.show-sql=false` 로 덮어쓴다.

단, 이 비교는 단일 변수 A/B 가 아니다 — 두 측정 사이에 k6 의 `preAllocatedVUs` 도 함께 올렸다.
누락된 반복은 요청을 만들지 않아 지연 지표에 들어가지 않으므로 VU 설정이 38배 차이를 만들 수는 없지만,
**이 표는 방향의 근거이지 정확한 배수의 근거가 아니다.**

## 4. 병목 특정 — 제약 스택

처리량 목표를 먼저 정하면 순서가 거꾸로다. **시스템의 제약을 먼저 그려야** 어느 구간을 재야 할지 나온다.

```
톰캣 워커 스레드 200        ← 여유 (병목 아님)
        ↓
HikariCP 커넥션 40          ← 분산 시나리오의 상한
        ↓
MySQL InnoDB 행 락          ← 핫스팟 시나리오의 상한
```

### 4.1 톰캣이 병목이 아닌 이유

워커 200 개가 커넥션 40 개를 두고 경쟁한다. 즉 **커넥션을 얻지 못한 160 개는 대기**한다.
`connection-timeout: 3000ms` 이므로 3초 안에 얻지 못하면 예외가 난다.
병목은 스레드가 아니라 그 아래 커넥션이다.

### 4.2 커넥션 풀이 상한이라는 증거 (1 차 환경)

> ⚠️ 이 절과 4.3 절의 근거는 **1 차 측정(앱 호스트) 에서 나온 것이다.**
> 2 차 환경에서는 `Threads_connected` / `Threads_running` 을 다시 관측하지 않았으므로,
> **분산 시나리오의 상한이 2 차에서도 커넥션 풀이라고 단정할 수 없다.** 12.7 장 참고.

부하 중 MySQL 을 관측했다.

| 구간 | `Threads_connected` | `Threads_running` |
|---|---|---|
| 저부하 (~600 TPS) | 39 | **2~3** |
| 고부하 (2,000+ TPS) | 41 | **최대 39** |

저부하에서 커넥션은 39개나 열려 있는데 실제로 쿼리를 실행하는 스레드는 2~3개다.
**조건부 `UPDATE` 가 워낙 짧아 DB 가 놀고 있다는 뜻**이고, 이 구간에서 DB 를 튜닝하는 것은 헛수고다.

고부하에서 `Threads_running` 이 39 까지 올라간다. 풀 크기 40 과 일치한다.
**커넥션 풀이 분산 시나리오의 상한이라는 직접 증거다.**

### 4.3 리틀의 법칙으로 검증 (1 차 환경)

단일 요청 baseline (워밍업 후 VU 1개) 은 median **4.28ms**, p99 7.01ms 였다.

```
TPS = 동시 처리 수 ÷ 응답 시간
    = 커넥션 40 ÷ 서비스 시간 20ms
    = 2,000 TPS
```

실측 분산 상한이 2,075 TPS 였다. **계산과 실측이 일치한다.**
baseline 4.28ms 가 포화 시 20ms 로 늘어난 것은 DB 내부 경합 때문이며, `Threads_running=39` 가 그 증거다.

## 5. 락 보유 구간의 분해

2 차 측정의 핫스팟 상한 708 TPS 를 역산하면 락 보유 시간이 나온다.

```
1 ÷ 708 TPS ≈ 1.41ms   ← products 한 행이 잠겨 있는 시간
```

같은 상품을 사려는 모든 트랜잭션이 이 창구에 한 줄로 선다. 그렇다면 그 1.41ms 안에 무엇이 들어 있는가.
`performance_schema` 로 분해했다 (개선 전 jar, 핫스팟 300 TPS).

> ⚠️ **이 표의 평균은 워밍업을 포함한 값이다.** digest 창이 k6 실행 전체 — 워밍업 5 초 +
> 측정 30 초 — 를 덮는다. 호출 수 10,501 이 그 증거다(300 TPS × 35 초). 측정 구간만의
> 요청 수는 9,001 이다. 콜드스타트가 섞여 있으므로 **절대값을 정상 상태의 성질로 읽으면 안 된다**
> (5.1 장). 아래 표는 그 한계를 안고 읽는다.
>
> 워밍업이 5 초인 것은 이 분해 전용 실행이라서다 — 8.1 장의 A/B 측정은 10 초를 썼다.

| 쿼리 | 호출 수 | 평균 | 락 구간 안인가 |
|---|---|---|---|
| `UPDATE products SET stock` | 10,501 | 9.983ms | 락 **획득** |
| `INSERT orders` | 10,501 | 0.070ms | **예** |
| `INSERT order_items` | 10,501 | 0.068ms | **예** |
| `UPDATE order_items SET order_id` | 10,501 | 0.045ms | **예** |
| `COMMIT` | 10,501 | 1.084ms | **예** (커밋 완료 시 락 해제) |
| `SELECT products` | 10,500 | 0.060ms | 아니오 |
| `SELECT users` | 10,498 | 0.073ms | 아니오 |

시간순으로 그리면 이렇다.

```
UPDATE products (락 획득) ─┐
  INSERT orders              0.070ms
  INSERT order_items         0.068ms   } 코드로 걷어낼 수 있는 구간 = 0.183ms
  UPDATE order_items(FK)     0.045ms
  COMMIT                     1.084ms   ← 락 안에서 잰 것들(1.267ms)의 86%
(락 해제) ─────────────────┘
```

역산한 창구 1.41ms 와 락 안에서 실제로 잰 합 1.267ms 의 차이는 측정에 잡히지 않는 구간
(네트워크 왕복, 커넥션 반납 등)이다. 어느 쪽을 분모로 잡든 결론은 같다 —
**코드로 걷어낼 수 있는 것은 0.183ms 뿐이고 나머지는 커밋이다.**

단, **두 값이 가깝다는 것을 근거로 삼지 않는다.** 1.41ms 는 포화 측정(800 TPS 목표)의 역산이고
1.267ms 는 300 TPS 실행의 digest 평균이라 서로 다른 창에서 나왔다. 게다가 뒤쪽은 워밍업에
오염돼 있다. 가까운 것은 우연일 수 있다.

> 1 차 환경에서는 같은 분해가 락 창구 2.7ms, 걷어낼 구간 0.361ms, `COMMIT` 5.145ms(93%) 였다.
> `COMMIT` 이 5.145ms 에서 1.084ms 로 줄어든 것이 2 차의 상한이 높은 주된 이유로 보인다 —
> 앱이 MySQL 과 같은 브리지 네트워크에 들어오면서 왕복이 짧아졌다.

### 5.1 `UPDATE products` 의 9.983ms 는 워밍업이 만든 값이다

같은 실행의 k6 지표와 나란히 놓으면 이 숫자는 성립할 수 없다.

| 창 | 요청 수 | avg | med | p95 |
|---|---|---|---|---|
| 측정 구간 (30 초) | 9,001 | **4.52ms** | 3.28ms | 11.0ms |
| 워밍업 포함 (35 초) | 10,501 | **28.58ms** | 3.55ms | 260.2ms |

(`max` 는 싣지 않는다 — 12.9 장.) 중앙값은 3.28 → 3.55ms 로 거의 움직이지 않는데 평균만
4.52 → 28.58ms 로 뛴다. **워밍업의 소수 요청이 만든 꼬리**라는 뜻이다.

**요청 하나가 통째로 평균 4.52ms 인데 그 안의 쿼리 하나가 9.983ms 일 수는 없다.**
그러므로 이 값은 측정 구간의 성질이 아니다. digest 창이 워밍업 5 초를 함께 덮고 있고,
그 구간을 포함한 평균이 28.58ms 다. 호출 수 10,501 이 9,001 이 아니라는 것이 창을 특정해 준다.

오염이 **균일하지 않다**는 점이 원인을 좁힌다. 같은 창에서 `INSERT orders` 는 0.070ms 인데
`UPDATE products` 만 140 배다. 경합하지 않는 쿼리는 멀쩡하고 **단일 행을 두고 다투는 쿼리만
튀었다.** 콜드스타트로 앱이 느려지면 `UPDATE` 와 `COMMIT` 사이가 길어지고, 그만큼 락을 오래 쥐어
뒤따르는 트랜잭션이 락 대기에 쌓인다. 락 대기를 포함한 값이라는 해석 자체는 맞지만,
**그 대기는 300 TPS 정상 상태가 아니라 워밍업이 만든 것이다.**

이 인과는 **추정이다.** 확정하려면 워밍업 구간과 측정 구간의 digest 를 나눠 떠야 한다.
1 차 환경에서 근거로 삼았던 `Innodb_row_lock_waits = 85,900`, `Innodb_row_lock_time_avg = 46ms`
도 같은 약점을 안고 있다 — 기동 이후를 통째로 누적한 상태 변수라 특정 구간의 성질이 아니다.

#### 이 오염이 어디까지 번지는가

같은 표에서 나온 값이므로 아래 결론들이 이 창을 물려받는다. 무엇이 남고 무엇이 약해지는지 적어 둔다.

| 값 | 쓰이는 곳 | 영향 |
|---|---|---|
| 걷어낼 구간 **0.183ms** | 1 장 · 9 장의 "13%" | 경합하지 않는 INSERT 라 오염이 작다 — 방향은 유지된다 |
| `COMMIT` **1.084ms** (86%) | 11.1 장 · 12.6 장 "다음 병목은 커밋" | **과대평가일 수 있다** — 근거 강도가 본문 서술보다 약하다 |
| `UPDATE products` **9.983ms** | 5.1 장 | 정상 상태 값이 아니다 |

**개선 자체의 근거는 흔들리지 않는다.** 상한 +25.3% 와 `UPDATE order_items` 소멸(8.2 장)은
digest 의 평균이 아니라 A/B 달성 TPS 와 호출 수에서 나왔고, 그 둘은 이 오염과 무관하다.
흔들리는 것은 **락 구간을 시간으로 쪼갠 이 표의 절대값**이다.

#### 고치는 법

`performance_schema` 초기화를 측정 직전이 아니라 **워밍업 직후**로 옮기면 된다.
지금 절차는 앱 기동 → 재고 주입 → digest 초기화 → k6 실행(워밍업 + 측정)이라
워밍업이 창 안으로 들어온다(3.5 장).

> 8.4 장은 1 차 측정에서 "부하 조건이 다른 통계를 섞지 마라" 고 적었다.
> **2 차에서 같은 실수가 형태만 바꿔 재발했다** — 이번에는 TPS 가 아니라 시간 창이 섞였다.

### 5.2 세어 본 적 없는 쿼리가 하나 있었다

`UPDATE order_items SET order_id = ? WHERE id = ?` 는 우리가 작성한 쿼리가 아니다.

`OrderModel` 이 단방향 `@OneToMany` + `@JoinColumn` 으로 `OrderItemModel` 을 소유했기 때문에,
Hibernate 가 **자식을 `order_id` 없이 INSERT 한 뒤 FK 를 채우는 UPDATE 를 따로 발행**했다.
자식이 부모를 모르는 채로 저장을 시작하므로 생기는 일이다.

주문 1건당 낭비 쿼리 1개가 **락을 쥔 채로** 실행되고 있었다.

## 6. 개선 A — 주문 저장을 재고 차감 앞으로 옮긴다

### 6.1 무엇을 바꾸는가

```
변경 전:  쿠폰 소모 → 재고 차감 → 주문 저장 → COMMIT
변경 후:  쿠폰 소모 → 주문 저장 → 재고 차감 → COMMIT
```

락은 재고 차감에서 잡히고 커밋에서 풀린다. 주문 저장을 앞으로 빼면 **INSERT 3건이 락 구간 밖으로 나간다.**

### 6.2 정합성은 그대로다

재고 차감이 실패하면 `CoreException` 이 트랜잭션 전체를 롤백시킨다. 주문 행도 항목 행도 남지 않는다.
`@Transactional` 의 기본 동작이며, 2026-08-24 문서 6.8 장이 "주문은 예외를 흡수하지 않는다" 고
정한 그 성질을 그대로 쓴다.

### 6.3 `OrderInfo` 변환을 차감보다 먼저 하는 이유

**이것이 이 변경에서 가장 위험한 지점이다.**

`ProductJpaRepository.decreaseStock` 은 `@Modifying(clearAutomatically = true, flushAutomatically = true)` 다.
호출될 때마다 **영속성 컨텍스트를 통째로 비운다.** 주문을 먼저 저장하면 방금 저장한 `OrderModel` 이
그 `clear()` 로 detach 되고, 그 뒤에 `order.items` 를 읽으면 컬렉션 초기화 여부에 따라 깨질 수 있다.

그래서 순서가 이렇게 된다.

```kotlin
val order = orderService.place(...)   // 주문 저장
val orderInfo = OrderInfo.of(order)   // ★ 차감 전에 변환을 끝낸다
sorted.forEach { decreaseStock(...) } // 여기서 영속성 컨텍스트가 비워진다
return orderInfo
```

"변환은 마지막에 하는 것이 자연스럽다" 며 이 순서를 되돌리면 **조용히 깨진다.**
코드에도 같은 경고를 주석으로 남겼다.

### 6.4 롤백이 처음으로 진짜 방어선이 되었다

변경 전에는 재고 차감이 먼저라 실패하면 **주문 저장에 도달조차 하지 않았다.** 롤백은 형식적이었다.
변경 후에는 이미 INSERT 된 주문 행을 **롤백이 실제로 걷어내야 한다.**

즉 이 변경은 새로운 위험을 만든다. 그래서 `OrderFacadeIntegrationTest` 의 롤백 테스트에
주문 행 수 단언을 추가했다 (10.2 장). 이 단언이 없으면 그 회귀를 잡을 테스트가 남지 않는다.

## 7. 개선 B — `order_items` 의 FK 소유권을 자식으로 옮긴다

### 7.1 무엇을 바꾸는가

```kotlin
// OrderItemModel — FK 소유자가 된다
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "order_id", nullable = false)
lateinit var order: OrderModel
    protected set

// OrderModel — 매핑의 주인 자리를 넘긴다
@OneToMany(mappedBy = "order", cascade = [CascadeType.ALL], orphanRemoval = true, fetch = FetchType.LAZY)
private val orderItems: MutableList<OrderItemModel> = items.toMutableList()
```

`OrderModel.init` 끝에서 `orderItems.forEach { it.assignOrder(this) }` 로 연관을 맺는다.
검증(`BAD_REQUEST`) 이후에 두어, 빈 항목이나 잘못된 회원 ID 로 실패하는 경로에서는 순회하지 않는다.

이렇게 하면 INSERT 문에 `order_id` 가 바로 실려 **뒤따르던 UPDATE 가 사라진다.**

### 7.2 애그리거트 경계는 바뀌지 않는다

`OrderItemModel` 은 여전히 `OrderModel` 의 내부 구성요소다. 2026-08-24 문서 5.2 장의 판단
— "다른 애그리거트가 아니라 이 애그리거트의 부품" — 이 그대로 유효하다.

바뀐 것은 **어느 쪽이 FK 컬럼을 소유한다고 JPA 에 선언하는가** 뿐이다.
생명주기는 여전히 `OrderModel` 이 `cascade = ALL` + `orphanRemoval` 로 지배하고,
`order_items` 를 독립적으로 조회하는 경로는 만들지 않았다.

### 7.3 캡슐화를 유지하는 장치

- `order` 의 세터는 `protected` 이고, `internal fun assignOrder(order)` 하나로만 채운다.
  항목이 생성 이후 다른 주문으로 옮겨갈 유스케이스가 없기 때문이다 — 이 연관은 조립 시점에 한 번만 맺힌다.
- Kotlin 에 package-private 이 없어 `internal` 이 낼 수 있는 가장 좁은 가시성이다.
- `data class` 로 만들지 않는다. `toString` / `equals` / `hashCode` 가 자동 생성되면
  `order` 를 되짚다 `order.items` 와 서로를 무한히 되풀이해 재귀에 빠진다.

### 7.4 QueryDSL fetch join 은 그대로 동작한다

`OrderQueryDslRepository.findById` 의 fetch join 은 수정하지 않았다.
Q-type 의 `orderItems` 필드가 `mappedBy` 여부와 무관하게 같은 형태로 생성되기 때문이다.

**분산은 상한을 단정하지 않는다.** 포화 구간의 달성 TPS 가 개선 전 1,030~1,284,
개선 후 1,008~1,176 사이에서 흔들린다. 1,400 TPS 를 개선 후로 두 번 쟀더니 1,112.9 와 1,008.2 로
갈렸다 — **한 번만 쟀다면 어느 쪽을 골랐든 그 숫자를 믿었을 것이다.**

포화 뒤의 처리량은 그 순간 큐에 무엇이 얼마나 쌓여 있었는지에 좌우되지 시스템의 능력이 아니다.
대신 무릎점은 분명하다 — **1,200 TPS 에서 p50 이 2,777ms 와 11.9ms 로 갈린다.**

### 8.2 개선 B 의 직접 증거

`performance_schema` 다이제스트를 개선 전후로 각각 잡았다
(핫스팟 300 TPS, 워밍업 5 초 + 측정 30 초 — 5 장과 같은 창이다).

여기서는 창이 넓어도 문제가 되지 않는다. **비교 대상이 평균이 아니라 호출 수**이고,
호출 수는 워밍업이 섞이든 아니든 "주문 1건이 쿼리 몇 개를 내는가" 를 그대로 말해주기 때문이다.

| 쿼리 | 개선 전 호출 수 | 개선 후 호출 수 |
|---|---|---|
| `UPDATE products SET stock` | 10,501 | 10,502 |
| `INSERT orders` | 10,501 | 10,499 |
| `INSERT order_items` | 10,501 | 10,501 |
| **`UPDATE order_items SET order_id`** | **10,501** | **0 — 사라짐** |
| `COMMIT` | 10,501 | 10,502 |
| **주문 1건당** | **7개** | **6개** |

### 8.3 1 차 측정 (앱 호스트 — 기록 보존)

앱을 호스트에서 `java -jar` 로 띄우고 MySQL 만 Docker 에 두었을 때의 결과다.
**2 차와 환경이 달라 같은 표에 놓고 비교할 수 없다.**

| 시나리오 | 개선 전 | 개선 후 | 변화 |
|---|---|---|---|
| 핫스팟 | 377 TPS | 589 TPS | +56% |
| 분산 | 2,075 TPS | 약 2,376 TPS | +14.5% |
| 핫스팟 400 TPS 의 p50 | 718.5ms | 4.8ms | -99.3% |

1 차에는 k6 스크립트가 저장소에 남지 않아 **재현할 수 없다.** 2 차부터 `loadtest/ab.js` 로 보존한다.

### 8.4 비교하면 안 되는 숫자

1 차에서 개선 후 `UPDATE products` 의 평균이 0.580ms 로 나왔지만, 개선 전의 9.002ms 와
직접 비교할 수 없었다. 9.002ms 는 최대 4,000 TPS 까지 밀어붙인 전체 스캔의 통계이고
0.580ms 는 `ab.js` 만의 통계라 부하 조건이 다르기 때문이다.

같은 이유로 **1 차와 2 차의 숫자를 섞어 쓰면 안 된다.** 신뢰할 근거는 8.1 의 A/B 표와
8.2 의 쿼리 소멸 두 가지이며, 둘 다 같은 환경 안에서 조건을 통일해 얻은 것이다.

## 9. 왜 예측보다 크게 개선됐는가

락 구간에서 걷어낸 것은 0.183ms 이고 전체 1.41ms 의 **13%** 다. 산술적으로는 708 → 813 TPS 정도여야 한다.
실제로는 **887 TPS (+25.3%)** 가 나왔다. 700 TPS 구간의 p50 은 8,331ms 에서 2.4ms 로 **3,471배** 좋아졌다.

두 환경이 같은 성질을 보였다는 점이 이 설명을 뒷받침한다. 1 차에서도 걷어낸 비율은 13%(0.361 / 2.7ms)
였는데 상한은 377 → 589 TPS(+56%)가 나왔다. **비율은 같고 효과는 달랐다** — 뒤에서 볼 이유 때문이다.

산술 계산이 틀린 이유는 **대기 시간이 이용률에 선형이 아니기 때문**이다.

```
평균 대기 시간 ∝ ρ / (1 - ρ)      (ρ = 이용률)

ρ = 0.95  →  대기 배수 19배
ρ = 0.80  →  대기 배수  4배
```

포화 직전 구간에서는 서비스 시간을 조금만 줄여도 ρ 가 임계점 아래로 내려가면서
**대기 시간이 비선형적으로 무너진다.** 개선 전 700 TPS 는 상한 708 을 코앞에 둔 과포화 상태였고,
개선 후에는 상한 887 아래의 여유 구간이 되었다. 그 차이가 8,331ms 와 2.4ms 다.

**동시성 최적화는 "얼마나 줄였나" 가 아니라 "임계점을 넘겼나" 로 평가해야 한다.**

같은 이유로, 임계점에서 먼 구간에서는 이 개선이 보이지 않는다. 400 TPS 에서 개선 전후가 똑같이
2.3ms 인 것이 그 증거다. **개선이 없어서가 아니라 그 구간에서는 잴 것이 없어서다.**

그리고 걷어낸 비율이 같은데(13%) 상한 증가가 1 차 +56%, 2 차 +25.3% 로 갈린 것도 같은 원리다.
1 차는 `COMMIT` 이 5.145ms 라 락 창구가 2.7ms 로 넓었고, 그 안에서 0.361ms 를 빼면 ρ 가 크게 떨어진다.
2 차는 창구가 1.41ms 로 이미 좁아 같은 13% 를 빼도 ρ 가 덜 움직인다.
**개선 효과는 코드가 아니라 코드와 환경의 조합이 정한다.**

### 9.1 두 시나리오의 개선 폭이 갈린 것이 병목 분석을 증명한다

| 시나리오 | 2 차 개선 | 1 차 개선 | 병목 |
|---|---|---|---|
| 핫스팟 | 상한 **+25.3%**, 700 TPS p50 **3,471배** | +56% | 락 보유 시간 → 락 구간 단축이 **직접** 작용 |
| 분산 | 상한 판정 불가, 1,200 TPS p50 **233배** | +14.5% | 커넥션 풀·CPU → 점유 시간이 줄어든 **간접** 효과 |

두 환경 모두에서 **핫스팟 쪽이 더 크게 개선됐다.** 락 구간을 줄였으니 락이 병목인 쪽이 더 좋아지는 것이
당연하고, 그 당연함이 관측된 것이 5 장 병목 분석이 맞았다는 증거다.

만약 측정 없이 "커넥션 풀을 늘리자" 로 갔다면 **핫스팟은 708 TPS 에 그대로 묶여 있었을 것이다.**
그쪽 병목은 커넥션이 아니라 락이기 때문이다. 병목을 먼저 특정한 것이 이 결과를 만들었다.

## 10. 테스트

### 10.1 기존 스위트가 회귀 방지선이다

이 작업은 동작을 바꾸지 않는다. 따라서 **기존 746건이 그대로 통과하는 것 자체가 검증**이다.
최종 **747건 전부 통과**했고(신규 1건 포함), 동시성 테스트 10건도 전부 통과했다.
**어떤 동시성 단언도 약화시키지 않았다.**

### 10.2 추가한 단언 — 롤백

`OrderFacadeIntegrationTest.throwsConflict_andRollsBackEverything_whenAnyStockIsInsufficient` 는
재고만 확인하고 주문 행 수를 세지 않았다. 6.4 장에서 적었듯 이 변경으로 롤백이 처음으로
진짜 방어선이 되었으므로, 주문 행이 남지 않았다는 단언을 추가했다.

### 10.3 바뀐 단위 테스트

`OrderFacadeTest` 의 세 건이 순서 변경의 영향을 받았다.

- `doesNotPlaceOrder_whenStockIsInsufficient` → `stillCallsOrderServicePlace_whenStockIsInsufficient`
  로 개명하고 단언을 뒤집었다. 이제 저장 호출 자체는 끝난 뒤에 재고 차감이 실패한다.
  **DB 에 남지 않는 것은 롤백 덕분이며, 목만 쓰는 단위 테스트는 롤백을 관찰할 수 없다.**
  그 보장은 10.2 의 통합 테스트가 진다.
- 나머지 두 건은 `orderService.place` 스텁을 추가했다. 스텁이 없으면 목이 `null` 을 돌려줘
  `OrderInfo.of` 에서 NPE 가 나고, 그 테스트의 원래 의도(CONFLICT 검증)가 가려진다.

### 10.4 새 계약을 고정한 테스트

`placesOrderBeforeDecreasingStock` 을 추가했다. `inOrder(orderService, productService)` 로
"주문 저장이 재고 차감보다 먼저" 를 단언한다.

**통합 테스트로는 이 순서를 관찰할 수 없다** — DB 최종 상태는 순서와 무관하게 같기 때문이다.
이 단위 테스트가 사실상 유일하게 이번 개선의 계약을 지킨다. 누군가 순서를 되돌리면 여기서 걸린다.

## 11. 하지 않은 것과 그 이유

### 11.1 인프라 병목을 건드리지 않는다

락 안에서 잰 1.267ms 중 **1.084ms(86%)가 `COMMIT`** 이고, 그 정체는 fsync 다
(1 차 환경에서는 5.145ms 로 93% 였다). `innodb_flush_log_at_trx_commit = 1` + `sync_binlog = 1`
+ `log_bin = ON` 이라 커밋마다 redo log 와 binlog 를 각각 디스크에 동기화한다.
Docker on macOS 에서 특히 느리다.

`innodb_flush_log_at_trx_commit = 2`, `sync_binlog = 0` 으로 바꾸면 처리량이 크게 오른다.
**그럼에도 하지 않는다.**

- 그것은 **내구성을 처리량과 맞바꾸는 결정**이다. 장애 시 커밋된 트랜잭션이 사라질 수 있고,
  주문 데이터에 대해 그 교환을 애플리케이션 레벨에서 임의로 할 수 없다.
- 이 값은 배포 환경마다 다르게 정해져야 하며, 로컬 측정값을 근거로 프로덕션 설정을 정하면 안 된다.
- **무엇보다 이 문서의 주제가 아니다.** 이번 과제는 애플리케이션 계층의 트랜잭션 처리이고,
  fsync 튜닝으로 얻는 숫자는 우리가 짠 코드의 성질을 말해주지 않는다.

측정 환경 보정 목적으로도 쓰지 않았다. 보정하면 코드 개선 효과가 더 선명하게 보였겠지만,
**보정 없이도 상한이 +25.3% 나왔으므로 필요가 없었다**(1 차에서도 마찬가지로 +56% 가 나왔다).

### 11.2 낙관적 락 · 비관적 락을 쓰지 않는다

조건부 `UPDATE` 를 유지한다. 이것은 판정과 갱신을 한 문장에 합쳐 read-check-write 틈 자체를 없애며,
낙관적 락과 달리 재시도가 없고 비관적 락과 달리 `SELECT ... FOR UPDATE` 왕복이 없다.

이번 측정이 그 선택을 뒷받침한다. **락 보유 시간이 짧다는 것이 처리량의 근거였고,
왕복을 하나 더 두는 방식이었다면 이 숫자가 나오지 않는다.**

### 11.3 커넥션 풀을 늘리지 않는다

분산 시나리오의 상한은 커넥션 40 이다(4.2 장). `maximum-pool-size` 를 올리면 그 상한이 올라간다.
하지만 이 값은 `modules/jpa` 에 있어 세 앱이 공유하고, DB 코어 수를 넘는 커넥션은
컨텍스트 스위칭만 늘린다. **측정 없이 올릴 값이 아니며, 올리려면 MySQL 쪽 용량 산정이 먼저다.**

## 12. 위험과 한계

### 12.1 절대 수치는 이 환경의 것이다

앱 3코어 · MySQL 2코어로 묶은 노트북 위 Docker 의 숫자다. 708 TPS 와 887 TPS 는 프로덕션 용량이 아니다.
**의미가 있는 것은 같은 조건에서 잰 전후 비율이다.**

### 12.2 쿠폰 경로는 측정하지 않았다

부하 스크립트가 `couponId` 를 보내지 않는다. 쿠폰은 1인 1매 · 1회 사용이라 두 번째 요청부터
409 가 나 지속 부하를 걸 수 없기 때문이다. **`user_coupons` 의 조건부 `UPDATE` 가
처리량에 어떤 영향을 주는지는 이 문서가 답하지 않는다.**

측정하려면 회원과 쿠폰을 요청 수만큼 미리 발급해 두는 준비 단계가 필요하다.

### 12.3 락 대기가 에러로 드러나지 않는다

1 차에서는 핫스팟 800 TPS 에서 p95 가 2.48초인데 **비200 응답이 0건**이었다.
2 차에서는 더 선명하게 드러났다 — 분산 1,400 TPS 의 p95 가 정확히 **59,999ms**, k6 의 기본 HTTP
타임아웃 60초였다. 서버가 에러를 반환한 것이 아니라 **요청이 큐에 쌓인 채 클라이언트가 먼저 포기**했다.
커넥션은 이미 쥔 채로 락을 기다리므로 `connection-timeout: 3000ms` 에 걸리지 않고,
`innodb_lock_wait_timeout` 은 50초라 여유롭기 때문이다.

**서버 지표만 보면 "에러 0%, 정상" 인데 실제 클라이언트는 타임아웃으로 전부 실패한다.**
부하 테스트의 임계값에는 에러율뿐 아니라 반드시 **응답 시간 기준**을 함께 넣어야 한다.

### 12.4 `lateinit var order` 는 조립 전에 읽으면 터진다

`OrderItemModel.create` 로 만든 직후부터 `OrderModel` 이 `assignOrder` 를 부르기 전까지
`order` 는 초기화되지 않은 상태다. 그 사이에 읽으면 `UninitializedPropertyAccessException` 이 난다.

현재는 `OrderModel.create` 가 즉시 조립하므로 그 틈이 없지만,
**`OrderItemModel` 을 주문 밖에서 단독으로 다루는 코드가 생기면 이 전제가 깨진다.**

### 12.5 `init` 블록에서 `this` 가 새어 나간다

`OrderModel.init` 이 `orderItems.forEach { it.assignOrder(this) }` 를 부를 때
아직 완전히 초기화되지 않은 `this` 가 자식에게 전달된다. JPA 양방향 연관관계 편의 메서드의
표준적인 패턴이지만, **`init` 블록 끝에 두어 다른 필드 초기화가 모두 끝난 뒤에 실행되도록** 순서를 잡았다.
이 호출을 위로 옮기면 자식이 미완성 부모를 보게 된다.

### 12.6 다음 병목은 커밋이다

락 구간에서 코드로 걷어낼 수 있는 것은 이번에 다 걷어냈다. 남은 것은 `COMMIT` 하나이며(11.1 장),
그것은 애플리케이션 코드가 아니라 배포 환경이 결정한다.
**이 방향으로 더 가려면 다음 개선은 코드가 아니라 인프라 결정이다.**

> ⚠️ **이 결론에는 전제가 있다 — "주문 항목이 1 개" 다.** `ab.js` 가 항상 항목 1 개짜리 주문만
> 보냈기 때문에(12.11 장), 항목이 여러 개일 때 차감이 상품 수만큼 반복되며 그 왕복이 전부 락 구간
> 안에서 일어난다는 사실이 측정에 잡히지 않았다. **코드로 걷어낼 것이 아직 남아 있다** —
> [2026-09-09 재고 차감 락 전략의 처리량 비교](2026-09-09-lock-strategy-throughput-design.md) —
> **11.2 장이 재 보지 않고 정한 락 전략을 세 방식 다 구현해 실측 비교**한다. 이 결론의 전제
> (항목 1 개)를 열어 다중 항목 축에서도 잰다.
>
> 왕복을 더 줄이는 개선은
> [2026-09-11 재고 차감 단일 문장화 설계](2026-09-11-batch-stock-decrease-design.md)로 분리돼
> **비교가 끝난 뒤**에 착수한다. 특정 전략에만 적용되는 최적화라 비교보다 먼저 하면
> 공정성이 깨지기 때문이다.
>
> 인프라 쪽도 한 가지 덧붙인다. 11.1 장이 배제한 것은 **내구성을 처리량과 맞바꾸는** 설정이다.
> `binlog_group_commit_sync_delay` 처럼 `sync_binlog = 1` 을 유지한 채 fsync 횟수만 줄이는 방법은
> 그 배제 사유에 해당하지 않는다 — 지연과 처리량을 맞바꾸는 것이지 내구성을 내주는 것이 아니다.
> 이번 범위에서 다루지 않았을 뿐이다.

### 12.7 환경이 바뀌면 병목도 바뀐다

같은 코드인데 1 차(앱 호스트)와 2 차(앱 컨테이너)의 핫스팟 상한이 377 과 708 로 갈렸다.
앱이 MySQL 과 같은 브리지 네트워크에 들어오면서 DB 왕복이 짧아졌고, `COMMIT` 이 5.145ms 에서
1.084ms 로 줄면서 락 보유 시간도 함께 짧아졌기 때문이다.

분산 쪽은 반대로 움직였다. 1 차에서는 분산 상한이 핫스팟의 5.5배(2,075 vs 377)였는데
2 차에서는 1.8배(약 1,200 vs 708)에 그친다. 앱 CPU 를 3코어로 묶으면서
**분산 시나리오의 제약이 커넥션 풀(40) 위로 올라온 것으로 보인다.** 다만 2 차에서
`Threads_running` 을 다시 관측하지 않았으므로 **이것은 관측이 아니라 추정이다.**
확인하려면 4.2 장과 같은 방식으로 다시 재야 한다.

### 12.8 부하 도구에도 상한이 있다

호스트 k6 → Docker published port → 톰캣 경로 자체의 한계를 먼저 쟀다.
DB 를 타지 않는 404 경로로 3,500 TPS 를 p95 2.56ms 에 소화했고, 8,000 TPS 를 목표로 걸었을 때
3,817 TPS 에서 포화했다.

측정 구간(핫스팟 ~887, 분산 ~1,200)보다 충분히 위여서 이번 결과를 왜곡하지는 않았다.
**하지만 측정값이 3,500 근처로 나온다면 그것은 서버가 아니라 하네스를 잰 것이다.**

### 12.9 k6 의 `max` 지표를 신뢰하지 않는다

k6 v2.1.0 에서 `http_req_duration` 의 `max` 가 **924,012ms(924초)** 로 찍혔다.
같은 실행의 `iteration_duration` `max` 는 1,650ms 였다. 반복 하나가 요청 하나를 담으므로
요청 시간이 반복 시간보다 클 수 없다 — **이 `max` 는 오염된 값이다.**

반대로 백분위수는 두 지표가 교차 검증됐다(`http_req_duration` p95 1,216.7ms ≈
`iteration_duration` p95 1,216.8ms). 그래서 이 문서는 **`max` 를 보고하지 않고 p50 / p95 만 쓴다.**

> 도구가 내놓은 숫자도 서로 모순되는지 대조해야 한다. 한 지표만 보면 검증할 방법이 없다.

### 12.10 분산 시나리오의 상한은 아직 모른다

8.1 장에 적었듯 포화 구간의 달성 TPS 가 반복마다 흔들려 상한을 정할 수 없었다.
무릎점(1,200 TPS)만으로 개선을 말했으므로, **분산 쪽 개선 폭을 수치로 주장하지 않는다.**

정하려면 같은 지점을 여러 번 재서 분포를 봐야 한다. 이번에는 1,400 TPS 를 두 번 잰 것이 전부다.

### 12.11 부하 스크립트가 항목 1 개만 보냈다

`ab.js` 는 `items: [{ productId, quantity: 1 }]` 로 고정이다. 따라서 이 문서의 모든 상한은
**주문 항목이 1 개일 때의 값**이며, 다중 항목 주문의 처리량은 이 문서가 답하지 않는다.

> **부하 스크립트가 만들지 않는 형태의 요청은 그 시스템에 존재하지 않는 것과 같다.**
> 측정하지 않은 축은 자동으로 최선의 값으로 보고된다.
