- 작성일: 2026-09-28
- 대상 모듈: `apps/commerce-batch` (이 프로젝트에서 처음으로 commerce-api 밖에 새 코드를 둔다 — 2.3 장)
- 상태: **구현 완료 (2026-10-02)** — 계획은 [plans/2026-09-28-like-count-reconcile.md](../plans/2026-09-28-like-count-reconcile.md)
- 선행 문서:
  - [2026-08-20 상품 좋아요 API 설계](2026-08-20-product-like-design.md) — `like_count` 증감 경로(6.4 장), "보정 배치는 두지 않는다"는 원래 결정(2 장 제외 표, 11.3 장), 시드 불일치(11.2 장), `product_id` 인덱스 부재(11.7 장)
  - [2026-09-16 상품 목록 인덱스 설계](2026-09-16-product-list-index-design.md) — 합성 `like_count` 를 심은 10 만 건 측정 시드의 출처

## 이 문서가 답하려는 것

> **`products.like_count` 가 실제 좋아요 행 수와 어긋났을 때, 운영 중인 좋아요 트래픽을 막지 않고
> 틀린 값을 새로 만들지도 않으면서 어떻게 되돌리는가.**

2026-08-20 설계는 정합성을 "같은 트랜잭션 안" 에서만 보장하고, 사후 검증·복구 수단은 두지 않기로 했다(11.3 장).
그 결정의 대가도 문서에 적혀 있다 — 직접 SQL 수정이나 아직 발견되지 않은 경로로 두 값이 어긋나면
**감지할 방법이 없고**, 감소 UPDATE 의 `WARN` 로그는 카운트가 실제보다 큰 방향을 잡지 못한다.

이 문서는 그 결정을 뒤집는다. 과제 요구사항("좋아요 등록/취소 시 count 동기화")은 이미 충족돼 있으므로
이것은 요구사항 이행이 아니라 **11.3 장이 남긴 공백을 메우는 작업**이다.

## 2. 구조

### 2.1 잡 구성

```
likeCountReconcileJob (run.id 만 올리는 incrementer — 2.2 장, JobListener)
└── likeCountReconcileStep (Tasklet, StepMonitorListener)
    ├── ① 탐지    : 어긋난 후보 상품 ID 목록 조회 (락 없음, 1 회)
    └── ② 재검증·보정 : 후보마다 트랜잭션 1 개 — dryRun=false 일 때만
```

`DemoJobConfig` / `DemoTasklet` 과 같은 형태다 — `@ConditionalOnProperty(spring.batch.job.name)` 으로 이 잡을 지정했을 때만 빈이 뜬다.

**Chunk 가 아니라 Tasklet 인 이유.** 페이징 리더는 페이지마다 쿼리를 다시 실행하는데, 이 탐지 쿼리는
`product_likes` 풀스캔 집계라(3.1 장) 페이지 수만큼 풀스캔이 반복된다. 후보 ID 는 `Long` 목록이라
10 만 건이어도 메모리에 문제가 없다. 한 번 읽고 끝까지 도는 편이 싸다.
Chunk 의 청크 단위 트랜잭션도 맞지 않는다 — 여러 상품 행의 락을 청크 동안 쥐고 있게 되기 때문이다(3.2 장은 상품 하나만 잠근다).

실행 결과는 `StepContribution` 에 남긴다. `readCount` = 탐지된 후보 수, `writeCount` = 실제로 보정한 상품 수.
둘의 차이가 "탐지 시점엔 어긋나 보였지만 재검증에서 정합했던" 일시적 불일치다.

### 2.2 `dryRun` 기본값이 `true` 인 이유

`loadtest/seed-products.sql` 은 상품 10 만 건에 **좋아요 행 없이 합성 `like_count`(지수 분포)** 를 심는다.
인덱스 측정(2026-09-16)의 전제가 이 분포다. 로컬 시더(2026-08-20 11.2 장)도 같은 성질이다.

이 DB 에서 보정을 한 번 돌리면 사실상 모든 상품이 0 으로 덮이고 측정 데이터가 영구히 망가진다.
"보정 잡인데 기본이 탐지만 한다" 는 놀라움보다 **이 사고를 한 번 막는 쪽이 비싸다.** 덮어쓰려면 `dryRun=false` 를 명시한다.

`dryRun=true` 는 ① 탐지만 하고 후보를 로그로 남긴다. 재검증은 하지 않으므로 일시적 불일치가 섞여 있을 수 있고, 로그 문구에 그 사실을 적는다.

**기본값이 실제로 적용되려면 `RunIdIncrementer` 를 쓰지 않는다.** `--job.name` 기동 시 Boot 의 `JobLauncherApplicationRunner` 는
`JobParametersBuilder.getNextJobParameters(job)` 로 **직전 실행의 파라미터 전체**를 incrementer 에 넘기고,
`RunIdIncrementer` 는 그것을 복사한 채 `run.id` 만 올린다. 이번 기동에 준 키만 덮어쓰므로,
어제 `dryRun=false` 로 돌렸다면 오늘 `dryRun` 을 생략해도 `false` 가 이어져 덮어쓰기가 된다 — 이 장이 막으려던 사고 그대로다.
그래서 이 잡은 **`run.id` 만 올리고 나머지 파라미터는 버리는 incrementer** 를 쓴다. `DemoJobConfig` 와 다른 유일한 지점이다.

### 2.3 commerce-api 밖에 두는 것 — `CLAUDE.md` 규칙의 예외

루트 `CLAUDE.md` 는 "새 파일은 `apps/commerce-api` 아래에 만든다" 고 정한다. 이 잡은 그 규칙의 첫 예외다.

| 대안 | 버린 이유 |
|---|---|
| commerce-api `@Scheduled` | API 인스턴스마다 돌아 다중 인스턴스에서 중복 실행 방지(ShedLock 등)가 따로 필요하다. 배치 부하가 API 프로세스와 커넥션 풀을 같이 쓴다. |
| 어드민 API 로 수동 실행 | 실행 이력이 남지 않고, 요청 타임아웃 안에 10 만 건을 도는 구조가 된다. |

대가는 **도메인 코드를 재사용하지 못한다**는 것이다. commerce-batch 는 commerce-api 를 의존하지 않으므로
`ProductModel` · `ProductLikeModel` 을 모르고, `JdbcTemplate` 으로 테이블과 컬럼 이름을 직접 쓴다.
스키마가 바뀌면 컴파일러가 알려주지 않는다 — 4.1 장의 테스트 스키마가 유일한 대조 수단이다.

`CLAUDE.md` 에는 "commerce-batch 의 잡은 예외" 라는 한 줄을 추가한다. `modules/*` · `supports/*` 는 건드리지 않는다.

## 3. 알고리즘

### 3.1 ① 탐지 — 집계 1 회, 락 없음

```sql
SELECT p.id
  FROM products p
  LEFT JOIN (SELECT product_id, COUNT(*) AS cnt
               FROM product_likes
              WHERE deleted_at IS NULL
              GROUP BY product_id) l ON l.product_id = p.id
 WHERE p.deleted_at IS NULL
   AND p.like_count <> COALESCE(l.cnt, 0)
 ORDER BY p.id
```

2026-08-20 11.3 장이 제안한 형태는 상품마다 상관 서브쿼리 `COUNT(*)` 를 실행한다.
`product_id` 인덱스가 없으므로(11.7 장) **상품 수만큼 풀스캔**이 된다. 파생 테이블 `GROUP BY` 는 풀스캔 1 회로 끝난다.

일반 `SELECT` 이므로 일관된 읽기(스냅샷)이고 락을 걸지 않는다. 좋아요 트래픽을 막지 않는 대신
결과는 **후보**일 뿐이다 — 진행 중인 좋아요 트랜잭션이 "좋아요 행은 커밋됐는데 카운트는 아직" 인 순간은 없지만(3.3 장),
스냅샷 시점과 ② 사이에 값이 움직일 수는 있다. 그래서 ② 가 반드시 다시 센다.

`LEFT JOIN` + `COALESCE` 는 "좋아요 행이 하나도 없는데 카운트가 양수" 인 상품을 잡기 위해서다.
`INNER JOIN` 이면 11.3 장이 지적한 "반대 방향" 이 정확히 빠진다.

### 3.2 ② 재검증·보정 — 후보당 트랜잭션 1 개, READ COMMITTED

```sql
-- (1) 상품 행을 먼저 잠근다
SELECT like_count FROM products WHERE id = :id AND deleted_at IS NULL FOR UPDATE
-- (2) 잠근 뒤에 락 없이 센다
SELECT COUNT(*) FROM product_likes WHERE product_id = :id AND deleted_at IS NULL
-- (3) 다를 때만 쓴다
UPDATE products SET like_count = :actual WHERE id = :id
```

- (1) 이 행을 돌려주지 않으면 그 사이 상품이 삭제된 것이다. 건너뛴다.
- (2) 는 상품 하나의 풀스캔이다. 후보가 적은 정상 운영에서는 문제가 되지 않는다. 후보가 수만 건이면 느리지만,
  그것은 이미 대량 불일치 사고이고 보정이 느린 것이 그 사고보다 작은 문제다.
- (3) 은 `updated_at` 을 건드리지 않는다. 좋아요 증감 UPDATE 와 같은 이유다 — 누구도 상품을 편집하지 않았다(2026-08-20 6.4 장).
- 보정한 건마다 `WARN` 으로 `productId, before, after` 를 남긴다. 어긋남은 그 자체로 버그 신호이므로 INFO 로 묻히면 안 된다.
- 상품 하나의 실패(교착 상태 희생 등)는 로그를 남기고 다음 후보로 넘어간다. 한 건 때문에 나머지 보정을 멈추지 않는다.
  실패가 하나라도 있으면 스텝은 `FAILED` 로 끝나 재실행 대상임이 드러나게 한다.

**트랜잭션을 상품 단위로 끊는 이유.** 락을 쥐는 시간이 곧 그 상품의 좋아요가 기다리는 시간이다.
여러 상품을 한 트랜잭션에 묶으면 앞에서 잠근 상품의 좋아요가 뒤 상품의 풀스캔이 끝날 때까지 멈춘다.

### 3.3 왜 이 순서가 경합에 안전한가

전제는 `LikeFacade` 의 트랜잭션 구조다. **좋아요 행 변경(INSERT / 부활 UPDATE / 소프트 삭제 UPDATE)과
`products` 행의 원자적 UPDATE 가 한 트랜잭션이며, 상품 행 X 락은 커밋까지 유지된다.**
(2026-08-20 6.6 · 6.7 장)

두 쓰기의 **순서는 전제가 아니다.** 지금 코드는 좋아요 행을 먼저 바꾸고 상품 행을 나중에 갱신하는데, 이쪽이 배치에게 더 어려운 경우다 —
"좋아요 행은 바뀌었는데 상품 행 락은 아직 없는" 순간이 생기기 때문이다(아래 표 세 번째 줄). 순서가 반대라면 T 는 무언가를 바꾸는 시점에
이미 상품 행 락을 쥐고 있으므로, 배치는 (1) 에서 기다리기만 하면 된다.

배치가 (1) 에서 상품 행 락을 얻은 순간, 그 상품의 좋아요 트랜잭션 T 는 셋 중 하나다.

| T 의 상태 | 배치가 보는 것 | 최종값 |
|---|---|---|
| 이미 커밋 | (2) 가 T 의 행을 센다 | 정확 |
| 상품 행 UPDATE 를 마쳤고 미커밋 | T 가 X 락을 쥐고 있어 배치는 (1) 에서 대기한다. T 가 커밋하면 첫 번째 줄과 같아진다 | 정확 |
| 좋아요 행만 바꿨고 상품 행은 아직 | (2) 가 T 의 미커밋 행을 **보지 않는다** → N 을 쓴다. T 는 배치 커밋 뒤 락을 얻어 +1 → N+1 | 정확 |

취소도 대칭이다. 세 번째 줄에서 T 의 미커밋 소프트 삭제는 (2) 에게 보이지 않아 그 행이 아직 활성으로 세어지고(N),
T 가 배치 커밋 뒤 -1 → N-1 이 된다.

세 번째 줄이 성립하려면 (2) 가 **락 없는 읽기**여야 하고, 그 스냅샷이 (1) **이후**에 잡혀야 한다.
READ COMMITTED 는 문장마다 새 스냅샷을 잡으므로 둘 다 만족한다.

REPEATABLE READ 에서도 스냅샷은 첫 일관된 읽기 시점(= (2))에 잡히므로 우연히 맞는다. 그러나
트랜잭션 안에 (1) 보다 앞선 일반 `SELECT` 가 하나라도 끼어드는 순간 스냅샷이 락 획득 전으로 당겨져 두 번째 줄이 깨진다.
**격리 수준을 명시해 그 전제를 코드가 아닌 설정이 보장하게 한다.**

### 3.4 버린 대안 — 한 문장 UPDATE

```sql
UPDATE products p
   SET like_count = (SELECT COUNT(*) FROM product_likes l WHERE l.product_id = p.id AND l.deleted_at IS NULL)
 WHERE p.id = :id
```

한 문장이라 간결해 보이지만, InnoDB 에서 **DML 안의 서브쿼리는 잠금 읽기(공유 락)** 다.

- 인덱스가 없으므로 `product_likes` 를 풀스캔하며 **훑은 모든 행에 공유 넥스트키 락**이 걸린다 — 보정 한 건이 도는 동안 모든 상품의 좋아요 등록이 막힌다.
- 3.3 장 세 번째 줄의 T 가 있으면: 배치는 상품 행 X 락을 쥔 채 T 의 미커밋 좋아요 행에서 대기하고,
  T 는 좋아요 행을 쥔 채 상품 행에서 대기한다 — **교착 상태**다. 희생자가 T 면 사용자의 좋아요가 실패한다.

## 4. 테스트

### 4.1 테스트 스키마

commerce-batch 에는 엔티티가 없어 `ddl-auto: create` 가 `products` · `product_likes` 를 만들지 않는다.
테스트 리소스에 두 테이블의 DDL 을 두고 `@Sql` 로 적용한다. 배치가 쓰는 컬럼(`id`, `like_count`, `deleted_at`, `product_id`, `user_id`)과
`uk_product_likes_user_product` 유니크 제약만 실제 스키마와 맞춘다.

⚠️ 이 DDL 은 commerce-api 엔티티와 **자동으로 동기화되지 않는다.** 2.3 장의 대가가 여기로 온다. DDL 파일 머리에 원본 엔티티 경로를 적는다.

### 4.2 E2E (`LikeCountReconcileJobE2ETest`)

| 상황 | 기대 |
|---|---|
| 카운트가 실제보다 큼 (좋아요 행 0, `like_count` 5) | 0 으로 보정 |
| 카운트가 실제보다 작음 | 실제 행 수로 보정 |
| 정합한 상품 | 변경 없음, `writeCount` 에 포함되지 않음 |
| 삭제된 상품 (어긋나 있어도) | 변경 없음 |
| `dryRun` 미지정 | 아무것도 바뀌지 않음, `readCount` = 후보 수 |
| 직전 실행이 `dryRun=false`, 이번엔 생략 (Boot 러너와 같은 파라미터 경로) | 아무것도 바뀌지 않음 — 2.2 장 |
| `dryRun` 오타 | 아무것도 바뀌지 않고 잡 실패 |
| 한 상품의 실패 | 나머지는 보정, 잡은 `FAILED` |

"소프트 삭제된 좋아요 행은 세지 않는다", "보정 후 `updated_at` 그대로", "재검증 시점에 삭제된 상품은 건너뜀" 은
잡을 거치지 않는 보정 로직 통합 테스트(`LikeCountReconcilerIntegrationTest`)가 맡는다. 잡 단위에서 다시 검증할 것이 없다.

### 4.3 경합 (`LikeCountReconcileConcurrencyTest`)

실제 `LikeFacade` 는 commerce-batch 에 없으므로 그 쓰기(한 트랜잭션 안에서 좋아요 행 → 상품 행 UPDATE — 배치에게 더 어려운 지금 순서 그대로)를 `JdbcTemplate` 으로 재현하고,
`CountDownLatch` 로 3.3 장 표의 두 줄과, 배치 쪽이 멈춘 한 상황을 고정한다.

1. **좋아요 행만 넣고 멈춘 T** — 배치가 대기 없이 N 을 쓰고 끝난다. T 를 재개해 커밋하면 최종값은 N+1.
2. **상품 행 UPDATE 까지 하고 커밋 전에 멈춘 T** — 배치가 (1) 에서 대기한다. T 커밋 후 배치가 실제 값(N+1)을 쓴다.
3. **배치가 센 뒤 쓰기 전에 멈춤, 그때 T 시작** — T 가 상품 행에서 대기한다. 잠금·세기·쓰기가 한 트랜잭션이라는 증거다.
   이것이 없으면 `JdbcTemplate` 이 트랜잭션에 묶이지 않고 문장마다 자동 커밋되는 사고를 못 잡는다 — 1·2 번은 덮어쓰는 값이 절댓값이라 그 상태에서도 통과한다.

테스트가 실제로 순서를 검증하는지 구현 중 한 번 확인한다. 세는 SELECT 를 잠금 읽기(`LOCK IN SHARE MODE`, 3.4 장의 한 문장 UPDATE 와 같은 성질)로 바꾸면
1 번이 깨져야 하고, 보정의 `@Transactional` 을 지우면 3 번이 깨져야 한다.

## 6. 위험과 한계

### 6.1 스키마 이중 관리

2.3 · 4.1 장. 컬럼 이름이 바뀌면 배치는 런타임에 실패하고, 테스트 DDL 을 같이 고치지 않으면 테스트는 계속 통과한다.
commerce-api 에 스키마 마이그레이션 도구가 생기면 테스트 DDL 을 그쪽에서 가져오도록 바꾼다.

### 6.2 후보가 많을 때의 비용

정상 운영에서 후보는 0 에 가깝다. 대량 불일치 사고에서는 후보마다 `product_likes` 풀스캔이 한 번씩 일어나
느려진다. 그때가 오면 11.7 장의 인덱스를 다시 저울질할 근거가 된다 — 이 문서는 그 판단을 앞당기지 않는다.

### 6.3 `LikeFacade` 의 트랜잭션 구조에 의존한다

3.3 장의 안전성은 "좋아요 행 변경과 카운트 갱신이 한 트랜잭션이고, 카운트 갱신이 상품 행 X 락을 커밋까지 쥔다" 에 기댄다.
누군가 카운트 갱신을 비동기(이벤트 · Redis, 2026-08-20 11.4 장)로 옮기면 **이 배치가 틀린 값을 쓰기 시작한다** —
"좋아요 행은 커밋됐는데 카운트는 아직" 인 순간이 생겨, 배치가 실제 값 N+1 을 쓴 뒤 늦게 도착한 +1 이 N+2 를 만든다.
`LikeFacade` KDoc 에 이 의존을 한 줄 남긴다.

두 쓰기의 순서를 뒤집는 것은 위험이 아니다(3.3 장).

### 6.4 로컬 · 측정 DB 에서 `dryRun=false`

2.2 장의 기본값은 실수를 한 번 막을 뿐이다. 명시적으로 `dryRun=false` 를 주면 측정 시드는 덮인다. 복구는 시드 재적재뿐이다.
