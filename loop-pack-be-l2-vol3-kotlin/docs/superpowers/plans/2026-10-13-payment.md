# PG 연동 결제와 회복탄력성 구현 계획

> **에이전트 작업자에게:** 필수 하위 스킬 — 이 계획은 `superpowers:subagent-driven-development`(권장) 또는
> `superpowers:executing-plans` 로 태스크 단위로 실행한다. 단계는 체크박스(`- [ ]`) 문법으로 추적한다.

**목표:** 주문에 대한 카드 결제 API 를 추가하고, 느리고 자주 실패하는 비동기 PG(`pg-simulator`)와 연동하면서
타임아웃 · 재시도 · 서킷브레이커 · 결과 동기화로 PG 장애가 서비스 전체로 번지지 않고 주문 상태가 PG 의 실제 결과와 맞게 한다.

**아키텍처:** `domain` 에 `PaymentGateway` 인터페이스를 두고 `infrastructure` 가 Feign + Resilience4j 로 구현한다(DIP).
`PaymentFacade` 는 PG 호출을 트랜잭션 밖에 두고(tx1 흔적 남기기 → PG 호출 → tx2 결과 반영), PG 결과를 `Accepted` · `NotSent` · `Unknown`
셋으로만 안다. 최종 결과는 콜백(신호로만 사용)과 스케줄러가 같은 `sync` 로 PG 를 다시 조회해 확정한다. 주문 상태 전이는 조건부 UPDATE 다.

**기술 스택:** Kotlin 2.0 / Spring Boot 3.4 / Spring Cloud OpenFeign(BOM 2024.0.1) / Resilience4j 2.2(`resilience4j-spring-boot3`, BOM 관리) /
Spring AOP / JPA / JUnit 5 · AssertJ · mockito-kotlin(`@MockitoBean`) / WireMock(`spring-cloud-contract-wiremock`) / Testcontainers(MySQL)

**설계 문서:** `docs/superpowers/specs/2026-10-13-payment-design.md`
(이 계획은 설계 문서를 근거로 삼는다. 실행자는 둘 다 읽는다. 어긋나면 설계 문서가 기준이다.)

## 전역 제약

모든 태스크의 요구사항에 아래가 암묵적으로 포함된다.

- **응답 · 주석 · 커밋 메시지 · 문서는 한국어.** 변수명 · 함수명은 영어.
- **커밋 메시지 형식은 `<타입> : <내용>`** — 콜론 앞에 공백. 끝에 빈 줄 하나 뒤 `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>` 를 붙인다.
- **`modules/` · `supports/` 는 고치지 않는다.** 새 모듈은 Task 1 의 `apps/pg-simulator` 뿐이다(2026-10-13 사용자 승인, 설계 2.1 장).
- **pg-simulator 의 동작을 바꾸지 않는다.** ktlint 등 빌드 통과를 위한 형식 수정만 허용한다.
- **수치는 설계 6 장 그대로다.** connect 500 ms · read 1 s / 재시도 3 회 · 200 ms ×2 · 5xx 만 / `pgRequest` 서킷(요청 단위) 윈도우 20 · 최소 10 · 50% · 느린 호출 2.5 s · 50% · OPEN 10 s · HALF_OPEN 5 / `pgQuery` 윈도우 20 · 최소 10 · 50% · 800 ms · 50% · OPEN 10 s · HALF_OPEN 5.
- **감싸는 순서는 `CircuitBreaker( Retry( 호출 ) )` — 서킷이 바깥이다.** 애노테이션 기본값의 반대라 yml 의 aspect-order 로 뒤집는다. (설계 6.3 · 6.4 장)
- **PG 호출은 DB 트랜잭션 안에서 하지 않는다.** (설계 4.1 장)
- **즉시 FAILED 로 확정하는 것은 `NotSent`(보내지 않은 것이 확실함 — 서킷 OPEN, 또는 첫 시도의 연결 거부) 뿐이다.** 읽기 타임아웃 · 5xx · 앞선 시도 뒤의 연결 거부 · 연결 타임아웃은 `Unknown`. (설계 4.2 장)
- **콜백 본문의 `status` 를 상태 반영에 쓰지 않는다.** PG 를 다시 조회한다. (설계 5.1 장)
- **`ktlintFormat` 을 실행하지 않는다.** 검증은 `ktlintCheck`. 최대 130 자(`*Test.kt` 예외), star import 금지, trailing comma 허용.
- **블록 주석 안에 `/**` 를 쓰지 않는다.** Kotlin 은 블록 주석이 중첩되어 `Unclosed comment` 로 컴파일이 깨진다.
- **주석은 "왜" 를 적는다.** 새로 쓰는 인용은 `(2026-10-13 결제 설계 N 장)` 형식이다.
- **조건부 UPDATE 는 `@Modifying(clearAutomatically = true, flushAutomatically = true)` 다.** 호출 뒤 영속성 컨텍스트가 비워지므로,
  같은 트랜잭션에서 그 전에 읽은 엔티티 값은 호출 **전에** 꺼내 둔다. 변경한 엔티티는 flush 가 먼저 돌아 반영된다.
- 테스트: `@AfterEach` 에서 `databaseCleanUp.truncateAllTables()`. `@Transactional` 을 테스트에 붙이지 않는다(트랜잭션 분리를 검증할 수 없게 된다).
- PG 를 바꿔 끼우는 테스트는 `@MockitoBean lateinit var paymentGateway: PaymentGateway`(`org.springframework.test.context.bean.override.mockito.MockitoBean`) 와 mockito-kotlin(`whenever`, `any`, `verify`, `never`)을 쓴다.
- **Gradle 명령은 `loop-pack-be-l2-vol3-kotlin/` 에서 실행한다.** Git 루트는 상위 `study-project/` 다 — `git status` 는 경로를 좁혀서 본다.
  - 전체: `./gradlew :apps:commerce-api:test`
  - 단일 클래스: `./gradlew :apps:commerce-api:test --tests 'com.loopers.<FQCN>'`
  - 린트: `./gradlew :apps:commerce-api:ktlintCheck`
- 측정(설계 11 장)은 이 계획에 넣지 않는다. 구현이 끝난 뒤 별도 계획으로 진행한다.

## 검토 초점

설계가 함의하지만 놓치기 쉬운 입력 · 실패 조건이다. 각 줄의 테스트를 담당 태스크에 넣었다.

1. **서킷이 재시도 하나하나를 셈** — 시도 실패율 40% 를 매 호출 판정하면 정상 PG 에서도 10 분 부하에 약 92% 확률로 서킷이 열려
   사용자가 결제 실패를 본다. 서킷을 재시도 바깥에 두는데, 애노테이션 기본 순서가 반대라 yml 로 뒤집는다. 키를 틀려도 에러가 없다.
   → Task 4 `retriesThreeTimes_andCountsOneCircuitFailure` (설계 6.3 · 6.4 장, 2026-10-16 검토)
2. **한 자리 주문 ID** — 주문 1 번을 그대로 보내면 PG 가 400 이다. `"000001"` 처럼 6 자리로 보내야 한다. → Task 4 `padsOrderIdToSixDigits`
3. **결제 실패 후 재결제한 주문의 PG 거래 목록** — 과거 실패 거래(이미 연결된 키)를 이번 REQUESTED 건으로 착각하면 안 된다. → Task 6 `failsRequested_whenOnlyKnownKeysExistAfterOneMinute`
4. **키가 기록되기 전에 온 콜백** — `transactionKey` 로 못 찾으면 `orderId` 의 진행 중 결제로 찾아야 한다. → Task 6 `syncsByOrderId_whenKeyIsNotLinkedYet`
5. **쿠폰으로 0 원이 된 주문** — PG 를 부르지 않고 바로 PAID 여야 한다. 400 으로 막으면 영원히 결제할 수 없다. → Task 5 `paysImmediately_whenAmountIsZero`
6. **같은 결제를 두 경로가 서로 다른 결과로 동시에 확정** — 버전이 없으면 결제는 마지막 커밋이, 주문은 먼저 UPDATE 한 쪽이 이겨
   "결제 FAILED · 주문 PAID" 로 어긋난 채 굳는다. 진 쪽의 낙관적 락 예외가 콜백 500 으로 새도 안 된다.
   → Task 3 `rejectsStaleUpdate`, Task 6 `keepsPaymentAndOrderConsistent_whenConfirmedConcurrently` (설계 3.1 · 5.2 장, 2026-10-15 검토)
7. **pg-simulator 가 `loopers` 스키마에 붙음** — `jpa.yml` 의 `local` 프로필 URL 이 pg-simulator 의 URL 을 덮어써,
   두 앱이 서로의 `payments` 테이블을 drop 한다. → Task 1 Step 6 의 스키마 확인 (설계 2.2 장, 2026-10-15 검토)
8. **PG 가 죽어 연결이 거부됨** — 요청이 나가지 않은 것이 확실하므로 `NotSent` 다. `Unknown` 으로 두면 PG 장애 내내 주문이 PAYING 에 묶인다.
   단, 앞선 시도가 5xx 로 PG 에 닿은 뒤의 연결 거부는 `Unknown`.
   → Task 4 `PgPaymentGatewayConnectionTest`, `PgPaymentGatewayTranslationTest` (설계 4.2 · 6.4 장, 2026-10-16 검토)
9. **고아 거래 키** — 1 분 뒤 포기한 결제가 뒤늦게 승인되면 그 키가 다음 결제 시도의 "모르는 키" 로 섞인다. 둘 중 하나를 골라 연결하면
   고아의 결과로 이번 결제를 확정한다. 모르는 키가 둘 이상이면 연결하지 않는다. 콜백의 대체 경로는 키 없는 진행 중 결제만 찾는다.
   → Task 6 `doesNotLink_whenUnknownKeysAreAmbiguous`, `ignores_whenInProgressPaymentHasAnotherKey` (설계 5.1 · 5.2 · 9.5 장, 2026-10-16 검토)
10. **금액 불일치를 그대로 둠** — 상태가 영영 안 바뀌어 매 주기 동기화 대상으로 남고, 쌓이면 스케줄러 앞자리를 막는다. FAILED 로 닫는다.
    → Task 6 `closesAsFailed_whenAmountMismatches` (설계 5.2 장, 2026-10-16 검토)
11. **가는 중인 요청에 고아 키를 연결** — 재결제 요청이 PG 로 가는 중(키 없음)에 고아 거래의 콜백이 오면, 모르는 키가 고아 하나뿐이라
    이번 결제에 연결해 확정하고, 뒤이어 이번 요청의 거래도 승인돼 이중 결제가 된다. REQUESTED 는 생성 후 6 s 동안 PG 를 조회하지 않는다.
    → Task 6 `skipsPg_whileRequestMayBeInFlight` (설계 5.2 · 9.5 장, 2026-10-17 검토)

```kotlin
package com.loopers.infrastructure.order

import com.loopers.domain.order.OrderModel
import com.loopers.domain.order.OrderStatus
import org.springframework.data.jpa.repository.JpaRepository
import org.springframework.data.jpa.repository.Modifying
import org.springframework.data.jpa.repository.Query
import org.springframework.data.repository.query.Param

/**
 * 단건 조회 메서드를 여기 두지 않는다. (Ruling T5-1)
 *
 * 단건 조회는 항목(orderItems)을 fetch join 으로 함께 끌어와야 하는데, 파생 쿼리 메서드가 반환하는
 * 컬렉션이 to-many 라 fetch join + distinct 없이는 항목이 둘 이상일 때 NonUniqueResultException 이 난다.
 * 파생 쿼리 메서드 이름만으로는 distinct 를 표현할 방법이 마땅치 않아, 그 조합을 명시적으로 다룰 수 있는
 * `OrderQueryDslRepository.findById` 로 옮겼다. 그래서 이 인터페이스에는 `save` 를 위한 상속과
 * 상태 전이용 조건부 UPDATE 만 남는다.
 */
interface OrderJpaRepository : JpaRepository<OrderModel, Long> {
    /**
     * 결제 상태 전이. 영향 행 수가 곧 판정이다 — 0 이면 다른 요청이 먼저 바꿨다. (2026-10-13 결제 설계 3.3 장)
     *
     * decreaseStock 과 같이 updated_at 을 건드리지 않는다.
     * clearAutomatically 이므로 호출 뒤 같은 트랜잭션의 엔티티는 detach 된다. 필요한 값은 호출 전에 꺼낸다.
     */
    @Modifying(clearAutomatically = true, flushAutomatically = true)
    @Query(
        """
        UPDATE OrderModel o
           SET o.status = :next
         WHERE o.id = :orderId AND o.deletedAt IS NULL AND o.status IN :expected
        """,
    )
    fun changeStatus(
        @Param("orderId") orderId: Long,
        @Param("expected") expected: Collection<OrderStatus>,
        @Param("next") next: OrderStatus,
    ): Int
}
```

```kotlin
package com.loopers.domain.payment

import com.loopers.support.error.CoreException
import com.loopers.support.error.ErrorType
import jakarta.persistence.Embeddable

/**
 * 카드 번호. PG 와 같은 형식(xxxx-xxxx-xxxx-xxxx)을 우리 쪽에서 먼저 막는다.
 * 형식 오류를 PG 까지 보내면 4xx 가 돌아오는데, 그건 PG 장애가 아니라 우리 입력 문제이므로 PG 를 부르기 전에 400 으로 끝낸다.
 *
 * toString 이 마지막 네 자리만 남기는 이유는 로그 · 예외 메시지에 카드 번호 전체가 찍히지 않게 하기 위해서다.
 */
@Embeddable
data class CardNo(val value: String) {
    init {
        if (!PATTERN.matches(value)) {
            throw CoreException(ErrorType.BAD_REQUEST, "카드 번호는 xxxx-xxxx-xxxx-xxxx 형식이어야 합니다.")
        }
    }

    override fun toString(): String = "****-****-****-${value.takeLast(4)}"

    companion object {
        private val PATTERN = Regex("^\\d{4}-\\d{4}-\\d{4}-\\d{4}$")
    }
}
```

```kotlin
 * 결제 상태.
 *
 * REQUESTED 는 "PG 에 닿았는지 모른다" 를 저장한 상태다. 타임아웃을 FAILED 로 처리하면 PG 에선 승인됐는데

    SUCCESS,
    FAILED,
    ;
```

```kotlin
package com.loopers.domain.payment

import com.loopers.domain.BaseEntity
import com.loopers.domain.product.Price
import com.loopers.support.error.CoreException
import com.loopers.support.error.ErrorType
import jakarta.persistence.AttributeOverride
import jakarta.persistence.Column
import jakarta.persistence.Embedded
import jakarta.persistence.Entity
import jakarta.persistence.EnumType
import jakarta.persistence.Enumerated
import jakarta.persistence.Index
import jakarta.persistence.Table
import jakarta.persistence.UniqueConstraint
import jakarta.persistence.Version

/**
 * 결제 애그리거트 루트. 주문 하나에 여러 건일 수 있다 — 실패하면 다른 카드로 다시 결제한다. (2026-10-13 결제 설계 3.2 장)
 *
 * 주문과 회원은 식별자로만 참조한다. 결제는 주문의 부품이 아니다 — 주문 없이 생기지는 않지만,
 * 주문과 따로 만들어지고 따로 저장되며 PG 거래 키로 주문을 거치지 않고 조회된다.
 *
 * 전이 메서드가 확정 상태에서 예외 없이 무시하는 이유는 콜백과 스케줄러가 같은 결과를 동시에 들고 오는 것이 정상 경로이기 때문이다.
 * 예외를 던지면 둘 중 하나가 매번 500 이 된다. (설계 3.1 장)
 */
@Entity
@Table(
    name = "payments",
    indexes = [
        Index(name = "idx_payments_order_id", columnList = "order_id"),
        Index(name = "idx_payments_status_updated_at", columnList = "status, updated_at"),
    ],
    uniqueConstraints = [UniqueConstraint(name = "uk_payments_transaction_key", columnNames = ["transaction_key"])],
)
class PaymentModel private constructor(
    orderId: Long,
    userId: Long,
    amount: Price,
    cardType: CardType,
    cardNo: CardNo,
) : BaseEntity() {
    @Column(name = "order_id", nullable = false)
    var orderId: Long = orderId
        protected set

    /** PG 의 X-USER-ID 로도 쓴다. PG 는 조회 때 요청 때와 같은 값을 요구하므로 저장해 둔 이 값을 계속 쓴다. */
    @Column(name = "user_id", nullable = false)
    var userId: Long = userId
        protected set

    /** 결제 요청 시점의 order.paidAmount 스냅샷. */
    @Embedded
    @AttributeOverride(name = "value", column = Column(name = "amount", nullable = false))
    var amount: Price = amount
        protected set

    @Enumerated(EnumType.STRING)
    @Column(name = "card_type", nullable = false, length = 20)
    var cardType: CardType = cardType
        protected set

    @Embedded
    @AttributeOverride(name = "value", column = Column(name = "card_no", nullable = false))
    var cardNo: CardNo = cardNo
        protected set

    /** PG 가 접수하기 전에는 null 이다. MySQL 유니크 인덱스는 NULL 을 여러 개 허용한다. */
    @Column(name = "transaction_key")
    var transactionKey: String? = null
        protected set

    @Enumerated(EnumType.STRING)
    @Column(name = "status", nullable = false, length = 20)
    var status: PaymentStatus = PaymentStatus.REQUESTED
        protected set

    @Column(name = "failure_reason")
    var failureReason: String? = null
        protected set

    /**
     * 낙관적 락. 주문 전이는 조건부 UPDATE 로 직렬화되지만 결제 전이는 읽고 바꾸는 더티 체킹이라,
     * 버전이 없으면 동시에 REQUESTED 를 읽은 두 확정 경로가 각자 커밋해 "결제 FAILED · 주문 PAID" 로 어긋난 채 굳을 수 있다.
     * 전이 메서드가 확정 상태를 무시하는 것(멱등)은 순차 실행에서만 통한다. (2026-10-13 결제 설계 3.1 장)
     *
     * BaseEntity 가 아니라 여기 두는 이유 — BaseEntity 는 세 앱이 공유한다.
     */
    @Version
    @Column(name = "version", nullable = false)
    var version: Long = 0
        protected set

    init {
        if (orderId <= 0) {
            throw CoreException(ErrorType.BAD_REQUEST, "주문 ID 는 양수여야 합니다.")
        }
        if (userId <= 0) {
            throw CoreException(ErrorType.BAD_REQUEST, "회원 ID 는 양수여야 합니다.")
        }
    }

    /** PG 가 접수했다. 요청됨이 아니면 무시한다 — 이미 키가 있거나 확정됐다. */
    fun markPending(transactionKey: String) {
        if (status != PaymentStatus.REQUESTED) return
        this.transactionKey = transactionKey
        status = PaymentStatus.PENDING
    }

    fun succeed() {
        if (status.isFinal) return
        status = PaymentStatus.SUCCESS
    }

    fun fail(reason: String) {
        if (status.isFinal) return
        status = PaymentStatus.FAILED
        failureReason = reason
    }

    companion object {
        fun create(
            orderId: Long,
            userId: Long,
            amount: Price,
            cardType: CardType,
            cardNo: CardNo,
        ): PaymentModel = PaymentModel(
            orderId = orderId,
            userId = userId,
            amount = amount,
            cardType = cardType,
            cardNo = cardNo,
        )
    }
}
```

```kotlin
import com.loopers.domain.product.Price

/**
 * 외부 PG 계약. domain 에 두고 infrastructure 가 구현한다(DIP).
 *
 * 예외를 던지지 않고 결과 타입을 돌려준다. 타임아웃 · 서킷 · HTTP 예외의 해석은 구현이 끝내고,
 * Facade 는 "보냈는지 / 안 보냈는지 / 모르는지" 만 안다. (2026-10-13 결제 설계 4.2 장)
 */

    fun request(request: PgPaymentRequest): PgRequestResult

    fun findTransaction(userId: Long, transactionKey: String): PgQueryResult<PgTransaction>

    /** 주문에 엮인 거래 목록. 목록 원소에는 금액이 없다(amount = null). */
    fun findTransactionsByOrder(userId: Long, orderId: Long): PgQueryResult<List<PgTransaction>>
}

data class PgPaymentRequest(
```

```kotlin
package com.loopers.infrastructure.payment

import io.github.resilience4j.circuitbreaker.annotation.CircuitBreaker
import io.github.resilience4j.retry.annotation.Retry
import org.springframework.stereotype.Component
import java.util.concurrent.atomic.AtomicInteger

/**
 * 재시도 · 서킷만 붙이는 층. 예외를 해석하지 않고 그대로 던진다. (2026-10-13 결제 설계 6.4 장)
 *
 * PgPaymentGateway 와 나눈 이유 — 애노테이션은 AOP 프록시로 동작해 같은 클래스 안의 호출에는 걸리지 않는다.
 * fallbackMethod 를 쓰지 않는 이유 — 재시도와 서킷 양쪽의 fallback 이 얽히면 어디서 무엇이 처리됐는지 읽히지 않는다.
 *
 * 감싸는 순서는 CircuitBreaker( Retry( 호출 ) ) 다 — 애노테이션 기본값의 반대라 application.yml 의 aspect-order 로 뒤집었다.
 * 서킷은 재시도를 다 마친 결과를 한 건으로 센다. 재시도 하나하나를 세면 평소 시도 실패율 40% 때문에 정상인 PG 에서도
 * 서킷이 열린다. (설계 6.3 · 6.4 장)
 */
@Component
class PgResilientClient(
    private val pgClient: PgClient,
) {
    /**
     * attempts 는 메서드 본문 첫 줄에서 올린다. 재시도가 본문을 다시 부를 때마다 오르므로 실제로 나간 시도 수다.
     * PgPaymentGateway 가 연결 거부가 첫 시도였는지 가리는 데 쓴다 — 앞선 시도가 PG 에 닿았다면 NotSent 가 아니다.
     * 이 줄을 pgClient 호출 뒤로 옮기면 실패한 시도가 세어지지 않아 NotSent 오판이 생긴다. (설계 4.2 장)
     */
    @CircuitBreaker(name = "pgRequest")
    @Retry(name = "pgRequest")
    fun requestPayment(
        userId: String,
        request: PgDto.PaymentRequest,
        attempts: AtomicInteger,
    ): PgDto.Response<PgDto.TransactionResponse> {
        attempts.incrementAndGet()
        return pgClient.requestPayment(userId, request)
    }

    /** 조회는 재시도하지 않는다. 스케줄러가 다음 주기에 다시 묻는다. (설계 6.2 장) */
    @CircuitBreaker(name = "pgQuery")
    fun getTransaction(userId: String, transactionKey: String): PgDto.Response<PgDto.TransactionDetailResponse> =
        pgClient.getTransaction(userId, transactionKey)

    @CircuitBreaker(name = "pgQuery")
    fun getTransactionsByOrder(userId: String, orderId: String): PgDto.Response<PgDto.OrderResponse> =
        pgClient.getTransactionsByOrder(userId, orderId)
}
```

```kotlin
package com.loopers.infrastructure.payment

import com.loopers.domain.payment.PaymentGateway
import com.loopers.domain.payment.PgPaymentRequest
import com.loopers.domain.payment.PgQueryResult
import com.loopers.domain.payment.PgRequestResult
import com.loopers.domain.payment.PgTransaction
import com.loopers.domain.payment.PgTransactionStatus
import feign.FeignException
import feign.RetryableException
import io.github.resilience4j.circuitbreaker.CallNotPermittedException
import org.slf4j.LoggerFactory
import org.springframework.stereotype.Component
import java.net.ConnectException
import java.util.concurrent.atomic.AtomicInteger

/**
 * PaymentGateway 구현. Feign · Resilience4j 예외를 결과 타입으로 번역하는 유일한 자리다. (2026-10-13 결제 설계 4.2 · 6.4 장)
 *
 * 즉시 실패(NotSent)로 번역하는 것은 보내지 않은 것이 확실한 두 경우 — 서킷이 막았을 때와 첫 시도의 연결이 거부됐을 때 — 뿐이다.
 * 5xx 도 Unknown 이다 — 실제 PG 는 어디까지 처리했는지 장담할 수 없다. 시뮬레이터의 구현 세부에 기대지 않는다.
 */
@Component
class PgPaymentGateway(
    private val client: PgResilientClient,
    private val properties: PgProperties,
) : PaymentGateway {
    private val log = LoggerFactory.getLogger(PgPaymentGateway::class.java)

    override fun request(request: PgPaymentRequest): PgRequestResult {
        val attempts = AtomicInteger(0)
        return try {
            val response = client.requestPayment(
                userId = request.userId.toString(),
                request = PgDto.PaymentRequest(
                    orderId = PgDto.toPgOrderId(request.orderId),
                    cardType = request.cardType.name,
                    cardNo = request.cardNo.value,
                    amount = request.amount.value,
                    callbackUrl = properties.callbackUrl,
                ),
                attempts = attempts,
            )
            response.data?.transactionKey
                ?.let { PgRequestResult.Accepted(it) }
                ?: run {
                    log.error("[orderId = {}] PG 가 200 을 주었지만 거래 키가 없습니다.", request.orderId)
                    PgRequestResult.Unknown
                }
        } catch (e: CallNotPermittedException) {
            // 서킷이 재시도 바깥이라 이 예외는 첫 시도 전에만 난다. 한 번도 보내지 않았다. (설계 6.4 장)
            log.warn("[orderId = {}] 서킷이 열려 PG 를 호출하지 않았습니다.", request.orderId)
            PgRequestResult.NotSent
        } catch (e: RetryableException) {
            // 연결 거부는 TCP 연결도 맺지 못한 것이라 요청이 나가지 않았다. 단 앞선 시도가 5xx 로 PG 에 닿았다면 그 결과를 모른다.
            // 연결 타임아웃은 읽기 타임아웃과 같은 SocketTimeoutException 이라 메시지로만 구분되므로 Unknown 으로 둔다. (설계 4.2 장)
            if (e.cause is ConnectException && attempts.get() == 1) {
                log.warn("[orderId = {}] PG 연결이 거부되어 결제 요청을 보내지 못했습니다.", request.orderId)
                PgRequestResult.NotSent
            } else {
                log.warn("[orderId = {}] PG 결제 요청 결과를 알 수 없습니다. 시도 {} 회. {}", request.orderId, attempts.get(), e.toString())
                PgRequestResult.Unknown
            }
        } catch (e: FeignException.FeignClientException) {
            // 입력은 우리 쪽에서 이미 검증했으므로 정상 경로에선 나오지 않는다. 요청 형식 버그의 신호다.
            log.error("[orderId = {}] PG 가 결제 요청을 거부했습니다. status = {}", request.orderId, e.status(), e)
            PgRequestResult.Unknown
        } catch (e: Exception) {
            log.warn("[orderId = {}] PG 결제 요청 결과를 알 수 없습니다. {}", request.orderId, e.toString())
            PgRequestResult.Unknown
        }
    }

    override fun findTransaction(userId: Long, transactionKey: String): PgQueryResult<PgTransaction> = query {
        client.getTransaction(userId.toString(), transactionKey).data
            ?.let { PgQueryResult.Found(PgTransaction(it.transactionKey, toStatus(it.status), it.reason, it.amount)) }
            ?: PgQueryResult.NotFound
    }

    override fun findTransactionsByOrder(userId: Long, orderId: Long): PgQueryResult<List<PgTransaction>> = query {
        client.getTransactionsByOrder(userId.toString(), PgDto.toPgOrderId(orderId)).data
            ?.let { data ->
                // 목록 응답에는 금액이 없다. 확정 전 금액 검증은 상세 조회로 한다. (설계 5.2 장)
                PgQueryResult.Found(
                    data.transactions.map { PgTransaction(it.transactionKey, toStatus(it.status), it.reason, amount = null) },
                )
            }
            ?: PgQueryResult.NotFound
    }

    /** 조회 실패는 "모른다" 다. 호출자는 상태를 바꾸지 않고 다음 주기를 기다린다. (설계 5.2 장) */
    private fun <T> query(block: () -> PgQueryResult<T>): PgQueryResult<T> = try {
        block()
    } catch (e: FeignException.NotFound) {
        PgQueryResult.NotFound
    } catch (e: Exception) {
        log.warn("PG 조회에 실패했습니다. {}", e.toString())
        PgQueryResult.Unavailable
    }

    /** 모르는 상태는 IllegalArgumentException 으로 query 의 catch 에 걸려 Unavailable 이 된다 — 확정하지 않는다. */
    private fun toStatus(value: String): PgTransactionStatus = PgTransactionStatus.valueOf(value)
}
```

```kotlin
package com.loopers.application.payment

import com.loopers.domain.order.OrderService
import com.loopers.domain.payment.PaymentCommand
import com.loopers.domain.payment.PaymentGateway
import com.loopers.domain.payment.PaymentModel
import com.loopers.domain.payment.PaymentService
import com.loopers.domain.payment.PaymentStatus

import com.loopers.domain.payment.PgRequestResult
import com.loopers.domain.product.Price
import com.loopers.domain.user.LoginId
import com.loopers.domain.user.UserModel
import com.loopers.domain.user.UserService
import com.loopers.support.error.CoreException
import com.loopers.support.error.ErrorType
import org.springframework.dao.OptimisticLockingFailureException
import org.springframework.stereotype.Component
import org.springframework.transaction.support.TransactionTemplate

/**
 * 결제 · 주문 두 애그리거트와 외부 PG 를 잇는 유스케이스.
 *
 * @Transactional 이 아니라 TransactionTemplate 인 이유 — PG 호출을 트랜잭션 밖에 두려면 한 메서드 안에서 두 번 커밋해야 한다.
 * PG 호출을 트랜잭션 안에 두면 요청마다 DB 커넥션을 PG 응답 시간만큼 쥐고, PG 가 느려지면 커넥션 풀이 말라
 * PG 와 무관한 API 까지 멈춘다. 서킷은 실패가 쌓인 뒤에야 열리므로 이걸 막지 못한다. (2026-10-13 결제 설계 4.1 장)
 *
 * tx1 을 PG 호출 전에 커밋하는 것이 복구의 전제다. 이후 무엇이 실패해도 주문은 PAYING, 결제는 REQUESTED 로 남아 동기화가 찾아낸다.
 *
 * 주의: 이 API 는 인증하지 않는다. 로그인 ID 를 아는 누구나 남의 주문을 PAYING 으로 묶어 둘 수 있다. (설계 9.3 장)
 */
@Component
class PaymentFacade(
    private val userService: UserService,
    private val orderService: OrderService,
    private val paymentService: PaymentService,
    private val paymentGateway: PaymentGateway,
    private val transactionTemplate: TransactionTemplate,
) {
    companion object {
        private const val REASON_NOT_SENT = "결제 시스템이 불안정합니다. 잠시 후 다시 시도해주세요."
    }

    fun request(command: PaymentCommand.Request): PaymentInfo {
        val payment = transactionTemplate.execute { startPayment(command) }!!
        if (payment.status == PaymentStatus.SUCCESS) {
            return PaymentInfo.of(payment)
        }

        val result = paymentGateway.request(
            PgPaymentRequest(
                userId = payment.userId,
                orderId = payment.orderId,
                cardType = payment.cardType,
                cardNo = payment.cardNo,
                amount = payment.amount,
            ),
        )

        // tx2 와 콜백의 확정이 겹치면 늦게 커밋하는 쪽이 @Version 검사로 실패한다. 콜백이 이겼다면 그 결과가 더 최신이므로
        // 덮어쓰지 않고 현재 상태를 돌려준다. 예외를 올리면 PG 가 접수한 결제 요청이 500 이 된다. (2026-10-13 결제 설계 5.2 장)
        return try {
            transactionTemplate.execute { applyRequestResult(payment.id, result) }!!
        } catch (e: OptimisticLockingFailureException) {
            PaymentInfo.of(paymentService.getPayment(payment.id)!!)
        }
    }

    /**
     * tx1. 주문을 PAYING 으로 바꾸고 결제를 REQUESTED 로 남긴다.
     *
     * ⚠️ paidAmount 를 startPayment 보다 먼저 읽는다. 조건부 UPDATE 가 clearAutomatically 라 호출 뒤 order 가 detach 된다.
     */
    private fun startPayment(command: PaymentCommand.Request): PaymentModel {
        val user = getUserOrThrow(command.loginId)
        val order = orderService.getOrder(command.orderId)
        if (order == null || order.userId != user.id) {
            throw CoreException(ErrorType.NOT_FOUND, "[orderId = ${command.orderId}] 존재하지 않는 주문입니다.")
        }
        val amount = order.paidAmount

        if (!orderService.startPayment(order.id)) {
            throw CoreException(ErrorType.CONFLICT, "[orderId = ${order.id}] 이미 결제 중이거나 결제가 완료된 주문입니다.")
        }

        val payment = paymentService.create(
            orderId = order.id,
            userId = user.id,
            amount = amount,
            cardType = command.cardType,
            cardNo = command.cardNo,
        )

        // 쿠폰으로 전액 할인된 주문. PG 는 0 원을 400 으로 거부하므로 PG 를 거치지 않고 확정한다.
        // 막으면 그 주문은 영원히 결제할 수 없다. (설계 4.3 장)
        // succeed 를 completePayment 보다 먼저 한다 — 조건부 UPDATE 의 flush 가 이 변경을 먼저 내보낸다.
        if (amount == Price.ZERO) {
            payment.succeed()
            orderService.completePayment(order.id)
        }
        return payment
    }

    /** tx2. PG 호출 결과를 반영한다. 즉시 실패로 확정하는 것은 NotSent 뿐이다. (설계 4.2 장) */
    private fun applyRequestResult(paymentId: Long, result: PgRequestResult): PaymentInfo {
        val payment = paymentService.getPayment(paymentId)!!
        when (result) {
            is PgRequestResult.Accepted -> payment.markPending(result.transactionKey)
            PgRequestResult.NotSent -> {
                payment.fail(REASON_NOT_SENT)
                orderService.failPayment(payment.orderId)
            }
            PgRequestResult.Unknown -> Unit
        }
        return PaymentInfo.of(payment)
    }

    private fun getUserOrThrow(loginId: LoginId): UserModel =
        userService.getUser(loginId)
            ?: throw CoreException(ErrorType.NOT_FOUND, "[loginId = ${loginId.value}] 존재하지 않는 회원입니다.")
}
```

```kotlin
    /**
     * PG 콜백. 본문에서 쓰는 것은 결제 건을 찾을 키와 주문 ID 뿐이다.
     * 키로 못 찾으면 주문의 진행 중 결제로 찾는다 — 키를 기록하기 전에 콜백이 온 경우다.
     * 단, 그 결제에 이미 다른 키가 있으면 이 콜백은 그 결제의 것이 아니다(고아 거래 또는 위조). 건드리지 않는다. (설계 5.1 장)
     */
    fun handleCallback(transactionKey: String, pgOrderId: String, now: ZonedDateTime = ZonedDateTime.now()) {
        paymentService.findByTransactionKey(transactionKey)?.let {
            sync(it.id, now)
            return
        }

        val unlinked = pgOrderId.toLongOrNull()
            ?.let { paymentService.findInProgressByOrderId(it) }
            ?.takeIf { it.transactionKey == null }
        if (unlinked == null) {
            // 1 분 뒤 FAILED 로 확정한 요청이 뒤늦게 승인된 고아 거래일 수 있다. 사람이 PG 를 조회해 확인한다. (설계 9.1 장)
            log.error("[transactionKey = {}, orderId = {}] 콜백과 이어지는 결제가 없습니다.", transactionKey, pgOrderId)
            return
        }
        // 생성 후 6 s 안이면 sync 가 아무것도 하지 않는다. 이 콜백은 놓치고 스케줄러가 30 s 뒤에 확정한다. (설계 5.2 장)
        sync(unlinked.id, now)
    }

    /** 스케줄러가 부른다. 한 건의 실패가 나머지를 막지 않게 건 단위로 잡는다. 처리한 건수를 돌려준다. */
    fun syncPending(now: ZonedDateTime = ZonedDateTime.now()): Int {
        val targets = paymentService.findSyncTargets(updatedBefore = now.minus(SYNC_DELAY), limit = SYNC_BATCH_SIZE)
        targets.forEach { payment ->
            runCatching { sync(payment.id, now) }
                .onFailure { log.error("[paymentId = {}] 결제 동기화에 실패했습니다.", payment.id, it) }
        }
        return targets.size
    }

    /**
     * PG 에 물어 결제를 확정한다. 콜백과 스케줄러가 함께 쓰는 유일한 확정 경로다. (설계 5.2 장)
     *
     * PG 조회는 트랜잭션 밖에서 한다. 요청과 같은 이유다 — 조회가 느려도 커넥션을 쥐지 않는다. (설계 4.1 장)
     * 조회가 실패하면(Unavailable) 아무것도 바꾸지 않는다. "모른다" 를 실패로 확정하지 않는다.
     */
    fun sync(paymentId: Long, now: ZonedDateTime = ZonedDateTime.now()) {
        val payment = paymentService.getPayment(paymentId) ?: return
        if (payment.status.isFinal) return
        // 키가 없는 결제는 요청이 아직 가는 중일 수 있다. 이때 PG 목록의 모르는 키를 연결하면 이중 결제가 날 수 있다. (설계 5.2 장)
        if (payment.transactionKey == null && payment.createdAt.isAfter(now.minus(IN_FLIGHT))) return

        val transactionKey = payment.transactionKey ?: when (val found = findUnlinkedTransaction(payment)) {
            is Unlinked.Found -> found.transactionKey
            Unlinked.None -> {
                giveUpIfExpired(payment.id, payment.createdAt, now, REASON_NOT_REACHED)
                return
            }
            Unlinked.Ambiguous -> {
                giveUpIfExpired(payment.id, payment.createdAt, now, REASON_AMBIGUOUS)
                return
            }
            Unlinked.Unavailable -> return
        }

        val detail = paymentGateway.findTransaction(payment.userId, transactionKey)
        if (detail !is PgQueryResult.Found) return
        inTransaction(payment.id) { confirm(payment.id, detail.value) }
    }

    /** 요청됨 결제의 PG 거래를 찾은 결과. Ambiguous 는 "모르는 키가 둘 이상" 이다. (설계 5.2 장) */
    private sealed interface Unlinked {
        data class Found(val transactionKey: String) : Unlinked

        data object None : Unlinked

        data object Ambiguous : Unlinked

        data object Unavailable : Unlinked
    }

    /**
     * 결제를 바꾸는 트랜잭션. 다른 경로(콜백 · 스케줄러 · 결제 요청의 tx2)가 같은 결제를 먼저 바꿨으면 @Version 검사로
     * 이 시도가 롤백되는데, 그건 정상 경합이다. 버리고 넘어간다 — 아직 확정 전이면 다음 동기화가 PG 에 다시 묻는다.
     * 예외를 올리면 콜백이 500 이 되고 스케줄러는 매번 ERROR 를 남긴다. (2026-10-13 결제 설계 5.2 장)
     */
    private fun inTransaction(paymentId: Long, block: () -> Unit) {
        try {
            transactionTemplate.executeWithoutResult { block() }
        } catch (e: OptimisticLockingFailureException) {
            log.info("[paymentId = {}] 다른 경로가 결제를 먼저 바꿔 이번 확정을 건너뜁니다.", paymentId)
        }
    }

    /**
     * 요청됨 결제의 거래를 PG 에서 찾는다. 우리가 모르는 키가 이번 요청의 거래다 — 과거 실패 결제의 키는 이미 연결돼 있고,
     * 진행 중 결제가 주문당 1 건이라 정상이면 모르는 키는 많아야 하나다. (설계 5.2 장)
     *
     * 둘 이상이면 1 분 뒤 포기한 결제가 뒤늦게 승인된 고아 거래가 섞인 것이다. PG 목록에는 금액도 시각도 없어 어느 쪽이 이번 요청인지
     * 가릴 수 없다. firstOrNull 로 하나를 고르면 고아의 결과로 이번 결제를 확정하게 되므로 연결하지 않는다. (설계 9.5 장)
     */
    private fun findUnlinkedTransaction(payment: PaymentModel): Unlinked =
        when (val result = paymentGateway.findTransactionsByOrder(payment.userId, payment.orderId)) {
            is PgQueryResult.Found -> {
                val known = paymentService.findAllByOrderId(payment.orderId).mapNotNull { it.transactionKey }.toSet()
                val unknown = result.value.map { it.transactionKey }.filter { it !in known }.distinct()
                when (unknown.size) {
                    0 -> Unlinked.None
                    1 -> Unlinked.Found(unknown.single())
                    else -> {
                        log.error("[paymentId = {}] 모르는 PG 거래가 둘 이상이라 연결하지 않습니다. keys = {}", payment.id, unknown)
                        Unlinked.Ambiguous
                    }
                }
            }
            PgQueryResult.NotFound -> Unlinked.None
            PgQueryResult.Unavailable -> Unlinked.Unavailable
        }

    private fun giveUpIfExpired(paymentId: Long, createdAt: ZonedDateTime, now: ZonedDateTime, reason: String) {
        if (createdAt.isAfter(now.minus(GIVE_UP_AFTER))) return
        inTransaction(paymentId) {
            val payment = paymentService.getPayment(paymentId)!!
            // 조회와 이 트랜잭션 사이에 콜백이 키를 연결했을 수 있다. 요청됨일 때만 포기한다.
            // 이 확인과 커밋 사이에 끼어든 확정은 @Version 이 막는다.
            if (payment.status != PaymentStatus.REQUESTED) return@inTransaction
            payment.fail(reason)
            orderService.failPayment(payment.orderId)
        }
    }

    /**
     * 결제와 주문을 한 트랜잭션에서 확정한다. 다른 경로가 먼저 확정했으면 결제 전이는 무시되고 주문 UPDATE 는 0 행이다.
     *
     * 결제 전이를 주문 UPDATE 보다 먼저 한다 — 조건부 UPDATE 의 flush 가 결제 변경을 먼저 내보내고 컨텍스트를 비운다.
     * 버전 검사도 그 flush 에서 일어나므로, 경합에 진 쪽은 주문을 건드리기 전에 실패하고 통째로 롤백된다.
     * 이 순서를 뒤집으면 진 쪽이 주문 UPDATE 를 먼저 실행한다. 롤백되긴 하지만 그동안 주문 행 락을 쥐어 이긴 쪽을 기다리게 한다.
     */
    private fun confirm(paymentId: Long, transaction: PgTransaction) {
        val payment = paymentService.getPayment(paymentId)!!
        if (payment.status.isFinal) return

        payment.markPending(transaction.transactionKey)
        if (transaction.amount != payment.amount.value) {
            // 위조나 버그의 신호라 PG 의 결과를 반영하지 않는다. 그대로 두면 상태가 영영 안 바뀌어 매 주기 동기화 대상으로 남고
            // 쌓이면 스케줄러 앞자리를 막으므로 실패로 닫는다. 키는 위에서 기록했다 — 뒤늦은 콜백이 이 결제 건을 찾게.
            // PG 에서 돈이 나갔을 수 있어 후속은 수동이다. (설계 5.2 · 9.5 장)
            log.error(
                "[paymentId = {}, transactionKey = {}] PG 금액({})이 결제 금액({})과 다릅니다. 실패로 닫습니다.",
                paymentId,
                transaction.transactionKey,
                transaction.amount,
                payment.amount.value,
            )
            payment.fail(REASON_AMOUNT_MISMATCH)
            orderService.failPayment(payment.orderId)
            return
        }
        when (transaction.status) {
            PgTransactionStatus.PENDING -> Unit
            PgTransactionStatus.SUCCESS -> {
                payment.succeed()
                orderService.completePayment(payment.orderId)
            }
            PgTransactionStatus.FAILED -> {
                payment.fail(transaction.reason ?: REASON_PG_FAILED)
                orderService.failPayment(payment.orderId)
            }
        }
    }
```
